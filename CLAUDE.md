## 1. О проекте

Школьный проект по информационной безопасности: локальный менеджер
паролей на Python с зашифрованным хранилищем записей (сайт / логин /
пароль) и мастер-паролем. Позже планируется добавить локального
ИИ-помощника (без отправки секретов во внешние сервисы) и графический
интерфейс. На первом этапе — только CLI.

Ключевая идея защиты проекта: **каждое крипто-решение обосновано**, а не
взято "потому что все так делают". Ниже — обоснования, они же дублируются
комментариями на русском прямо в коде рядом с соответствующими строками.

## 2. Технологический стек

| Компонент          | Выбор                          | Почему |
|---------------------|--------------------------------|--------|
| Язык                | Python 3.11+                   | Стандарт для учебного проекта, богатая крипто-экосистема, `match`-синтаксис и улучшенные ошибки типизации доступны с 3.10+. |
| Шифрование данных    | AES-256-GCM (`cryptography`)   | AEAD-шифр: даёт конфиденциальность **и** целостность/подлинность (auth tag) за один примитив. 256-битный ключ — запас прочности сверх практически достижимого перебора. |
| Вывод ключа из пароля | Argon2id (`argon2-cffi`)      | Победитель Password Hashing Competition (2015), устойчив и к GPU-перебору (за счёт требований к памяти), и к side-channel атакам (гибрид Argon2i + Argon2d). Рекомендован OWASP как основной выбор для хранения/вывода ключей из паролей. |
| CLI                 | стандартная библиотека (`argparse`) | Не тянуть лишних зависимостей на этапе, где важна крипто-логика, а не UX. |
| Тесты               | `pytest`                       | Стандарт де-факто, простой синтаксис assert. |

### Почему не PBKDF2?

PBKDF2 (даже с высоким числом итераций) уязвим к параллельному перебору
на GPU/ASIC, потому что не требует памяти — только вычислений. Argon2id
делает перебор экономически дорогим: каждая попытка требует выделения
существенного объёма RAM (в коде — `time_cost=3`, `memory_cost=64 MiB`,
`parallelism=4`, см. `vault/crypto.py`; это с запасом больше минимальных
рекомендаций OWASP `m=19 MiB, t=2, p=1` — вывод ключа выполняется редко,
при открытии хранилища, поэтому можно позволить себе более медленный и
дорогой по памяти вариант), а RAM нельзя дёшево распараллелить так,
как арифметику. Именно поэтому Argon2id — сегодняшняя рекомендация NIST/
OWASP для вывода ключей из пользовательских паролей, а PBKDF2 считается
устаревшим для новых проектов (сохраняется только для обратной
совместимости).

### Почему Argon2**id**, а не Argon2i / Argon2d?

- Argon2**d** максимально устойчив к GPU-перебору, но уязвим к
  side-channel атакам (по времени доступа к памяти), т.к. доступ к памяти
  зависит от самого пароля.
- Argon2**i** устойчив к side-channel, но слабее против GPU-перебора.
- Argon2**id** — гибрид: первая половина проходов использует
  data-independent доступ (как Argon2i, защита от side-channel), вторая —
  data-dependent (как Argon2d, защита от GPU/ASIC). Это и есть выбор,
  рекомендуемый OWASP по умолчанию.

### Почему AES-256-GCM, а не AES-CBC / ChaCha20 / просто AES без режима AEAD?

- **AES-CBC** не даёт аутентификации сама по себе — нужен отдельный HMAC
  ("encrypt-then-MAC"), что легко реализовать неправильно (например,
  перепутать порядок MAC/шифрования, что открывает padding oracle атаки).
  GCM убирает этот класс ошибок, объединяя шифрование и аутентификацию.
- **ChaCha20-Poly1305** — тоже валидный современный выбор (особенно на
  платформах без аппаратного ускорения AES), но AES-GCM выбран из-за
  повсеместной аппаратной поддержки (AES-NI) и того, что это самый
  "canonical" пример AEAD для образовательного проекта — легче объяснить
  на защите с опорой на широко известные источники (NIST SP 800-38D).
- Размер ключа 256 бит — сознательный запас (не 128), обычная практика
  для хранилищ секретов.

## 3. Формат файла хранилища

Один бинарный файл, layout (big-endian, если не указано иное):

```
смещение   размер   поле         назначение
--------   ------   -----------  --------------------------------------------
0          4 байта  MAGIC        b"PMGR" — быстрая проверка "это точно наш формат"
4          1 байт   VERSION      номер версии формата (сейчас: 1) — для миграций в будущем
5          16 байт  SALT         соль для Argon2id (генерируется заново при каждом encrypt_vault)
21         12 байт  NONCE        nonce для AES-GCM (генерируется заново при каждом encrypt_vault)
33         остаток  CIPHERTEXT   AES-GCM ciphertext, ПОСЛЕДНИЕ 16 байт которого — auth tag
```

Итоговая структура на диске: `MAGIC || VERSION || SALT || NONCE || CIPHERTEXT`.

### Почему SALT и NONCE хранятся в открытом виде рядом с шифротекстом?

Это стандартная и безопасная практика:
- **Соль** для Argon2id не обязана быть секретной — её единственная
  задача не дать злоумышленнику посчитать один rainbow-table на все
  хранилища сразу и заставить пересчитывать KDF для каждого хранилища
  отдельно. Секретность даёт сам мастер-пароль + параметры Argon2id.
- **Nonce** для GCM тоже публичен по определению режима — секретность
  обеспечивает ключ, а не nonce.

### Почему nonce обязан быть уникальным (и что будет, если это нарушить)

Для AES-GCM **повторное использование пары (ключ, nonce)** — это
катастрофический сценарий: XOR двух шифротекстов с одинаковым
keystream'ом снимает шифрование почти полностью (classic
"two-time pad"), а для GCM это ещё и позволяет восстановить
аутентификационный ключ и подделывать сообщения (forgery). Поэтому:
- nonce генерируется криптографически случайным образом (`os.urandom`)
  заново при **каждом** вызове `encrypt_vault` — вместе с новой солью,
  значит и производный ключ будет новым, но даже без этого 12-байтный
  случайный nonce на GCM безопасен, пока хранилище не переписывается
  триллионы раз одним и тем же ключом (см. NIST SP 800-38D, вероятность
  коллизии).
- Каждое сохранение хранилища = новый вызов `encrypt_vault` = новая соль
  + новый nonce + полное перешифрование всего JSON целиком (мы не делаем
  "инкрементальное" шифрование отдельных записей — так проще не ошибиться
  с уникальностью nonce).

### Что внутри зашифрованного JSON

```json
{
  "canary": "PMGR-OK",
  "entries": [
    {
      "site": "example.com",
      "username": "user@example.com",
      "password": "...",
      "created_at": "2026-09-11T12:00:00Z"
    }
  ]
}
```

- **canary** — константная строка-маркер. После расшифровки мы проверяем,
  что она равна ожидаемому значению. Это даёт дружелюбную ошибку
  "неверный мастер-пароль" вместо путаницы для пользователя — хотя сам
  AES-GCM auth tag уже отклонит расшифровку при неверном ключе (см. ниже),
  canary — это дополнительный, человекочитаемый уровень проверки на
  случай будущих изменений формата.
- **entries** — список записей: сайт, логин, пароль, дата создания
  (ISO 8601, UTC).

### Почему проверка мастер-пароля не требует отдельного хеша

Мы **не храним** отдельно хеш мастер-пароля для "проверки логина" — это
намеренно. Если бы мы хранили `Argon2id(master_password)` отдельно от
ключа шифрования, то при компрометации файла хранилища атакующий получил
бы дополнительную зацепку для офлайн-перебора. Вместо этого сам факт
успешной расшифровки AES-GCM (валидный auth tag) **и** совпадение
canary-строки — это и есть проверка мастер-пароля. Один секрет — один
источник истины.

## 4. Обработка неверного мастер-пароля

Два независимых уровня защиты от "тихого" принятия неверного пароля:

1. **AES-GCM auth tag.** Если мастер-пароль неверен, производный ключ
   будет другим, и расшифровка с высочайшей вероятностью либо бросит
   исключение аутентификации (tag mismatch), либо (в исчезающе малой
   доле случаев) даст на выходе случайный мусор вместо валидного JSON —
   что отловит следующий уровень.
2. **Проверка canary + валидация JSON.** После успешной расшифровки (тег
   совпал) мы дополнительно парсим JSON и сверяем canary-строку. Это
   защищает от искусственно сконструированных случаев и делает код
   защищённее при будущих изменениях формата.

`decrypt_vault` должна кидать одно и то же понятное исключение
(например, `InvalidMasterPasswordError`) в обоих случаях — снаружи не
должно быть заметно, на каком именно уровне отклонён пароль (это тоже
осознанное решение: не давать атакующему лишнюю информацию через разницу
в поведении/сообщениях об ошибке).

## 5. Атомарная запись хранилища

Файл хранилища — это единственный источник правды обо всех паролях
пользователя. Потеря или повреждение файла при сбое посреди записи
(отключение питания, kill -9, переполнение диска) неприемлемы. Поэтому
запись всегда выполняется по схеме:

1. Сформировать новый blob (`MAGIC || VERSION || SALT || NONCE || CIPHERTEXT`) в памяти.
2. Записать его во **временный файл в той же директории**, что и
   целевой файл (важно — та же файловая система/раздел).
3. `flush()` + `os.fsync()` временного файла, чтобы данные точно ушли на диск,
   а не остались в буфере ОС.
4. `os.replace(tmp_path, target_path)` — на POSIX и Windows это
   атомарная операция переименования: в любой момент времени файл по
   целевому пути либо старый, либо новый целиком, **никогда** не
   "наполовину записанный".

Если процесс упадёт на шаге 2–3, у нас останется нетронутый старый
файл + мусорный временный файл (можно чистить). Если упадёт после шага 4
— запись уже полностью завершена. Промежуточного "битого" состояния
целевого файла не существует в принципе — в этом и есть смысл атомарности.

Реализация в `vault/storage.py` (`save_vault_file`) добавляет две детали
сверх этой схемы:

- Используется `os.replace()`, а не `os.rename()`: `replace()` атомарно
  перезаписывает уже существующий целевой файл на любой ОС, тогда как
  `rename()` на Windows падает с ошибкой, если файл назначения занят.
- После `os.replace()` дополнительно вызывается `os.fsync()` для самой
  директории (кроме Windows, где открыть директорию через `os.open()`
  нельзя) — само переименование тоже является записью (в метаданные
  каталога: какое имя на какой inode указывает), и эта запись тоже может
  задержаться в буфере ОС. Без этого шага теоретически возможен сценарий
  "process crash сразу после успешного `save_vault_file()`, при котором
  ОС ещё не зафиксировала само переименование на диске".
- При любой ошибке до `os.replace()` временный файл удаляется в блоке
  `except` — на диске не остаётся мусора вида `.vault.bin.XXXXXX.tmp`.

### Детали CLI (`vault/cli.py`)

- Файл хранилища по умолчанию — `~/passwords.vault` (можно переопределить
  флагом `--path`, который указывается ПЕРЕД именем команды:
  `vault --path другой/файл.vault add example.com`).
- Мастер-пароль и пароль записи всегда запрашиваются через
  `getpass.getpass()`, а не `input()` или аргумент командной строки —
  секреты не отображаются на экране и не попадают ни в историю шелла,
  ни в вывод `ps aux` (в отличие от передачи пароля через `sys.argv`).
- `create` требует минимум 8 символов для мастер-пароля и подтверждение
  вводом дважды. Это НЕ крипто-механизм (см. `MIN_MASTER_PASSWORD_LENGTH`
  в коде) — обычная защита формы ввода от совсем тривиальных паролей,
  реальную стойкость даёт Argon2id (раздел 2).
- `create` дополнительно (после проверки длины) предупреждает, если
  мастер-пароль формально СЛАБЫЙ — по той же планке
  `WEAK_ENTROPY_THRESHOLD_BITS`/списку утёкших паролей, что советник
  уже применяет к паролям записей (`assistant.advisor`, раздел 9.3), а
  не по отдельному порогу, придуманному только для этого места (раздел
  10.18 — там же обоснование, почему это ПРЕДУПРЕЖДЕНИЕ, а не жёсткая
  блокировка). Подтверждается той же формой `y/N`, что и `delete`.
- `create` отказывается перезаписывать существующее хранилище без флага
  `--force` — случайное затирание всех паролей одной командой было бы
  необратимой потерей данных.
- `add` перечитывает и заново шифрует **весь** JSON хранилища (не только
  добавляемую запись) — соответствует модели из раздела 3: каждое
  сохранение хранилища = один вызов `encrypt_vault` с новыми salt/nonce.
- `get`/`update`/`delete` находят записи через общий `_find_matches(data,
  site, username)`: точное совпадение по `site`, а `username` сужает
  выбор, если на сайте несколько аккаунтов. `list` показывает только
  сайты и логины — пароли в `list` никогда не выводятся.
- `update` требует однозначно определить ровно одну запись (иначе просит
  уточнить `--username`) и при смене пароля обновляет `created_at` на
  текущий момент — семантически это поле означает "когда пароль был
  последний раз установлен", а не буквально "когда создана запись": это
  ровно то, что нужно эвристике устаревших паролей (`assistant.advisor`,
  раздел 9.3) — после ротации пароль закономерно перестаёт считаться
  устаревшим.
- `delete` перед удалением печатает список того, что будет удалено, и
  запрашивает подтверждение (`y`/`yes`/`да`), если не передан `--yes` —
  необратимая операция не должна срабатывать от одной опечатки. Записи
  для удаления сравниваются по `id()` объекта, а не по значению — иначе
  две записи с полностью совпадающим содержимым (гипотетически, включая
  `created_at` до секунды) удалились бы обе, даже если выбрана была
  только одна.
- Все внутренние исключения (`InvalidMasterPasswordError`,
  `VaultFormatError`, отсутствие файла хранилища) превращаются в
  понятные сообщения в stderr и код возврата процесса — наружу traceback
  не протекает.

## 9. Локальный ИИ-помощник

Решено, что ИИ-помощник должен уметь:

1. ✅ **Советник по безопасности** — эвристический анализ хранилища:
   повторно используемые пароли (сравнение хешей/значений между
   записями), низкая энтропия, "старые" пароли (по `created_at`).
   **Реализовано** в `assistant/advisor.py` — см. 9.3.
2. ✅ **Советы по усложнению паролей** — конкретные рекомендации, как
   усилить существующий пароль. **Реализовано** как часть отчёта
   советника (`EntryIssue.reasons` в `assistant/advisor.py`) — каждая
   найденная проблема сразу сопровождается причиной ("содержит имя
   пользователя", "низкая оценка энтропии" и т.п.).
3. ✅ **Генератор надёжных паролей с объяснением** — сама генерация идёт
   через криптографически стойкий ГПСЧ (`secrets`), а не через LLM (это
   вопрос криптостойкости, не текста). **Реализовано** в
   `assistant/generator.py` — см. 9.3. Объяснение пока текстовый шаблон
   (`explain_password`); заменить/дополнить его LLM можно позже, не
   меняя сам генератор.
4. ⏳ **Разговорный помощник на локальной LLM** — свободный чат поверх
   вышеперечисленного. Не реализовано — зависит от открытого вопроса
   про движок ниже.

**Ключевое архитектурное правило (обязательно к соблюдению):**
расшифрованный пароль (или мастер-пароль) НИКОГДА не передаётся в prompt
LLM — ни в открытом виде, ни в замаскированном. Модель в лучшем случае
получает метаданные (длина, набор символов, факт повторного
использования, оценка энтропии), а не сам секрет. Показ самого пароля
пользователю (`get`) всегда идёт напрямую через `vault.crypto`, в обход
модели — это гарантирует, что даже баг или "галлюцинация" модели не
может привести к утечке пароля через её вывод.

**Решено: движок инференса — `llama-cpp-python`.**
Рассматривались два варианта: `llama-cpp-python` (модель грузится прямо
в процессе Python, без отдельного сервиса) и `Ollama` (отдельный демон
на `localhost`, к которому обращаются по HTTP). Оба варианта не
отправляют данные в сеть за пределы машины пользователя, но
`llama-cpp-python` выбран по трём причинам:

1. **Проще доказать "без сети" на защите** — один процесс, ни одного
   сетевого сокета вообще, а не HTTP-запрос на loopback, для которого
   пришлось бы объяснять разницу "не выходит в интернет" vs "нет сети
   совсем".
2. **Проще запустить проверяющему** — один `pip install`, без
   отдельной установки и ручного запуска стороннего сервиса (`ollama
   serve`), который мог бы забыться и сорвать демонстрацию.
3. **Естественно стыкуется с пайплайном дообучения** (раздел 9.2):
   `unsloth` сам умеет сохранять результат дообучения сразу в `.gguf`
   — ровно тот формат, который напрямую загружает `llama-cpp-python`,
   без Ollama-специфичных шагов конвертации/импорта модели.

Модуль `assistant/llm.py` (см. структуру в разделе 9.1) будет
обёрткой именно над `llama-cpp-python`.

### 9.1. Требование: модель нужно будет дообучать

Это важное уточнение, которое меняет техническую реализацию (не сам
выбор движка инференса, а то, ЧТО именно мы для него готовим).

**Почему это важно.** `llama.cpp` (а значит и `Ollama`, которая
использует тот же движок под капотом) — это инструмент только для
**инференса**: он работает с уже готовыми весами в формате GGUF
(обычно квантованными до 4-8 бит) и не умеет дообучать модель. Значит,
пайплайн придётся разделить на два принципиально разных этапа с разными
инструментами:

1. **Дообучение (offline, один раз, на этапе разработки).**
   - Берём модель в исходном формате Hugging Face (`safetensors`,
     fp16/bf16) — **не** готовый квантованный `.gguf`, его дообучать
     стандартными средствами нельзя.
   - Дообучаем через LoRA/QLoRA (`transformers` + `peft`, опционально
     `bitsandbytes` для 4-бит квантования во время обучения) —
     параметро-эффективное дообучение, при котором меняется не вся
     модель, а маленькая "надстройка" поверх замороженных весов. Это
     на порядки дешевле полного fine-tuning'а и реалистично выполнимо
     на скромном железе (или бесплатном Google Colab) — важно для
     школьного проекта, где нет доступа к кластеру GPU.
   - Результат дообучения (LoRA-адаптер) сливаем с базовой моделью
     (`merge_and_unload()` в `peft`) и конвертируем в `.gguf` через
     `convert-hf-to-gguf.py` из репозитория `llama.cpp` (на практике
     этот шаг делает сам `unsloth`, см. 9.2) — только ПОСЛЕ этого шага
     модель готова к офлайн-инференсу через `llama-cpp-python` в самом
     приложении (движок выбран, см. решение выше).
2. **Инференс (runtime, у пользователя, полностью офлайн).**
   - Приложение грузит уже готовый `.gguf` — дообучение на этом этапе
     не происходит и не нужно.

**Следствие для структуры проекта** — пайплайн дообучения физически
отделён от кода приложения:

```
menedger/
├── vault/                    — как сейчас
├── assistant/                — RUNTIME: код, который работает у
│   │                           пользователя (инференс через .gguf)
│   ├── advisor.py
│   ├── generator.py
│   ├── nlu.py
│   └── llm.py
├── training/                 — DEV-ONLY: пайплайн дообучения, не
│   │                           часть поставляемого приложения
│   ├── data/dataset.jsonl    — обучающие примеры (instruction/response)
│   ├── prepare_dataset.py
│   ├── finetune.py           — LoRA-дообучение (transformers + peft)
│   └── merge_and_convert.py  — слияние адаптера + конвертация в GGUF
└── requirements-training.txt — torch/transformers/peft и т.п. —
                                 ОТДЕЛЬНО от requirements.txt, чтобы
                                 обычному пользователю менеджера паролей
                                 не нужно было ставить многогигабайтный
                                 ML-стек ради самого приложения
```

**Важное уточнение границы "без сети" (см. раздел 1 и правило про
LLM выше):** требование "без отправки секретов во внешние сервисы"
относится к **runtime** — моменту, когда приложение уже работает с
расшифрованными паролями пользователя. Одноразовая загрузка базовой
модели с Hugging Face Hub на этапе `training/` (в процессе разработки,
до того как в системе появился хоть один пароль пользователя) — это
другая граница доверия и **не является нарушением** этого требования.
На защите стоит явно проговорить это разделение "build-time network
access" vs "runtime — строго офлайн".

### 9.2. Дообучение и LoRA простыми словами (для защиты)

Этот подраздел — не про код, а про то, чтобы можно было объяснить
комиссии на защите, что вообще происходит с ИИ-частью проекта, не имея
специального ML-образования. Ниже — та же идея, что и в разделе 9.1, но
без жаргона, с аналогиями.

**Что такое базовая модель.** Готовая скачанная LLM (например,
Qwen2.5-0.5B) — это уже обученный "универсал": она умеет писать связный
текст на русском и немного знает обо всём на свете, потому что училась
на огромном количестве текста из интернета. Но она не заточена именно
под нашу задачу — советы по безопасности паролей в нужном нам стиле и
формате.

**Что такое дообучение (fine-tuning).** Это "донастройка" уже готовой
модели на небольшом наборе примеров вида *"вопрос → правильный,
желаемый ответ"*, специфичных именно для нашей задачи. Аналогия: у вас
уже есть сотрудник, который хорошо говорит по-русски и вообще неглупый
(базовая модель) — вы даёте ему прочитать методичку компании
("здесь мы отвечаем на такие вопросы вот так, в таком тоне, с такими
рекомендациями") — обучающий датасет. После этого он не становится
другим человеком, но начинает отвечать точнее именно на вопросы из
методички и в нужном стиле.

**Что такое LoRA и почему не переобучаем модель целиком.** Полное
переобучение модели — это заново пересчитать ВСЕ её "веса" (миллионы
или миллиарды чисел) — очень дорого по времени и по вычислительной
мощности (нужны серьёзные видеокарты, дни или недели работы). LoRA
(Low-Rank Adaptation) — это не переучивание "с нуля", а прикрепление
маленькой "стикер-заметки" поверх уже готовой модели: сама модель
остаётся замороженной (неизменной), а обучается только эта маленькая
добавка размером в несколько мегабайт. Из-за этого:

- обучение занимает минуты-часы, а не дни, даже на скромной видеокарте;
- можно уместиться в бесплатный Google Colab (видеокарта в браузере,
  ничего не покупать и не устанавливать на свой компьютер);
- то, что происходит "под капотом", реально понять и объяснить, а не
  просто зачитать код: "мы не трогаем большую модель, мы добавляем
  маленькую обучаемую надстройку поверх неё".

**Максимально простой практический план (не требует опыта в ML):**

1. **Google Colab** — открываем в браузере готовый ноутбук с уже
   написанным кодом, ничего не устанавливаем локально.
2. **Библиотека `unsloth`** — берёт на себя почти весь сложный код
   LoRA-дообучения: загрузка модели, настройка LoRA-надстройки, цикл
   обучения — сводится к нескольким понятным вызовам функций. Умеет
   сама сохранить результат сразу в формат `.gguf`, готовый для
   `llama.cpp` — то есть отдельный шаг "слить LoRA с моделью и
   сконвертировать" (упомянутый в разделе 9.1 как `merge_and_convert.py`)
   `unsloth` делает одной командой сам.
3. **Датасет** — обычный текстовый файл с примерами
   "вопрос → хороший ответ" (60–200 штук достаточно для учебного
   проекта). Написать и проверить такие примеры — задача про контент
   (знание предметной области — информационная безопасность), а не про
   ML: с этим справится любой, кто понимает, что такое хороший ответ на
   вопрос про пароли.
4. Итог этапа: файл `assistant_model.gguf`, который приложение (модуль
   `assistant/llm.py`) загружает через `llama-cpp-python` — полностью
   офлайн, без Colab, без интернета, без всего, что было на этапе
   обучения.

**Шпаргалка для ответов на вопросы комиссии:**

| Могут спросить | Короткий ответ |
|---|---|
| "Вы сами обучали нейросеть с нуля?" | Нет, и это осознанный выбор: обучение современной LLM с нуля стоит миллионы долларов. Мы взяли готовую открытую модель и **дообучили** её под свою узкую задачу — это стандартная и единственная реалистичная практика даже в индустрии. |
| "Что такое LoRA?" | Способ дообучить модель, не трогая большую часть её весов — обучается только маленькая "надстройка" поверх замороженной модели, поэтому это быстро и дёшево по вычислениям. |
| "Где физически шло обучение?" | В Google Colab, на этапе разработки, один раз. Итоговый файл модели (`.gguf`) уже готовый и офлайн — на компьютере пользователя во время работы приложения обучение не происходит и интернет не нужен. |
| "А не утечёт ли что-то в интернет при обучении?" | На этапе обучения в системе ещё нет ни одного пароля пользователя — датасет состоит из наших собственных обучающих примеров, а не из реальных данных хранилища. Секреты появляются только после того, как пользователь запустит уже готовое офлайн-приложение. |
| "Почему не использовали ChatGPT/API для этой части?" | Требование проекта — ИИ-часть должна работать полностью локально и не отправлять данные пользователя во внешние сервисы (см. раздел 1); облачный API по определению это нарушает. |

### 9.3. Реализовано: эвристический советник и генератор паролей

Пункты 1–3 из раздела 9 реализованы БЕЗ какой-либо LLM — они не зависят
от открытого вопроса про движок инференса (9) и требования дообучения
(9.1/9.2), поэтому сделаны уже сейчас:

```
assistant/
├── __init__.py
├── strength.py   — общая оценка "силы" пароля (используется и
│                   советником, и генератором — единая формула)
├── advisor.py    — analyze_vault(data) -> AdvisorReport,
│                   format_report(report) -> str
└── generator.py  — generate_password(...), explain_password(...)
```

- [x] `assistant/strength.py`, `assistant/advisor.py`,
      `assistant/generator.py` — реализованы.
- [x] `tests/test_strength.py`, `tests/test_advisor.py`,
      `tests/test_generator.py` — 25 тестов, все проходят.
- [x] `vault/cli.py` дополнен командами `audit` и `generate`.

**`assistant/strength.py` — оценка энтропии.** Пароль оценивается по
формуле `длина × log2(размер_алфавита)`, где размер алфавита считается
по тому, какие классы символов встречаются в пароле (строчные/
заглавные буквы, цифры, спецсимволы — 26/26/10/30 соответственно).
**Важное ограничение, которое стоит проговорить на защите:** это НЕ
полноценный анализ вроде zxcvbn — формула предполагает независимые
случайные символы, поэтому для пароля, придуманного человеком, она
завышает реальную стойкость (человек предсказуемее равномерного
распределения). Компенсируется двумя дополнительными эвристиками:
проверкой по списку самых частых утёкших паролей (`COMMON_PASSWORDS`)
и проверкой на вхождение логина/сайта в сам пароль.

**`assistant/advisor.py` — советник.** `analyze_vault()` принимает уже
расшифрованные данные (`{"entries": [...]}`, ровно то, что возвращает
`vault.crypto.decrypt_vault`) и ищет три типа проблем: повторно
используемые пароли (группировка записей по одинаковому значению
пароля), слабые пароли (частый пароль / содержит логин или сайт /
низкая энтропия — порог `WEAK_ENTROPY_THRESHOLD_BITS = 50`, что
соответствует примерно 8-символьному паролю из большого алфавита) и
устаревшие пароли (не менялись дольше `OLD_PASSWORD_THRESHOLD_DAYS =
180` дней). Модуль не знает про мастер-пароль и не трогает файл
хранилища — то же разделение ответственности, что между
`vault.crypto` и `vault.storage`.

**`assistant/generator.py` — генератор.** `generate_password()`
использует `secrets.choice()` (а не `random.choice()`) по тем же
причинам, что `os.urandom()` используется для salt/nonce в
`vault/crypto.py` (см. раздел 2) — предсказуемый Mersenne Twister
непригоден для генерации секретов. Каждый символ выбирается независимо
и равномерно из объединённого алфавита включённых классов, поэтому для
сгенерированного (а не придуманного человеком) пароля формула энтропии
из `strength.py` — точная, а не грубая оценка. Есть до 10 попыток
перегенерации, если случайно не попал символ одного из явно включённых
классов (нужно некоторым сайтам, требующим обязательный спецсимвол
и т.п.) — при разумной длине это происходит практически всегда с
первой попытки.

**Новые команды CLI:**
- `vault audit` — расшифровывает хранilище и печатает отчёт советника.
- `vault generate [--length N] [--no-symbols] [--no-digits] [--no-uppercase] [--no-lowercase]`
  — не требует мастер-пароля (не трогает хранилище); пароль печатается
  в stdout, объяснение силы — в stderr, чтобы `vault generate | xclip`
  и подобные конвейеры получали в stdout только сам пароль.

## 10. Графический интерфейс (`gui/app.py`)

Реализован на **Tkinter** — по той же логике, что и выбор `argparse` для
CLI (раздел 2): это часть стандартной библиотеки Python, ни одной
дополнительной внешней зависимости. Рассматривались также PySide6/Qt
(современнее внешне, но тяжёлая зависимость и сложнее лицензионно
объяснить на защите) и локальный веб-интерфейс (Flask/FastAPI + браузер
— но это добавило бы ещё один сетевой компонент на localhost, ту же
дискуссию, что была при выборе движка LLM в разделе 9, только без
реальной необходимости). Для учебного проекта Tkinter — самый
объяснимый вариант: «ничего не добавляли, всё уже было в Python».

**Ключевой архитектурный принцип: GUI — тонкая презентационная
надстройка.** `gui/app.py` не содержит ни крипто-логики, ни бизнес-логики
поверх той, что уже есть в `vault.crypto`/`vault.storage`/`assistant.*` —
он только вызывает те же функции, что и `vault/cli.py`, в ответ на клики
и ввод в полях вместо команд терминала и `input()`/`getpass()`. Общие
константы (`DEFAULT_VAULT_PATH`, `MIN_MASTER_PASSWORD_LENGTH`, формат
даты) вынесены в `vault/common.py`, чтобы CLI и GUI гарантированно не
разошлись в этих деталях — раньше они были приватными объектами внутри
`vault/cli.py`, и GUI пришлось бы либо дублировать их, либо тянуть
приватные (`_`-префиксные) имена из чужого модуля.

**Устройство окна:**
- Два "экрана"-`Frame` внутри одного окна: разблокировка/создание
  хранилища и основной список записей (`ttk.Treeview` с колонками
  «Сайт»/«Логин» — пароли в списке никогда не показываются, как и в
  `vault list`). Показывается только один экран за раз. Раскладка обоих
  экранов — "Разделённая панель" (тёмный сайдбар/фон + светлая рабочая
  область), см. раздел 10.4.
- Разовые действия — отдельные модальные `Toplevel`-диалоги:
  добавление записи, просмотр записи целиком, отчёт советника
  (`assistant.advisor`), генератор паролей (`assistant.generator`).
  Просмотр записи открывается двойным кликом по строке в списке
  (`<Double-1>` на `Treeview`) — отдельная кнопка "Открыть запись" на
  панели инструментов изначально дублировала этот же жест один-в-один
  и была убрана как лишняя.
- Мастер-пароль и пароль записи вводятся через `Entry(show="*")` —
  тот же смысл, что у `getpass.getpass()` в CLI: символы не видны на
  экране.
- Кнопка «Копировать пароль» кладёт пароль в системный буфер обмена и
  сама очищает его через 20 секунд (`CLIPBOARD_CLEAR_DELAY_MS`), если
  буфер к этому моменту всё ещё содержит именно этот пароль (проверяется
  перед очисткой, чтобы не стереть то, что пользователь скопировал уже
  после) — иначе пароль мог бы бессрочно висеть в буфере, доступном
  любому другому процессу в системе.
- Кнопка «Заблокировать» явно обнуляет `self.data`/`self.master_password`/
  `self.vault_path` и возвращает к экрану разблокировки. **Важная
  оговорка для защиты:** строки в Python неизменяемы, поэтому обнуление
  ссылки — это не криптографическое затирание байт пароля в памяти;
  сборщик мусора освобождает память не гарантированно немедленно и не
  обязательно перезаписывает её нулями. Это снижает, но не устраняет
  риск полностью — тот же компромисс, с которым CLI живёт всё время,
  пока процесс запущен; GUI просто дольше держит эти данные "в живых"
  между действиями пользователя, чем однократный вызов CLI-команды.

**Тестирование (`tests/test_gui.py`, 15 тестов).** Tkinter требует
собранного Tcl/Tk и (для реального создания окна) доступного дисплея —
в headless-окружениях без дисплея (например, в этой сессии разработки)
модуль `tkinter` может быть вовсе недоступен. Тесты явно рассчитаны на
такую ситуацию: `pytest.importorskip("tkinter")` и пробное создание
`tk.Tk()` — если дисплей недоступен, все тесты файла аккуратно
**пропускаются** (`SKIPPED`), а не падают и не блокируют остальные 68
тестов. На обычной машине разработчика с рабочим tkinter они выполняются
полностью. Как и в `tests/test_cli.py`, модальные диалоги
(`simpledialog.askstring`, `messagebox.askyesno`/`showerror`) подменяются
через `monkeypatch` — так же, как там подменяются `getpass.getpass()` и
`input()`. Сама крипто- и бизнес-логика повторно не тестируется (она уже
покрыта в `test_crypto.py`/`test_storage.py`/`test_advisor.py`/
`test_generator.py`) — здесь проверяется именно связка "GUI вызывает то
же самое ядро корректно": создание/разблокировка хранилища, добавление,
поиск/фильтрация, выбор записи в дереве по индексу, смена пароля,
удаление (с подтверждением и без), блокировка, и что все диалоговые окна
вообще строятся без ошибок вёрстки/аргументов.

**Запуск:** `python -m gui.app`.

### 10.1. Визуальное оформление (`ttkbootstrap`)

По запросу пользователя внешний вид GUI улучшен подключением
**`ttkbootstrap`** — пакета, который переопределяет стандартные ttk-темы
в современном плоском стиле и добавляет параметр `bootstyle` для
семантической окраски виджетов (`"primary"`, `"success"`, `"danger"` и
т.п.), плюс готовые стили вроде `"round-toggle"` (чекбокс в виде
переключателя).

**Почему это НЕ противоречит принципу "минимум зависимостей" из
раздела 2.** Тот принцип — про код, который **обрабатывает секреты**
(крипто-цепочка: `cryptography`, `argon2-cffi` — незаменимы, всё
остальное вокруг них — стандартная библиотека, чтобы минимизировать
площадь доверия именно там, где цена ошибки — компрометация пароля).
`ttkbootstrap` — чисто визуальный слой поверх `ttk`: он не читает, не
хранит и не передаёт пароли иначе, чем обычный `ttk` — путь
`Entry(show="*")` → `.get()` → `encrypt_vault()` не меняется ни на
строчку. Supply-chain риск от него — того же порядка, что и у уже
принятых зависимостей (`cryptography`/`argon2-cffi` тоже ставятся с
PyPI); пакет популярный (миллионы загрузок) и чистый Python. Так что
это инженерный компромисс (чуть больше веса при сборке, ещё одна
зависимость в `requirements.txt`), а не брешь в модели угроз.

**Что изменилось:**
- `App` теперь наследуется от `ttkbootstrap.Window`, диалоги — от
  `ttkbootstrap.Toplevel`, вместо `tk.Tk`/`tk.Toplevel`. Тема —
  `THEME_NAME = "bootstrap-light"` (светлая, плоская, синий акцент;
  использовано современное "2.0" имя темы, а не легаси-имя `"flatly"`,
  которое даёт `DeprecationWarning` и будет убрано в ttkbootstrap 3.0).
- Кнопки получили семантический цвет через `bootstyle`: зелёный —
  добавление, красный — удаление, жёлтый — предупреждающие действия
  (смена пароля, советник), синий/голубой — нейтральные/информационные
  (просмотр, генератор, копирование).
- Чекбоксы наборов символов в `GeneratorDialog` — `bootstyle=
  "round-toggle"` (переключатель вместо квадратного чекбокса).
- Список записей (`ttk.Treeview`) — чередующийся фон строк через
  `tag_configure`/`tags=` (нужно считать чётность по позиции СРЕДИ
  ВИДИМЫХ после фильтра строк, а не по индексу в полном списке — иначе
  полоски выглядели бы вразнобой после поиска).
- Диалоговые окна центрируются через `place_window_center()` — без
  этого при отсутствии оконного менеджера (как в headless-тестовом
  окружении) новые окна прижимались к углу экрана; на реальном рабочем
  столе это тоже просто аккуратнее, чем позиция по умолчанию.
- Кнопки первоначально дополнялись emoji-иконками (➕ 🗑 🛡 🎲 и т.п.) для
  быстрого визуального различения. **Позже заменены на собственный
  схематичный набор** (`gui/icons/`) — см. раздел 10.3: у emoji
  оставалась зависимость от наличия цветного emoji-шрифта в системе, а
  само по себе разноцветное изображение внутри кнопки (со своей
  палитрой, не связанной с `bootstyle` кнопки) визуально не так
  аккуратно вписывалось в плоский монохромный стиль `ttkbootstrap`, как
  собственная схематичная (line-art) иконка в цвет текста кнопки.
- Диалоги подтверждения/ввода (`tkinter.messagebox`/
  `tkinter.simpledialog`) намеренно НЕ переведены на `ttkbootstrap`
  (у него есть свои аналоги в `ttkbootstrap.dialogs`) — это ограничило
  бы объём изменений, сохранило совместимость с уже написанными тестами
  (`monkeypatch.setattr(guiapp.messagebox, ...)`) и не даёт заметного
  визуального выигрыша по сравнению с риском регрессий.

**Найденный и исправленный баг вёрстки.** При визуальной проверке (см.
ниже) обнаружилось, что кнопка "Закрыть" в `AuditDialog` пропадала:
`ScrolledText` без явного `width`/`height` наследует размер по умолчанию
от `tk.Text` — 80×24 символа, что заметно больше фиксированного окна
480×360. Когда виджет с `expand=True` запрашивает больше места, чем
целиком есть в контейнере, `pack` не ужимает его ради соседних
виджетов — в результате кнопка получала фактический размер 1×1 пиксель
(технически присутствовала, визуально невидима). Это не ловилось
исходным тестом `test_dialog_construction_does_not_raise` — он проверял
только отсутствие исключений при построении диалога, а не реальные
размеры виджетов после раскладки. Исправление — явные `width=56,
height=14` у `ScrolledText`; добавлен отдельный регрессионный тест
`test_audit_dialog_close_button_is_not_squeezed_to_zero`, который через
`winfo_reqwidth()/winfo_reqheight()` после `update_idletasks()`
проверяет, что кнопка не сжата до нуля.

**Проверено визуально**, а не только тестами: в среде разработки (через
Python 3.12 + Xvfb, см. раздел 10) сделаны и просмотрены реальные
скриншоты каждого экрана — разблокировка, список с записями и поиском,
просмотр записи, генератор с переключателями, отчёт советника — именно
так и была найдена ошибка с кнопкой "Закрыть" выше: тест на отсутствие
исключений её не поймал, а взгляд на реальный рендер — поймал сразу.

### 10.2. Иконка приложения (`gui/icon.png` / `gui/icon.ico`)

По макету, утверждённому пользователем (тёмно-синий скруглённый
квадрат, белая гора с вырезом-замочной скважиной в вершине — та же
метафора "секрет под замком", что и в названии "Хранилище тайн"),
сделана настоящая иконка приложения, а не только референс для мокапов
экранов (раздел 10.1 был про сами экраны).

**Откуда взят файл.** Пользователь прислал готовое изображение значка.
Само изображение пришло в виде JPEG-скриншота предпросмотра с "прозрачным"
клетчатым фоном (артефакт инструмента предпросмотра, а не часть
дизайна) и с лёгкими артефактами JPEG-сжатия за пределами самого значка.
Рисунок квадрата с горой и скважиной — **ровно тот же, без единого
изменения пикселей** внутри него: обрезка по границе непрозрачного
квадрата и добавление настоящего альфа-канала за пределами скруглённых
углов (вместо клетчатого фона предпросмотра) — это не редактирование
дизайна, а перевод из "картинки-превью" в пригодный для использования
файл значка. Радиус скругления углов маски подобран по границе самого
рисунка (~22.5% от стороны) — то есть маска повторяет уже
нарисованную форму, а не добавляет свою.

**Два файла, две разные цели:**
- `gui/icon.png` (256×256, RGBA) — иконка ОКНА в рантайме. Загружается
  в `gui/app.py` через `tk.PhotoImage(file=...)` и `self.iconphoto(True,
  ...)` в `App.__init__`. PNG выбран потому, что Tcl/Tk 8.6+ понимает
  этот формат нативно, без Pillow — не нужна ни одна дополнительная
  зависимость ради одной картинки. Ссылка на `PhotoImage` обязательно
  сохраняется в `self._icon_image` — иначе сборщик мусора Python
  освободил бы объект сразу после `__init__`, и иконка окна пропала бы
  (сам Tk не держит на неё отдельной ссылки).
- `gui/icon.ico` (multi-size: 16/24/32/48/64/128/256 px) — значок самого
  `.exe`-файла на Windows (Проводник, панель задач, ярлык). Подключается
  ОТДЕЛЬНО, параметром `icon=` в `EXE(...)` в `packaging/menedger.spec`
  — Windows берёт значок исполняемого файла из его ресурсов, а не из
  PNG, который приложение грузит уже во время работы, поэтому нужен
  именно `.ico` и именно multi-size (иначе Explorer в разных местах —
  ярлык, список файлов, диспетчер задач — использовал бы один и тот же
  размер, растянутый или обрезанный). На Linux/macOS PyInstaller этот
  параметр допустим, но на Linux не имеет эффекта (ELF не хранит
  ресурсов такого рода) — при сборке печатает безобидное `WARNING:
  Ignoring icon; supported only on Windows and macOS!`, что и
  подтверждено реальной сборкой в этой сессии.

**Почему `gui/icon.png` пришлось отдельно прописать в
`packaging/menedger.spec`.** `ICON_PATH` в `gui/app.py` вычисляется как
`Path(__file__).resolve().parent / "icon.png"` — то есть обычным чтением
файла, а не через `import`. Статический анализ импортов, которым
PyInstaller определяет, что упаковывать (см. раздел 11 про `collect_all`
и `hiddenimports`), в принципе не видит файлов, к которым код обращается
как к данным на диске — то есть без явной записи в `datas` PNG просто
не попал бы в собранный `.exe`, и `ICON_PATH.exists()` в рантейме
возвращала бы `False` (окно осталось бы без иконки, без ошибки — на
такой отказ код рассчитан намеренно, чтобы отсутствие картинки не
роняло всё приложение). Добавлена строка `datas.append((str(project_root
/ "gui" / "icon.png"), "gui"))` — проверено пересборкой: собранный файл
запускается и грузит иконку без исключений.

### 10.3. Схематичные иконки кнопок (`gui/icons/`) вместо emoji

По запросу пользователя цветные emoji на кнопках (➕ 🗑 🛡 🎲 🔒 🔓 ✏️ 📋
💾 👁) заменены на собственный набор монохромных схематичных
(line-art) иконок — 10 штук: плюс, глаз, корзина, щит, кубик, закрытый
и открытый замок, карандаш, копирование, дискета.

**Почему не просто взять готовый набор иконок (например, из
`ttkbootstrap` или сторонней иконочной библиотеки).** Раздел 2
формулирует принцип "не тянуть лишних зависимостей" — сторонний
иконочный пакет (Font Awesome/Feather/Bootstrap Icons и т.п.) добавил
бы ещё одну зависимость ради 10 картинок, которые несложно нарисовать
самим и которые тогда гарантированно совпадают по чистоте линий со
своим же приложением (тот же приём уже применён для `gui/icon.png` —
раздел 10.2: своя, полностью контролируемая графика вместо стороннего
ассета).

**Как нарисованы.** Каждая иконка нарисована программно через
`PIL.ImageDraw` на большом холсте (240×240), затем уменьшена до
итогового размера (22×22) фильтром `LANCZOS` — тот же приём
сглаживания, что и при подготовке `gui/icon.png`/`icon.ico` (раздел
10.2), нужен по той же причине: `ImageDraw` рисует без антиалиасинга,
а простое уменьшение с усреднением даёт гладкие края без пикселизации.
**Практический урок, полученный в процессе:** первая версия дайса
(шесть точек, как на грани кубика) и карандаша (тонкая диагональная
линия) на холсте 240×240 выглядела нормально, но после уменьшения до
22px мелкие детали сливались — шесть точек кубика превращались в
нечитаемое пятно, а карандаш — в невыразительную диагональную черту
без намёка на кончик. Пришлось перерисовать: кубик — с тремя крупными
точками вместо шести (грань "3", читается яснее при уменьшении), а
карандаш — цельным толстым телом с явным треугольным остриём. То же
самое коснулось открытого/закрытого замка: дужка, отличающаяся только
на несколько градусов дуги, на маленькой иконке визуально не
отличалась от закрытой — исправлено явным смещением открытой дужки в
сторону (держится на одном конце), а не просто "недорисованной" дугой.
**Вывод для защиты:** то, что нормально выглядит на большом холсте во
время рисования, нужно обязательно проверять уже в целевом маленьком
размере — ровно тот же принцип, что и с "собирается без ошибок" vs
"реально работает" для PyInstaller-сборки (раздел 11.1).

**Два цветовых варианта на каждую иконку — `_white.png` и `_dark.png`.**
У кнопок разных `bootstyle` в теме `bootstrap-light` разный цвет
текста — это не предположение, а прямой замер в разработческой сессии
через `ttk.Style().lookup(style, "foreground")`:

| bootstyle | цвет текста | вариант иконки |
|---|---|---|
| `primary`, `success`, `danger` | белый (`#ffffff`) | `_white` |
| `info`, `warning`, `secondary-outline` | тёмный (`#000000`/`#686d71`) | `_dark` |

Использование неверного варианта (например, тёмной иконки на тёмном
`primary`-фоне) сделало бы её невидимой — соответствие "bootstyle →
вариант иконки" явно перечислено в местах создания кнопок в
`gui/app.py`, а не выведено автоматически из `bootstyle` (десяток
кнопок — не тот масштаб, где стоит городить автоматизацию поверх явного
списка, см. раздел 7 о том, что не нужно усложнять код сверх задачи).

**Как подключено в `gui/app.py`.** Метод `App._button_icon(name,
variant)` читает `gui/icons/<name>_<variant>.png` через
`tk.PhotoImage` и кэширует результат в `self._icons` (словарь на
экземпляр окна); `App._icon_kwargs(name, variant)` оборачивает это в
`{"image": ..., "compound": "left"}` для прямой подстановки в
`ttk.Button(..., **parent._icon_kwargs("trash", "white"))`.
Модальные диалоги (`EntryDialog`, `ViewEntryDialog`, `GeneratorDialog`)
не наследуются от `App`, но получают ссылку на неё как `parent` —
вызывают `parent._icon_kwargs(...)` тем же способом, каким
`ViewEntryDialog` уже обращается к `parent._copy_to_clipboard(...)`
(один и тот же существующий в проекте паттерн, не новый).

**Найденный и исправленный баг: `TypeError: 'PhotoImage' object is not
callable`.** Метод был изначально назван `_icon` (короче и симметричнее
`_icon_kwargs`) — и это ломало создание главного окна прямо в
`App.__init__`, при первом же обращении к иконке. Причина: у
`ttkbootstrap.Window` (родителя `App`) есть свой внутренний метод
`_setup_icon()`, который для НЕ-`.ico`-иконки сам присваивает
`self._icon = tkinter.PhotoImage(...)` (см. `ttkbootstrap/window.py`) —
ровно то же имя, которым уже пользуется наша иконка окна (раздел 10.2,
`ICON_PATH`/`self.iconphoto`). Присвоение атрибута экземпляру
(`self._icon = ...`) перекрывает одноимённый МЕТОД класса для этого
конкретного экземпляра — поэтому последующий вызов `self._icon(name,
variant)` пытался "вызвать" уже не метод, а объект `PhotoImage`,
получая `TypeError`. Исправление — переименование метода в
`_button_icon` (имя, которое ttkbootstrap не использует ни для чего
своего). **Урок для защиты:** переопределяя `App`, унаследованный от
стороннего класса (`ttkbootstrap.Window` → `tkinter.Tk`), нельзя
считать пространство имён атрибутов "своим" — конфликт с внутренним
атрибутом родителя ловится не на этапе написания кода (никакого
предупреждения от Python или линтера), а только при реальном вызове,
и именно поэтому важно реально запускать GUI (или хотя бы тесты,
которые создают `App()`), а не полагаться на то, что код "выглядит
правильно".

**Файлы:** `gui/icons/<name>_white.png` и `gui/icons/<name>_dark.png`,
10 иконок × 2 цвета = 20 файлов, каждый 22×22 PNG с альфа-каналом.
Как и `gui/icon.png` (раздел 10.2), не видны статическому анализу
PyInstaller (читаются по пути, не импортируются) — в
`packaging/menedger.spec` добавлен цикл по `gui/icons/*.png`,
добавляющий каждый файл в `datas`.

### 10.4. Раскладка окна "Разделённая панель" вместо плоского тулбара

До этого раздела GUI был устроен как один плоский экран: заголовок с
поиском и кнопкой "Заблокировать" сверху, список записей посередине,
ряд из 4-5 кнопок снизу. По решению пользователя (выбор из нескольких
визуальных референсов-мокапов, сделанных заранее как отдельные HTML/PNG
картинки, ещё не код) главный экран и экран разблокировки перестроены
под раскладку "Разделённая панель": тёмный сайдбар/фон (тот же цвет,
что и у самой иконки приложения, `#12233d` — раздел 10.2) + светлая
рабочая область.

**Главный экран (`_build_main_frame`).** Вместо одного `Frame` с
кнопками в один ряд — два дочерних `Frame` side-by-side:
- **Сайдбар** (`pack(side="left", fill="y")`) — бренд (иконка + название
  приложения) сверху, ниже — "Советник" и "Генератор", внизу (прижата
  `pack(side="bottom")`) — "Заблокировать".
- **Рабочая область** (`pack(side="left", fill="both", expand=True)`) —
  поиск, список записей, и ПОД списком — "Добавить"/"Удалить".

**Почему именно советник/генератор ушли в сайдбар, а добавить/удалить —
остались в рабочей области.** Это не случайное распределение "4 кнопки
сюда, 2 туда", а разделение по тому, к чему привязано действие:
советник анализирует ВСЁ хранилище целиком, а генератор вообще не
трогает хранилище (не требует ни выбранной записи, ни мастер-пароля,
см. раздел 9.3) — оба этичны как инструменты уровня приложения, что и
оправдывает сайдбар-навигацию, где обычно живут именно такие
глобальные разделы. "Добавить" и "Удалить", наоборот, работают с
конкретными записями списка ("Удалить" без выбранной строки вообще
ничего не делает, см. `_on_delete_selected`) — им логичнее оставаться
рядом с самим списком, а не быть оторванными в сайдбар.
"Заблокировать" — тоже действие уровня приложения (сбрасывает
состояние всей сессии, а не одной записи), поэтому ушло в сайдбар
вместе с советником/генератором.

**Как заведены цвета сайдбара — БЕЗ конфликта с `bootstyle`.** Первая
попытка была через `ttk.Style().colors.set("navy", "#12233d")` и затем
`bootstyle="navy"` на виджетах — не сработало: `bootstyle` в
ttkbootstrap понимает только фиксированный список токенов
(primary/secondary/success/danger/warning/info/light/dark и их
модификаторы `-outline`/`-link` и т.п.), а незнакомый токен тихо
игнорируется с предупреждением в консоль, и виджет откатывается к
цветам по умолчанию — проверено в разработческой сессии до того, как
это попало в код. Рабочее решение — метод `App._setup_custom_styles()`,
который заводит цвета НАПРЯМУЮ через `ttk.Style().configure("ИмяСтиля",
background=..., foreground=...)` под собственными именами стилей
(`Sidebar.TFrame`, `SidebarNav.TButton`, `SidebarLock.TButton`,
`UnlockBg.TFrame`), которые дальше передаются виджетам параметром
`style=`, а не `bootstyle=`. `ttk.Style().configure()` — более низкий
уровень API, чем `bootstyle`, ttkbootstrap его не перехватывает и не
сверяет по списку токенов, поэтому произвольный цвет заводится без
проблем.

**Экран разблокировки (`_build_unlock_frame`).** Тот же язык: тёмный
фон на всё окно (`UnlockBg.TFrame`) + белая "карточка" по центру
(иконка приложения, заголовок, поле выбора файла, поле мастер-пароля,
кнопки). **Приём центрирования карточки** — не абсолютное позиционирование
и не `grid` с весами, а особенность `pack()`: виджет, упакованный с
`expand=True` и БЕЗ `fill`, центрируется в родительском контейнере по
обеим осям одновременно. Карточка не имеет отдельного именованного
стиля — её белый фон получается "бесплатно", потому что фон
по умолчанию у `TFrame`/`TLabel`/`TEntry` в теме `bootstrap-light` и
так белый (`#ffffff`, тот же цвет, что и у остальной, не-сайдбарной
части приложения) — кастомный стиль понадобился только тёмному фону
вокруг карточки, который ИНАЧЕ выглядит, чем цвет темы по умолчанию.
Тонкая рамка карточки — не отдельный стиль, а параметры самого
`ttk.Frame(..., borderwidth=1, relief="solid")`, без обращения к
`ttk.Style()` вообще.

**Что не изменилось.** Сами диалоги (`EntryDialog`, `ViewEntryDialog`,
`AuditDialog`, `GeneratorDialog`) остались как были — простые модальные
окна со светлым фоном, без тёмной шапки, как в диалоге просмотра
записи на референсе-мокапе. Это сознательное ограничение объёма
изменения в эту сессию, а не забытая часть дизайна — при желании
дотянуть их до того же визуального языка можно позже отдельным шагом,
не трогая уже переделанные экраны.

**Проверено:** полный набор 83 тестов проходит без изменений (кнопки
переехали в сайдбар, но вызывают ровно те же методы — тесты дёргают
`app._on_audit()`/`app._on_generate_standalone()` напрямую, а не ищут
кнопку по тексту, поэтому переезд их не затронул); реальная пересборка
и запуск `.exe` через PyInstaller; визуально — через Xvfb-скриншоты
обоих экранов, сверено с референсом.

### 10.5. Скруглённые кнопки

По запросу пользователя у всех кнопок появились скруглённые углы — на
референсах-мокапах (раздел 10.4) они уже были нарисованы скруглёнными
(обычный `border-radius` в HTML/CSS), а в реальном GUI до этого раздела
оставались плоскими прямоугольными — ttk `TButton` в теме
`bootstrap-light` рисуется классическим `relief`/`bordercolor`
элементом, без единого пикселя скругления.

**Почему `bootstyle="... round"` не подходит.** Первая проверка — сам
`ttkbootstrap` заявляет модификатор `round` в списке допустимых токенов
(`ttkbootstrap.constants.BootStyle`). На практике он относится только к
чекбоксам/переключателям (`"primary round"`, `"primary round toggle"` —
то же семейство, что уже даёт `bootstyle="round-toggle"` в
`GeneratorDialog`), а не к обычной кнопке: `bootstyle="success round"`
на `ttk.Button` печатает `UserWarning: invalid bootstyle combination
'round-button'` и просто отбрасывает `round` — проверено прямым
запуском в разработческой сессии, а не по документации (в самом коде
`ttkbootstrap.style.builders.button` вообще нет обращения к скруглённым
фигурам, только плоский `style.configure(..., relief=RAISED,
borderwidth=1, ...)`).

**Как сделаны скруглённые кнопки — свой image-based стиль.** Тот же
9-patch приём, что используют сами темы `ttk` под капотом: изображение
скруглённого прямоугольника (рисуется `PIL.ImageDraw.rounded_rectangle`
на холсте с 4-кратным суперсэмплингом, уменьшается `LANCZOS` — тот же
метод, что и для `gui/icon.png`/`gui/icons/*.png`, разделы 10.2–10.3)
становится фоном кнопки через `ttk.Style().element_create(name,
"image", ..., border=радиус, sticky="nsew")` — угловые радиусы
(`border=`) остаются нетронутыми, остальная площадь растягивается под
любую ширину текста, поэтому одна маленькая (28×28) картинка обслуживает
кнопку любого размера. `App._rounded_button_style(...)` кэширует стиль
по имени (`self._rounded_style_names`) и собирает под каждый нужный
цвет свои hover/pressed-варианты (осветление/затемнение на 18% —
`_mix()`), чтобы кнопка не была совсем "мёртвой" без обратной связи на
клик, пусть и не пиксель-в-пиксель повторяя прежние переходы
`ttkbootstrap`. Первая версия этого раздела заводила цвета кнопок через
короткие обёртки над уже знакомыми смысловыми цветами `bootstyle`
(`primary`/`success`/`danger`/`info`/`warning`/`secondary`, каждый
своим оттенком) — эта схема заменена в разделе 10.6 на более простую,
взятую прямо из референса.

**Найденный и исправленный баг №1: кастомный `style=` в конструкторе
`ttk.Button(...)` тихо подменялся обратно.** Первая версия передавала
`style=self._flat_style("primary")` прямо в `ttk.Button(...)` — и
результат был на кнопках `Обзор...`/`Открыть`/`Создать новое...`
показывал СТАРЫЕ плоские стили (`primary.TButton`,
`secondary.Outline.TButton`), а у кнопок без цветового токена в имени
(`Rounded.SidebarNav`) — вообще голый `TButton` без единого своего
цвета. Причина — в `ttkbootstrap.Button.__init__` (проверено чтением
исходника в разработческой сессии): аргумент `style` там не передаётся
дальше как есть, а сверяется с `Style.style_exists_in_theme(style)`; не
найдя имя в СВОЁМ внутреннем реестре стилей (наши `Rounded.*` там,
конечно, не значатся — они заведены напрямую через
`ttk.Style().layout()`, а не через регистрационные функции
`ttkbootstrap`), он трактует переданную строку как строку `bootstyle` и
пересчитывает стиль заново через свой парсер токенов — отсюда и
"primary" из "Rounded.**primary**" неожиданно "нашёлся" как цветовой
токен, а "Rounded.SidebarNav" не нашёл никакого токена и откатился к
стилю по умолчанию. Исправление — `App._styled(widget, style_name)`:
применяет стиль ПОСЛЕ создания кнопки, через обычный
`widget.configure(style=...)`, а не через аргумент конструктора —
`ttkbootstrap.Button` не переопределяет `configure()` (только
`__init__`), так что этот путь не проходит через перехватчик токенов.
**Урок для защиты:** обёртка над сторонним виджетом может перехватывать
и переинтерпретировать даже "прозрачные" параметры вроде `style=`, и
единственный надёжный способ это обнаружить — реально запустить и
посмотреть, какой стиль в итоге РЕАЛЬНО применился
(`widget.cget("style")`), а не полагаться на то, что переданное значение
дошло как есть.

**Найденный и исправленный баг №2: белёсые "уголки" на кнопках
сайдбара.** После фикса бага №1 кнопки "Советник"/"Генератор" в тёмном
сайдбаре показывали едва заметные светлые угловые артефакты — фон
кнопки заливался цветом сайдбара (`_SIDEBAR_BG`), то есть должен был
визуально сливаться с сайдбаром без следа, но по контрастным углам
стало видно чужой (светлый) цвет. Первая гипотеза — "звон" (эффект
Гиббса) от `LANCZOS`-интерполяции на резкой границе прозрачности;
проверка отдельным сравнением `LANCZOS`/`BILINEAR`/`BICUBIC` на
изолированном тестовом изображении её не подтвердила — сама фигура на
прозрачном холсте уменьшалась чисто. Настоящая причина оказалась не в
PIL, а в самом Tk: изображение-элемент кнопки рисуется ПОВЕРХ
штатного (светлого) фона `Button`, который Tk всё равно готовит под
своим базовым элементом раньше, чем накладывается наш image-элемент —
на белом/светлом фоне (диалоги, карточка разблокировки) эта щель
незаметна (оба цвета светлые), а на тёмном сайдбаре бросается в глаза.
Исправление — никакой прозрачности вообще: `_rounded_image(...)`
получил параметр `surface` (реальный цвет ТОГО, на чём стоит кнопка —
белый по умолчанию, `_SIDEBAR_BG` для кнопок сайдбара) и теперь сразу
заливает им весь холст ДО того, как рисует сверху саму скруглённую
фигуру — картинка кнопки получается полностью непрозрачной, и вопрос
"что видно из-под угла" перестаёт существовать в принципе, независимо
от того, что там рисует Tk под капотом. **Урок для защиты:** когда
видимый артефакт совпадает по форме с "местом, где ожидается
прозрачность", это не обязательно повод чинить именно интерполяцию
(баг может быть похож на прошлые истории с антиалиасингом иконок —
разделы 10.2/10.3 — но не быть тем же самым багом) — стоит сначала
изолированно проверить сам шаг, который подозреваешь, прежде чем его
менять.

**Новая прямая зависимость: `Pillow`.** До этого раздела Pillow была
только ТРАНЗИТИВНОЙ зависимостью `ttkbootstrap` (раздел 11, про
`PIL._tkinter_finder`) — `gui/app.py` сам её не импортировал. Теперь
импортирует (`from PIL import Image, ImageDraw, ImageTk`) — значит, по
собственному же правилу проекта (раздел 11.1: точная версия, а не
диапазон, и явная запись в `requirements.txt`, а не расчёт на то, что
её кто-то другой подтянет транзитивно), она добавлена в
`requirements.txt` явной строкой `pillow==12.3.0` (версия — та, что уже
и так стояла транзитивно через `ttkbootstrap` в протестированном
окружении, так что для уже работающей установки ничего не меняется).

### 10.6. Цветовая схема кнопок — по образцу референса C, а не по
`bootstyle`-семантике

Раздел 10.5 дал кнопкам скруглённую ФОРМУ референса, но не цвет: до
этого раздела заливка каждой кнопки бралась из смысловых цветов
`bootstyle` (зелёный — добавление, красный — удаление, жёлтый — смена
пароля, голубой — просмотр/копирование, синий — основное действие) —
палитра, унаследованная от прежнего (плоского, до-скруглённого) GUI, а
не с самого референса-мокапа "Разделённая панель" (вариант C, раздел
10.4). По запросу пользователя цвета кнопок приведены к тому, что
реально нарисовано в HTML-референсах (`unlock_c.html`, `dialog_c.html`,
`variant_c_split.html`) — там своя, гораздо более скупая схема: почти
все кнопки — НЕЙТРАЛЬНЫЕ (светло-серая заливка `#eef1f8`, тонкая рамка
`#dfe4ee`, тёмный текст `#33415c`), и только ОДНА кнопка на экран/диалог
— синий акцент (`#2f6fed`, белый текст) для главного действия. Цвета
сняты прямым чтением CSS в мокапах, а не подобраны на глаз.

**Почему не оставить смысловые цвета (зелёный=добавить, красный=
удалить и т.п.).** Это была самостоятельная придумка поверх референса,
а не то, что реально нарисовано в утверждённом пользователем мокапе —
референс сознательно НЕ красит "Удалить" в красный и "Добавить" в
зелёный: различитель действия там — иконка (`gui/icons/`, раздел 10.3),
а не цвет кнопки, и это сделано в самом дизайне намеренно, чтобы не
пестрить одинаково яркими кнопками на одном экране, где ни одна из них
не главнее другой. Красный в референсе зарезервирован только за
"Заблокировать" в сайдбаре — единственное явно "опасное" по смыслу
действие уровня всего приложения, а не любое удаление записи.

**`App._neutral_style(self, **kwargs)` / `App._accent_style(self,
**kwargs)`** — теперь единственные два входа в `_rounded_button_style`
для обычных кнопок (кроме кнопок сайдбара, у которых свои уникальные
цвета — красный `_SIDEBAR_LOCK_BG`, тёмно-синий `_SIDEBAR_BG` — они
заведены отдельными прямыми вызовами `_rounded_button_style`, минуя
`_neutral_style`/`_accent_style`, раздел 10.4). Обе кнопки одного
диалога/экрана нейтральны, кроме ровно одной акцентной — главного
действия:

| Экран/диалог | Акцент (`_accent_style`) | Нейтральные (`_neutral_style`) |
|---|---|---|
| Разблокировка | Разблокировать | Выберите файл, Создать новое хранилище |
| Главный экран | — | Добавить, Удалить, Советник, Генератор (раздел 10.11) |
| Новая запись | Сохранить | Сгенерировать (быстрая), Отмена |
| Просмотр записи | Копировать пароль | Закрыть (раздел 10.9 — "Удалить"/"Сменить пароль" убраны из футера) |
| Советник | — | Закрыть |
| Генератор паролей | Сгенерировать | Закрыть, Копировать |

Из-за этого у части кнопок пришлось сменить вариант схематичной иконки
(`_icon_kwargs`, раздел 10.3) на противоположный — иконка должна
оставаться контрастной новому фону кнопки: "Добавить"/"Удалить"
(главный экран) и "Удалить" (просмотр записи) были на цветном
(`success`/`danger`) фоне с белой иконкой — на светлой нейтральной
заливке белая иконка стала бы невидимой, заменена на тёмный вариант;
"Копировать пароль" (просмотр записи), наоборот, была на голубом
(`info`) фоне с тёмной иконкой, а на синем акценте (`#2f6fed`, заметно
темнее прежнего голубого) тёмная иконка потерялась бы — заменена на
белый вариант.

**Направление hover-подсветки зависит от того, светлая кнопка или
тёмная.** `_rounded_button_style` раньше всегда сдвигал цвет наведения
к белому, если `fill != surface`, и к чёрному — только для кнопок
сайдбара (`fill == surface`, т.е. фон кнопки совпадает с фоном под ней
в состоянии покоя). Это верно для СТАРОЙ семантической палитры (все
цвета были достаточно тёмными, чтобы освещение при наведении читалось),
но перестало быть общим правилом с приходом светлого нейтрального фона
(`#eef1f8`) — светлую кнопку при наведении нужно НЕМНОГО ЗАТЕМНИТЬ, а не
осветлить ещё сильнее (иначе разница на глаз не видна, `#eef1f8` и так
почти белый). Условие переписано на прямую проверку яркости самой
заливки (`_hex_to_rgb(fill)[0] < 0x99` — грубая, но для двух десятков
кнопок проекта достаточная эвристика "тёмная/светлая" по каналу red):
тёмные кнопки (сайдбар, красный "Заблокировать") при наведении
светлеют, светлые (нейтральные, синий акцент) — темнеют. Это исправило
заодно и старую, ранее не до конца проверенную деталь: hover тёмных
кнопок сайдбара до этого замера яркости определялся условием `fill !=
surface`, которое для сайдбара технически совпадало (`fill ==
surface == _SIDEBAR_BG`), но было привязано к побочному признаку
("кнопка того же цвета, что фон под ней"), а не к самому факту "кнопка
тёмная" — новое условие проверяет ровно то, что нужно, и не зависит от
случайного совпадения fill/surface.

**Модуль-уровневые константы** — `_NEUTRAL_FILL = "#eef1f8"`,
`_NEUTRAL_BORDER = "#dfe4ee"`, `_NEUTRAL_TEXT = "#33415c"`, `_ACCENT =
"#2f6fed"` — заменили собой прежний словарь `_FLAT_COLORS`
(бывшую bootstyle-палитру primary/success/danger/info/warning/
secondary), который удалён как более не нужный.

### 10.7. Экран разблокировки переверстан один-в-один под референс C

По запросу пользователя (прислан итоговый скриншот-мокап) экран
разблокировки (`_build_unlock_frame`) переверстан вплотную к этому
референсу — раньше он был лишь приблизительно в том же визуальном языке
("Разделённая панель", раздел 10.4), но с другой структурой полей и
кнопок.

**Что изменилось:**
- Подписи полей переехали НАД поля ввода, заглавными буквами, мелким
  полужирным шрифтом (`"ФАЙЛ ХРАНИЛИЩА"`, `"МАСТЕР-ПАРОЛЬ"`) — вместо
  прежнего `"Файл хранилища:"` слева от поля на одной строке. Letter-
  spacing (видимый на референсе лёгкий разряд между буквами) в Tkinter
  нативно не поддерживается — сознательно не имитировался вставкой
  пробелов между буквами (это сломало бы выделение/копирование текста
  подписи и всё равно не дало бы точного визуального совпадения);
  расхождение с референсом здесь признанное и незначительное.
- Кнопка выбора файла переименована `"Обзор..."` → `"Выберите файл"`
  (текст с референса), логика (`_on_browse`) не изменилась.
- У поля мастер-пароля появилась кнопка-"глаз" (`_on_toggle_password_
  visibility`) — переключает `Entry(show=...)` между `"*"` и `""`.
  Использует ту же схематичную иконку `eye_dark`, что и до этого нигде
  не была задействована (раздел 10.3 рисовал её про запас вместе с
  остальными). Один и тот же значок для обоих состояний (показан/скрыт)
  — самостоятельная перерисовка перечёркнутого варианта ради одной
  кнопки была бы избыточна для учебного проекта (раздел 7: не усложнять
  сверх задачи); показ/скрытие заметно и так по самому содержимому поля.
- Кнопка-"глаз" — отдельный кастомный стиль `Rounded.IconToggle` (тот же
  нейтральный цвет, что `_neutral_style`, но с компактным `padding=(8,
  6)` под квадратную иконку-без-текста), а не сам `_neutral_style()` —
  `_rounded_button_style` кэширует стиль по имени и параметры (включая
  padding) учитывает только при ПЕРВОМ создании стиля с этим именем;
  переиспользовать `"Rounded.Neutral"` с другим padding для одной кнопки
  было бы невозможно, не сломав padding всех остальных нейтральных
  кнопок в приложении.
- Главная кнопка `"Открыть"` → `"Разблокировать"` (текст с референса), и
  теперь она — единственная в своём ряду, на всю ширину карточки
  (раньше делила строку 50/50 с кнопкой создания хранилища).
- Между `"Разблокировать"` и созданием нового хранилища — разделитель
  `ttk.Separator` с обеих сторон от заглавной подписи `"НЕТ
  ХРАНИЛИЩА?"` в один ряд (`pack(side="left", fill="x", expand=True)`
  у обоих `Separator`, подпись — между ними без `expand`) — тот же
  привычный паттерн "OR"-разделителя, что и на референсе.
- Кнопка `"Создать новое..."` → `"Создать новое хранилище"` (текст с
  референса), тоже теперь на всю ширину карточки, отдельным рядом под
  разделителем, а не делит строку с `"Разблокировать"`.
- Заголовок `APP_TITLE` лишился `bootstyle="primary"` (раньше — синий) —
  на референсе заголовок тёмный, обычного цвета текста темы; синий
  оставлен только за акцентной кнопкой `"Разблокировать"`, чтобы не
  спорить с ней за внимание на экране, где и так минимум цвета (раздел
  10.6).

**Из-за возросшей высоты карточки пришлось увеличить размер окна.**
Новые ряды (подписи над полями, разделитель, вторая полноширинная
кнопка) сделали карточку заметно выше прежней — при старом размере окна
(`size=(780, 480)`) нижняя часть карточки (разделитель и кнопка
"Создать новое хранилище") обрезалась рамкой окна ещё до его нижнего
края. Обнаружено визуально, реальным Xvfb-скриншотом, а не только
прогоном тестов (`test_gui.py` строит виджеты, но не проверяет, что все
они физически помещаются в окно) — тот же урок, что уже фиксировался в
разделах 10.1/11: отсутствие исключений при построении ≠ корректный
внешний вид. Исправление — `size=(780, 480)` → `(780, 620)`, `minsize=
(560, 340)` → `(560, 460)`. Главный экран (`_build_main_frame`) при этом
не пострадал — он просто получил немного больше свободного места под
списком записей, что не является проблемой (список и так заполняет
доступное пространство через `expand=True`).

**Проверено:** полный набор 83 тестов проходит без изменений (тесты
вызывают `_on_browse`/`_on_unlock`/`_on_create` напрямую, а не ищут
кнопки по прежнему тексту); реальный запуск под Xvfb и скриншоты обоих
состояний поля пароля (скрыт/показан) — сверено с присланным
референсом визуально, включая главный экран (не регрессировал от
увеличения окна).

### 10.8. Главный экран переверстан под референс C: карточка со
скруглёнными внешними углами, расширенная панель инструментов, третий
пункт навигации

Аналогично разделу 10.7 (экран разблокировки), пользователь прислал
итоговый скриншот-мокап главного экрана, и `_build_main_frame`
переверстан вплотную к нему — раньше сайдбар и рабочая область были
двумя прямоугольными `Frame` впритык к краям окна (раздел 10.4), без
общей внешней рамки и без светлого фона вокруг.

**Карточка со скруглёнными только ВНЕШНИМИ углами.** До этого раздела
скругление (раздел 10.5) применялось только к кнопкам — сам сайдбар и
рабочая область оставались обычными прямоугольниками. Референс
показывает сайдбар+рабочую область как ОДНУ карточку: у сайдбара
скруглены только левые два угла, у рабочей области — только правые, а
стык между ними посередине остаётся ровным, что вместе читается как
единая панель с скруглённой рамкой, лежащая с отступом на светло-серой
"странице" (`_PAGE_BG = "#eef1f6"`), а не занимающая всё окно вплотную
к краям.

Изначально это был тот же 9-patch приём, что и у кнопок (раздел 10.5) —
`App._panel_style(style_name, fill, corners)`, — но применённый к
`TFrame`. **Важная оговорка задним числом (см. раздел 10.9 для полной
истории): этот приём НА САМОМ ДЕЛЕ не работал для `TFrame` под
`ttkbootstrap`** — угол ниже был визуально спутан со скруглённым, хотя
попиксельная проверка (сделанная позже, в разделе 10.9) показала, что
угол всё это время был острым. `_panel_style` был заменён на
`App._rounded_backdrop(...)`, описанный в разделе 10.9 — сама ИДЕЯ
асимметричного скругления через параметр `corners` у
`PIL.ImageDraw.rounded_rectangle()` (`(top_left, top_right,
bottom_right, bottom_left)`, начиная с Pillow 8.2 — в проекте и так
`pillow==12.3.0`) осталась той же, изменился только механизм наложения
картинки на виджет.

Вложенные виджеты сайдбара (бренд, кнопки навигации) остаются на своих
прежних плоских стилях (`Sidebar.TFrame`/`Sidebar.TLabel`,
`_SIDEBAR_BG`) без изменений — они просто лежат ПОВЕРХ уже скруглённой
по краям панели теми же цветами, что и её сплошная заливка, поэтому
визуально сшиваются бесшовно; переделывать пришлось только два САМЫХ
внешних `Frame` (сайдбара и рабочей области), не всё дерево виджетов
внутри них.

**Третий пункт навигации сайдбара — "Все записи".** Раньше в сайдбаре
были только "Советник"/"Генератор" (раздел 10.4) — список записей был
единственным, что вообще показывалось в рабочей области, без
отдельного переключателя. Референс явно рисует его как пункт навигации
с иконкой глаза, ПОДСВЕЧЕННЫЙ как активный (более светлый оттенок
навy — `_SIDEBAR_HOVER_BG = "#1e3a63"`, до этого раздела заведённый в
коде, но нигде не использовавшийся как самостоятельный фон, только как
цель для подмешивания hover-оттенка других кнопок). Поскольку в
приложении сейчас физически только ОДИН экран внутри главного окна
(список записей), кнопка "Все записи" всегда отображается как активная
(`Rounded.SidebarActive`, фон `_SIDEBAR_HOVER_BG`, текст
`_SIDEBAR_TEXT_ACTIVE`) — честное отражение реального состояния
приложения, а не притворство, будто есть переключение между экранами,
которого пока нет. Клик (`_on_show_all_entries`) сбрасывает фильтр
поиска обратно к плейсхолдеру — единственное осмысленное действие
"показать вообще все записи" при одном экране; когда/если у приложения
появится второй полноценный экран (см. открытые пункты раздела 9),
этот же пункт станет настоящим переключателем состояния, а не
"вечно активным" — данный раздел явно фиксирует, что сейчас это
осознанное временное упрощение, а не законченная архитектура вкладок.

**Панель инструментов расширена с 2 до 6 кнопок.** Раньше в рабочей
области были только "Добавить"/"Удалить" (раздел 10.6) — просмотр
записи был доступен только двойным кликом по строке, смена пароля —
только через кнопку внутри уже открытого `ViewEntryDialog`. Референс
выносит оба действия прямо на панель инструментов:
- **"Просмотр"** — то же самое, что и двойной клик (`_on_view_selected`,
  без изменений); двойной клик по строке остаётся рабочим наравне с
  кнопкой, а не заменяется ею.
- **"Сменить пароль"** — новый метод `_on_change_password_selected()`:
  проверяет, что запись выбрана (иначе — то же сообщение "Нет выбора",
  что и у "Удалить"), и сразу вызывает уже существующий
  `_on_update_entry(entry)` — тот же код, что и одноимённая кнопка
  внутри `ViewEntryDialog`, только без промежуточного открытия диалога
  просмотра целиком ради одного действия.
- **"Советник"/"Генератор"** — референс дублирует их и в сайдбаре
  (глобальная навигация), и на панели инструментов (быстрый доступ) —
  оставлены доступны в обоих местах, а не убраны из сайдбара: это не
  противоречит рассуждению раздела 10.4 о том, ГДЕ им место
  (глобальный уровень приложения, не привязаны к записи) — дублирование
  на панели инструментов просто даёт более короткий путь к ним, не
  переопределяя их природу.

Шесть кнопок не помещаются в один ряд при разумной ширине окна — вместо
попытки написать настоящий flow-layout с пересчётом переноса по ширине
(overkill сложности для десятка кнопок школьного проекта, раздел 7)
кнопки статично разбиты на два `Frame`-ряда (4 + 2: Добавить/Просмотр/
Сменить пароль/Удалить, затем Советник/Генератор) — подобранная под
размер окна по умолчанию группировка, а не автоматическая, что и
проще, и предсказуемее в верстке.

**Строка поиска — плейсхолдер вместо отдельной подписи.** Referencing:
вместо `"Поиск:"` слева от поля — сам текст `"Поиск по сайту или
логину..."` серым цветом ПРЯМО в поле, пропадающий по фокусу. Реализовано
без отдельного булева флага "плейсхолдер активен/нет" — вместо этого
`_refresh_tree()` просто сравнивает сырое значение `_search_var.get()`
с константой `_SEARCH_PLACEHOLDER` напрямую: если равно, считать фильтр
пустым, иначе — использовать как обычно. Это осознанный выбор ради
устойчивости к тестам: `tests/test_gui.py` (`test_search_filters_tree`)
устанавливает `_search_var.set("example")` напрямую, в обход событий
`<FocusIn>`/`<FocusOut>`, где обычно вставляется/убирается текст
плейсхолдера — булев флаг, обновляемый только в обработчиках фокуса, в
этом сценарии остался бы в неверном состоянии и сломал бы фильтрацию;
прямое сравнение текста работает одинаково правильно что через реальный
UI (фокус мышью/Tab), что через прямую установку переменной в тесте.

**Увеличена ширина окна по умолчанию.** Шесть кнопок панели инструментов
(даже разбитые на два ряда по 4+2) физически не помещались в прежнее
окно 780px шириной — избыточные кнопки не оборачивались на новую
строку и не обрезались с явной ошибкой, а просто отрисовывались ЗА
пределами видимой области окна (тихая, незаметная потеря, обнаруженная
только реальным Xvfb-скриншотом, а не прогоном тестов — тот же урок,
что и в разделах 10.1/10.7/11: отсутствие исключений при построении ≠
корректный видимый результат). Исправление — `size=(780, 620)` → `(980,
640)`, `minsize=(560, 460)` → `(760, 460)`. Экран разблокировки
(раздел 10.7) не пострадал — его карточка центрируется независимо от
ширины окна.

**Что сознательно НЕ повторяет референс:** список записей (`Treeview`)
остался обычным прямоугольным блоком без собственного скругления углов
— применение того же 9-patch-приёма к `Treeview` рискованно
переопределять внутренние элементы виджета, отвечающие за скроллинг и
выделение строк, ради чисто декоративного эффекта на второстепенном
элементе; строка поиска — обычный `ttk.Entry` с увеличенным `ipady`, а
не отдельная "таблетка"-панель с собственной рамкой (как обводка вокруг
поля мастер-пароля на экране разблокировки, раздел 10.7) — оба
упрощения того же рода, что и отказ от имитации letter-spacing в
подписях полей (раздел 10.7): видимое, но незначительное расхождение с
референсом, принятое ради того, чтобы не городить хрупкий кастомный
рендеринг поверх стандартных виджетов ttk ради долей пикселя.

**Проверено:** полный набор 83 тестов проходит без изменений в самих
тестах (переезд кнопок в другие контейнеры не ломает вызовы `_on_add`/
`_on_view_selected`/`_on_delete_selected`/`_selected_entry`/
`_refresh_tree` напрямую, `_on_change_password_selected` — новый метод,
не заменяющий ничего, что тестировалось раньше); реальный запуск под
Xvfb и скриншоты — активный пункт "Все записи", панель инструментов из
6 кнопок в два ряда, живой плейсхолдер (пропадает по фокусу, фильтрация
работает и при прямом наборе текста) — сверено с присланным референсом
визуально. **Само скругление углов карточки на момент написания этого
раздела визуально КАЗАЛОСЬ верным, но не было проверено попиксельно —
на самом деле не работало; см. раздел 10.9, где это обнаружено и
исправлено.**

### 10.9. Диалог просмотра записи переверстан под референс C; найден и
исправлен баг ttkbootstrap со скруглёнными фонами `TFrame`

Пользователь прислал референс-мокап диалога просмотра записи и попросил
сделать его точно таким же, а заодно перенести кнопку "Сменить пароль"
из футера в саму строку поля пароля. В процессе верстки обнаружился
серьёзный баг в приёме, которым были нарисованы скруглённые панели
главного экрана (раздел 10.8) — он не показывал себя там, но стал
сразу заметен здесь.

**Новый вид `ViewEntryDialog`.** Тёмная "шапка" (иконка + `"Запись —
<сайт>"`, белый текст на `_SIDEBAR_BG`, скруглены только верхние два
угла) над белым "телом" (скруглены только нижние два угла) — тот же
язык карточки, что и на главном экране (раздел 10.8), только в
масштабе одного диалога. Поля показаны как read-only "плитки"
(`_NEUTRAL_FILL` заливка, `_NEUTRAL_BORDER` рамка, свои скруглённые
углы со всех четырёх сторон) с заглавной подписью НАД полем — тот же
приём, что уже был у полей экрана разблокировки (раздел 10.7).
`"Логин"` получил кнопку-копирование сбоку от поля; `"Пароль"` — сразу
три: "глаз" (показать/скрыть, маскируется точками `•` по умолчанию —
тот же смысл, что и `show="*"` у мастер-пароля, раздел 10.7),
"карандаш" (`_on_update` — смена пароля) и копирование. `"Создан /
изменён"` форматируется как `дд.мм.гггг` (`datetime.strptime(...,
CREATED_AT_FORMAT).strftime("%d.%m.%Y")`) вместо сырой ISO-строки —
для человека, а не только для машины. Футер сведён к двум кнопкам
референса — "Копировать пароль" (акцент) и "Закрыть" (нейтральная);
"Удалить" из диалога убрана вовсе (она и так уже есть на панели
инструментов главного экрана, раздел 10.8 — дублировать её здесь
референс не просит).

**"Сменить пароль" перенесена из широкой кнопки в футере в маленькую
иконку-карандаш рядом с самим полем пароля.** Раньше это была
полноширинная кнопка среди `Закрыть`/`Удалить`/`Копировать пароль`
(раздел 10.6) — референс не рисует отдельную широкую кнопку для этого
вообще, а к полю пароля добавляет свою иконку. По буквальной просьбе
пользователя ("перенеси туда кнопку сменить пароль") — реализовано
именно так: `add_icon_button(password_row, "pencil", self._on_update)`,
`_on_update` не изменилась (по-прежнему закрывает диалог, потом зовёт
`App._on_update_entry`).

**Найденный и исправленный баг: скруглённые фоны `TFrame` под
ttkbootstrap не растягиваются и не перерисовываются вообще.** При
первой попытке переиспользовать `_panel_style` (раздел 10.8) для шапки
диалога результат совсем не совпал с ожиданием: за текстом заголовка
был виден не navy-фон, а обычный белый фон диалога, то есть заливка не
дотягивалась даже до края текста, не то что до края окна. Расследование
заняло несколько шагов:

1. **Прямой замер пикселей.** `PIL.Image.open(screenshot).getpixel(...)`
   в стороне от текста заголовка показал БЕЛЫЙ (255,255,255), а не
   navy — заливка `_panel_style` не рисовалась вообще за пределами
   области, занятой дочерними виджетами (иконкой/текстом).
2. **Проверка на главном экране (раздел 10.8) — та же попиксельная
   проверка угла сайдбара показала РОВНЫЙ (острый) угол**, а не
   скруглённый, каким он казался на глаз при обычном просмотре
   скриншота. Оказалось, что то, что выглядело как "скруглённый
   сайдбар", было заливкой обычного плоского `Sidebar.TFrame` —
   вложенного дочернего фрейма, который целиком (включая точные
   угловые пиксели) занимал ту же площадь тем же цветом, что и внешняя
   (якобы скруглённая) панель — визуальное совпадение цветов маскировало
   то, что сама форма скругления никогда не применялась.
3. **Минимальная изолированная репродукция** (отдельный скрипт вне
   всего проекта): тот же самый код — `ttk.Style().element_create(...,
   "image", ..., border=radius, sticky="nsew")` + `style.layout(...)` —
   применённый к `ttk.Frame` под ЧИСТЫМ `tkinter.ttk` (без
   `ttkbootstrap`), растягивается и скругляется КОРРЕКТНО, даже когда
   финальный размер фрейма определяется соседним виджетом уже ПОСЛЕ
   создания стиля. Тот же код под `ttkbootstrap.Window` — НЕТ: фон не
   растягивается вообще, виден только в границах первого добавленного
   ребёнка. Кнопки (`ttk.Button`) с абсолютно ТЕМ ЖЕ приёмом при этом
   растягиваются прекрасно и под `ttkbootstrap` (подтверждено —
   полноширинная кнопка "Разблокировать" красится в синий цвет
   от края до края, раздел 10.5/10.7) — то есть баг специфичен именно
   для `TFrame`, а не для механизма "image"-элемента ttk в целом.
   Вывод: `ttkbootstrap.Button` — полностью переписанный Python-класс с
   собственной, проверенной логикой применения кастомных стилей (см.
   баг №1 раздела 10.5), а `ttkbootstrap.Frame`, судя по всему, ничего
   подобного не получил и для кастомных image-based стилей просто не
   работает надёжно.

**Исправление — обычный `tk.Label` с картинкой вместо ttk-стиля.**
`App._rounded_backdrop(frame, fill, corners, ...)` заменил
`_panel_style`: кладёт `tk.Label` с готовой PNG-картинкой скруглённого
прямоугольника НУЖНОГО (не абстрактного 9-patch) размера поверх
`frame` через `.place(x=0, y=0, relwidth=1, relheight=1,
bordermode="outside")`, затем `.lower()` — опускает эту подложку на
задний план, чтобы обычные `pack()`/`grid()`-виджеты `frame` рисовались
поверх неё как ни в чём не бывало. Это уже не зависит от того, как
`ttkbootstrap` обрабатывает кастомные ttk-стили для `TFrame` вообще —
`tk.Label`/`.place()` — база Tk без какой-либо ttk-стилизации картинки.

**Зачем `bordermode="outside"`.** Без него `.place(x=0, y=0,
relwidth=1, relheight=1)` отсчитывает (0,0) и relwidth/relheight от
ВНУТРЕННЕЙ, уже отступленной на величину `padding=` области `frame`
(если она задана — а она задана у ВСЕХ вызовов в этом диалоге:
`header`/`body`/каждая "плитка" поля) — обнаружено отдельно, попиксельно
(`winfo_children()`/`winfo_x/y/width/height()` каждого виджета
показали подложку, вписанную ровно в отступ `padding`, а не в полный
размер фрейма). `bordermode="outside"` заставляет `.place()` считать от
НАСТОЯЩЕГО внешнего края фрейма, как и было нужно.

**Найденный и исправленный баг №2: перерисовка через `after_idle`
срабатывала СЛИШКОМ РАНО, до того как `pack` посчитал реальную
геометрию.** Первая версия `_rounded_backdrop` планировала перерисовку
через `frame.after_idle(redraw)` сразу в момент создания каждого
фрейма — картинка получалась размером `1×1` (проверено напрямую:
`image cget -width -height` в Tcl буквально возвращали `1 1`).
Причина: пересчёт геометрии `pack`/`grid` в Tk САМ выполняется через
очередь idle-задач, и наша собственная `after_idle`-задача, поставленная
в очередь РАНЬШЕ (в момент создания фрейма, когда у него ещё нет
дочерних виджетов и/или соседи ещё не добавлены), срабатывала раньше,
чем Tk успевал пересчитать реальный размер — `frame.winfo_width()`
внутри `redraw()` в этот момент ещё возвращал плейсхолдер `1`
("виджет создан, но ещё не размещён"), а не итоговое число.
Исправление — `_rounded_backdrop` для `dynamic=False` теперь НЕ
планирует перерисовку сама, а ВОЗВРАЩАЕТ саму функцию `redraw`
вызывающему коду; `ViewEntryDialog.__init__` собирает все такие функции
в список `pending_backdrops` по ходу построения диалога и в самом конце
(когда всё уже построено) сперва зовёт `self.update_idletasks()`
(синхронно досчитывает геометрию до конца), а только потом вызывает
каждую отложенную перерисовку напрямую — к этому моменту `winfo_width()/
height()` у всех фреймов уже гарантированно правильные. Для главного
экрана (`dynamic=True`, раздел 10.8) этот баг не проявлялся — там
перерисовка привязана к реальному Tk-событию `<Configure>`, которое
Tk генерирует уже ПОСЛЕ того, как размер фактически пересчитан, а не
к вручную поставленной в очередь задаче.

**Урок для защиты:** то, что код "визуально работает" на скриншоте
беглым взглядом, не означает, что он работает ПО ПРИЧИНЕ, которую
описывает комментарий рядом с ним — раздел 10.8 несколько дней
описывал скруглённые углы карточки, которых на самом деле никогда не
было, потому что случайное цветовое совпадение с плоским вложенным
фреймом визуально маскировало то, что 9-patch-приём для `TFrame` под
`ttkbootstrap` был сломан с самого начала. Обнаружилось это только
благодаря НОВОМУ диалогу, где такой маскировки не было (текст заголовка
не закрывает собой всю площадь). Тот же принцип, что уже фиксировался
в разделах 10.1/10.5/10.7/11 ("собирается без ошибок" ≠ "работает
правильно"), но на новом уровне: даже РЕАЛЬНЫЙ скриншот можно
неправильно интерпретировать на глаз — попиксельная проверка
(`PIL.Image.getpixel`) там, где есть малейшее сомнение, надёжнее.

**Проверено:** полный набор 83 тестов проходит без изменений; реальный
запуск под Xvfb с попиксельной проверкой (`getpixel` в характерных
точках — за текстом заголовка, внутри полей, на угловых пикселях
сайдбара главного экрана) подтверждает, что заливка теперь
действительно растягивается на весь фрейм и угол действительно
скруглён (плавная диагональная граница по пикселям, а не резкий
излом) — и на диалоге, и на главном экране; отдельный функциональный
тест переключения видимости пароля (`_toggle_password` меняет текст
лейбла между `•••` и настоящим паролем и обратно).

### 10.10. Скругление строки поиска и панели списка записей

По запросу пользователя ("сделай также нормальное скругление на окне
поиска и панели с логинами") тот же приём `App._rounded_backdrop`
(раздел 10.9) применён ещё к двум местам главного экрана, которые до
этого оставались обычными прямоугольниками: строка поиска и список
записей (`Treeview`).

- **Строка поиска** — обёрнута в `search_row = ttk.Frame(content,
  padding=(6, 4))` со скруглённой по всем четырём углам белой подложкой
  (`_ROUNDED_RADIUS`, рамка `_NEUTRAL_BORDER`); сам `ttk.Entry` внутри
  получил новый стиль `Flat.TEntry` — без него у поля осталась бы СВОЯ
  прямоугольная рамка ВНУТРИ уже скруглённой подложки, видимая как
  тонкая прямая линия поверх плавной кривой скругления. Стиль применён
  через `.configure(style=...)` ПОСЛЕ создания `Entry`, а не аргументом
  конструктора — та же предосторожность, что и у кнопок (`App._styled`,
  раздел 10.5).
- **Список записей** — сам `Treeview` НЕ трогаем изнутри в смысле
  скроллинга/выделения (раздел 10.8: переопределять эти внутренние
  механизмы ради декоративного скругления рискованно), а оборачиваем
  его в `table_wrap = ttk.Frame(content, padding=6)` с такой же
  скруглённой белой подложкой снаружи — небольшой отступ (`padding=6`)
  не даёт прямым углам самого `Treeview` вылезать за скруглённые углы
  подложки. Собственную рамку `Treeview` — трогаем, см. ниже.

Обе подложки — `dynamic=True` (как и у сайдбара/рабочей области,
раздел 10.8), поскольку главное окно пользователь может менять в
размере, и подложки должны перерисовываться заново при каждом
`<Configure>`, а не единожды как у диалогов.

**Найденный и исправленный баг: `borderwidth=0`/`relief="flat"` через
`style.configure()` не убирали собственную рамку `Entry`/`Treeview`.**
По итоговому запросу пользователя убрать "внутреннюю линию" оказалось,
что первая версия `Flat.TEntry` (`style.configure("Flat.TEntry",
borderwidth=0, relief="flat", fieldbackground="#ffffff")`) не решила
проблему — тонкая прямая линия внутри скруглённой подложки осталась на
месте, просто была не так заметна на скриншоте, пока не присмотрелись
специально. Причина: `style.configure()` лишь МЕНЯЕТ ПАРАМЕТРЫ уже
существующего в раскладке элемента `Entry.field` (тот самый, что и
рисует рамку поля в теме `bootstrap-light`) — сам элемент, отвечающий
за рамку, никуда не девается, а рисует её не только через
`borderwidth`, но и через собственный цвет обводки
(`bordercolor`/`lightcolor`/`darkcolor`), не затронутый этими двумя
параметрами. Правильное исправление — `style.layout("Flat.TEntry",
[("Entry.padding", {"sticky": "nswe", "children": [("Entry.textarea",
{"sticky": "nswe"})]})])`: раскладка ПОЛНОСТЬЮ исключает элемент
`Entry.field` (рамку) из дерева отрисовки, оставляя только отступ и
сам текст — сквозь эту область виден фон родителя, то есть уже наша
скруглённая подложка, без какой-либо второй рамки поверх неё. Тот же
приём применён к `Treeview` — стиль `Flat.Treeview` убирает элемент
`Treeview.field`, оставляя `Treeview.padding`/`Treeview.treearea`
(сама область строк — не элемент скроллинга/выделения, так что раздел
10.8 не нарушается: убирается только внешняя рамка вокруг таблицы, а
не что-то из её интерактивного поведения).

**Проверено:** полный набор 83 тестов проходит без изменений;
попиксельная проверка обоих угловых скруглений подтверждает, что
внутри скруглённой границы больше нет второй прямой линии — тот же
метод контроля, что уже применялся при обнаружении и исправлении бага
в разделе 10.9, чтобы не повторить ту же ошибку "визуально выглядит
правильно, а на самом деле нет".

### 10.11. Цвет строки поиска приведён к референсу; убраны дублирующие
кнопки "Просмотр"/"Сменить пароль" с панели инструментов

По запросу пользователя внесены два независимых, но небольших изменения
главного экрана.

**Строка поиска — заливка `_NEUTRAL_FILL`, а не белая.** На референсе
поле поиска — того же светло-серого тона, что и нейтральные кнопки, а
не белое (белым оно случайно оказалось в разделе 10.10, где фон
скруглённой подложки строки поиска взяли равным `"#ffffff"` по аналогии
с диалогами, не сверяясь с референсом заново). Смена фона подложки
(`_NEUTRAL_FILL` вместо `"#ffffff"`) сама по себе результата не дала —
внутри поля всё равно оставался белый прямоугольник.

**Найденный и исправленный баг: `fieldbackground` через `style.
configure()`/`style.map()` не красит `Entry.textarea`.** После удаления
элемента `Entry.field` из раскладки `Flat.TEntry` (раздел 10.10, для
устранения второй рамки) красить заливку больше НЕЧЕМ через стиль:
`fieldbackground` — это цвет, которым закрашивает себя именно элемент
`Entry.field`, а не какая-то отдельная, не привязанная к элементу
характеристика виджета в целом. Раз элемента `Entry.field` в раскладке
больше нет, `fieldbackground` в любом виде (`configure`, `map`) просто
нечего красить — оставшийся `Entry.textarea` не читает эту опцию.
Проверено прямым замером (`ttk.Style().lookup("Flat.TEntry",
"fieldbackground")` возвращал правильное значение, а сам виджет
всё равно оставался белым — то есть опция СУЩЕСТВОВАЛА в стиле, но
физически некому было её применить). Исправление — `Entry.textarea`
оказался обёрткой над классическим Tk-виджетом ввода текста, у
которого есть своя обычная (не ttk-стилевая) Tk-опция `background`;
`search_entry.configure(background=_NEUTRAL_FILL)` — напрямую на самом
объекте `Entry`, а не через `style` — красит его корректно.

**Убраны "Просмотр" и "Сменить пароль" с панели инструментов.** Оба
дублировали уже существующие способы того же действия: "Просмотр" —
двойной клик по строке (`_on_view_selected`, который остаётся
привязанным к `<Double-1>` без изменений), "Сменить пароль" — иконку-
карандаш прямо в `ViewEntryDialog` (раздел 10.9). Метод
`_on_change_password_selected()`, обслуживавший кнопку на панели,
удалён целиком как код, которым больше некому пользоваться (раздел 7:
не оставлять мёртвый код) — если этот путь понадобится снова, его
несложно восстановить, скопировав тело из истории git. Панель
инструментов главного экрана теперь — 4 кнопки в один ряд (`Добавить`,
`Удалить`, `Советник`, `Генератор`), а не 6 в два ряда, как в разделе
10.8 — второй ряд стал не нужен.

**Проверено:** полный набор 83 тестов проходит без изменений (тесты не
ссылались ни на `_on_view_selected`-кнопку тулбара, ни на удалённый
`_on_change_password_selected` — `_on_view_selected` сам по себе
остался, просто без отдельной кнопки в тулбаре); попиксельная проверка
подтверждает, что заливка поля поиска теперь совпадает с нейтральными
кнопками, а не белая.

### 10.12. Список записей переработан в более современном виде:
цветные аватары, мягкое выделение, просторные строки

По запросу пользователя ("переделай панель с сайтами логинами на более
современный лад") список записей избавлен от вида "таблица-эксель" —
без замены самого `Treeview` на кастомный виджет (риск которого не
оправдан для школьного проекта, раздел 7), а перестройкой его
оформления в духе современных менеджеров паролей (Bitwarden, 1Password
и подобные): цветной кружок-аватар с первой буквой сайта перед каждой
записью, более просторные строки, мягкий акцентный цвет выделения
вместо системного серого/синего, приглушённые заголовки колонок вместо
чёрного текста на сером фоне.

**`App._site_avatar(site)` — цветной кружок с буквой.** Рисуется тем же
способом, что и остальная графика приложения (`PIL.ImageDraw` на
холсте с 4-кратным суперсэмплингом, уменьшение `LANCZOS` — разделы
10.2/10.3/10.5), но, в отличие от кнопок и панелей, БЕЗ проблем с
прозрачностью: аватар рисуется на `RGBA`-холсте с настоящим альфа-
каналом (прозрачный фон за пределами круга) и передаётся в `Treeview`
через штатный параметр `image=` при `tree.insert(...)` — `Treeview`
показывает такие картинки обычным Tk-блиттингом с честной альфа-
композицией поверх фона строки (чередующегося или подсвеченного), а не
через кастомный ttk-стиль, где с прозрачностью были найдены проблемы
(разделы 10.5/10.9). Кэшируется по паре (буква, цвет) в
`self._avatar_images` — на экземпляр окна, а не на модуль, по той же
причине, что и `self._icons` (раздел 10.3): `ImageTk.PhotoImage`
привязан к конкретному Tcl-интерпретатору.

**Цвет аватара — детерминированный, но НЕ через встроенный `hash()`.**
Идея — одна и та же запись должна выглядеть одинаково от показа к
показу и от перезапуска к перезапуску, чтобы пользователь мог со
временем научиться узнавать запись по цветовому пятну, не читая текст.
**Найденный и исправленный баг:** первая версия использовала `hash(site)
% len(_AVATAR_PALETTE)` — и цвет аватара оказался РАЗНЫМ при каждом
перезапуске процесса, хотя в пределах одного запуска был стабилен.
Причина — Python по умолчанию рандомизирует `hash()` для строк между
запусками интерпретатора (`PYTHONHASHSEED`, защита от алгоритмических
DoS-атак на хеш-таблицы через специально подобранные ключи) — это
поведение специально для СТРОК, а не общее свойство всех хешируемых
типов, и легко упустить из виду, ожидая от `hash()` детерминированности
"как обычно". Обнаружено скриншотами трёх ОТДЕЛЬНЫХ повторных запусков
приложения — тот же принцип, что уже не раз фиксировался в этом файле
(разделы 10.1/10.9 и другие): визуально код "работал" при однократном
взгляде, а расхождение проявлялось только при сравнении между запусками.
Исправление — `sum(map(ord, site)) % len(_AVATAR_PALETTE)`: не
криптографический хеш, а простая и НАМЕРЕННО детерминированная сумма
кодов символов — для равномерного разбрасывания 8-10 записей по 8
цветам палитры криптостойкость не нужна, а вот стабильность между
запусками — единственное реальное требование, и `sum()`/`ord()` его
гарантируют без каких-либо оговорок про рандомизацию.

**`show="tree headings"` вместо `show="headings"` — без изменения
`values`.** Аватар кладётся в служебную колонку `"#0"` (у `Treeview`
она обычно скрыта в режиме `show="headings"`) через `image=` при
`insert(...)` — а колонки `"site"`/`"username"` и их `values=(entry
["site"], entry["username"])` остались РОВНО такими же, как были.
Это осознанный выбор ради обратной совместимости с
`tests/test_gui.py`: `app._tree.item(children[0], "values") ==
("example.com", "alice")` — эта и другие проверки продолжают работать
без единой правки, потому что структура данных строки не поменялась,
поменялось только то, что перед ней теперь показывается иконка.

**Остальные штрихи:**
- `_TREE_ROW_COLORS["oddrow"]` — `#f2f3f5` → `#f7f8fa` (заметно светлее
  прежнего): современные списки помечают чередование едва заметной
  полоской, а не выраженной "зеброй" таблицы-эксельки.
- `_TREE_SELECTED_BG = "#dce8fd"` — мягкий осветлённый оттенок `_ACCENT`
  вместо стандартного цвета выделения темы `bootstrap-light`
  (`style.map("Flat.Treeview", background=[("selected", ...)])`) —
  выделение читается как часть той же акцентной цветовой истории, что
  и синие кнопки, а не как случайный несвязанный системный цвет.
- `rowheight=40` (раньше — стандартная для темы, заметно меньше) —
  аватар 28px с отступами физически не поместился бы в прежнюю
  компактную высоту строки, да и сам по себе более просторный список
  выглядит менее "табличным".
- Заголовки колонок (`Flat.Treeview.Heading`) — приглушённый серый
  текст (`_SEARCH_PLACEHOLDER_COLOR`, тот же тон, что уже используется
  для плейсхолдера строки поиска, раздел 10.8 — не придуман новый
  оттенок серого специально для этого) на белом фоне вместо чёрного
  текста на сером фоне темы по умолчанию.

**Что сознательно НЕ сделано:** имя сайта не выделено жирным
отдельно от логина внутри одной и той же строки — `Treeview` не
поддерживает разное форматирование текста для разных колонок ОДНОЙ
строки (теги `tag_configure` красят/форматируют строку целиком, а не
отдельную ячейку) без owner-drawn ячеек, которых у стандартного
`ttk.Treeview` попросту нет. Полная замена `Treeview` на кастомный
список из `Frame`-строк ради этой детали означала бы также переписать
`_selected_entry`/`_refresh_tree` и все связанные тесты
(`tests/test_gui.py` полагается на `app._tree.get_children()`/`.item()`/
`.selection()`/`.selection_set()` как на `Treeview`-специфичный API) —
несоразмерный риск и объём изменений ради одной типографской детали;
цветной аватар уже даёт основной современный эффект без этого.

**Проверено:** полный набор 83 тестов проходит без изменений (структура
`values` не поменялась, см. выше); реальный запуск под Xvfb —
скриншоты списка с аватарами, скриншот с выбранной строкой (мягкая
синяя подсветка), и трёх ОТДЕЛЬНЫХ повторных запусков процесса с
попиксельным сравнением цвета аватара одной и той же записи (`github.
com`) — до фикса цвет менялся между запусками, после — идентичен во
всех трёх.

### 10.13. Оценщик надёжности пароля перенесён из генератора в окно
добавления записи

По запросу пользователя текстовое объяснение силы пароля
(`assistant.generator.explain_password` — длина + оценка энтропии в
битах, см. раздел 9.3) убрано из `GeneratorDialog` и показано вместо
этого в `EntryDialog` — окне, где пользователь реально набирает или
вставляет пароль для СОХРАНЯЕМОЙ записи.

**Почему именно туда, а не оставить в генераторе.** `GeneratorDialog` —
самостоятельный инструмент: пароль оттуда копируется куда-то ещё (не
обязательно в хранилище этого приложения), поэтому оценка его силы
внутри диалога генератора отвязана от того места, куда пароль в итоге
попадёт. `EntryDialog`, наоборот, — то самое окно, где принимается
решение "сохранить именно этот пароль в записи" (`_on_save`), и кнопка
быстрой генерации (`_on_generate`, значения по умолчанию) уже была
внутри него и раньше (раздел 9.3: у `EntryDialog` — своя быстрая
генерация, у отдельного `GeneratorDialog` — тонкая настройка длины и
наборов символов). Показ оценки прямо там, где стоит поле "Пароль:",
даёт обратную связь ровно в момент принятия решения о сохранении, а не
в оторванном от записи вспомогательном диалоге.

**Как реализовано.** `EntryDialog._password_var.trace_add("write",
self._update_strength)` — оценка пересчитывается на КАЖДОЕ изменение
переменной поля пароля, то есть одинаково срабатывает и при ручном
наборе через `Entry`, и при программной подстановке через кнопку
"Сгенерировать" (`self._password_var.set(...)`), без дублирования кода
для этих двух путей. `_update_strength()` очищает подпись при пустом
пароле (`explain_password("")` дал бы формально корректное, но
бессмысленное "Длина: 0 символов... ~0 бит", раздел 9.3 —
`estimate_entropy_bits("")` определён как `0.0`, а не как ошибка) — до
первого ввода/генерации подписи под полем просто не видно.

**Что осталось без изменений.** Сама функция `explain_password` и вся
логика `assistant.generator`/`assistant.strength` не менялись — перенос
чисто на уровне GUI, какой диалог вызывает уже существующую функцию.
`GeneratorDialog` не потерял способность помочь пользователю оценить
сгенерированный пароль вручную: тот же алгоритм (`assistant.strength.
estimate_entropy_bits`) доступен через команду `vault audit`/`vault
generate` в CLI (раздел 9.3) и через советника (`AuditDialog`) для уже
сохранённых записей — просто в самом диалоге генератора текстовая
подпись больше не дублируется.

**Проверено:** полный набор 83 тестов проходит без изменений (ни один
тест не ссылался на удалённый `GeneratorDialog._explanation_var` —
`test_audit_dialog_close_button_is_not_squeezed_to_zero` использует
`GeneratorDialog` только через `_on_copy_click()`); реальный запуск под
Xvfb — скриншот `EntryDialog` с подставленным сгенерированным паролем
подтверждает, что подпись оценки надёжности появляется под полем
"Пароль:" и над кнопками "Сохранить"/"Отмена".

### 10.14. `GeneratorDialog` переверстан по референсу: карточка с
бейджем, сегментированная шкала надёжности, слайдер длины

Пользователь прислал референс-мокап более современного генератора
паролей (карточка с иконкой, крупным полем пароля, цветной шкалой
надёжности, слайдером и переключателями-пилюлями вместо прежней формы
"Spinbox + список чекбоксов + одна строка объяснения снизу") и попросил
переверстать диалог вплотную к нему.

**Новый вид.** Иконка-бейджа (скруглённый синий квадрат 42×42 с
иконкой кубика, `App._rounded_image`) + заголовок + подпись
`"secrets · криптостойкий · полностью офлайн"` — та же формула, что уже
объясняет выбор `secrets` в разделе 9.3, но теперь прямо в интерфейсе,
а не только в комментариях. Поле сгенерированного пароля —
моноширинным шрифтом (`Consolas`) в скруглённой "плитке"
(`_rounded_backdrop`, тот же приём, что и в `ViewEntryDialog`, раздел
10.9) с кнопкой копирования сбоку, а не отдельной строкой `Entry` под
чекбоксами. Длина — `ttk.Scale` (слайдер) вместо `ttk.Spinbox`, с
бейджем текущего значения (`"20 симв."`) рядом с подписью. Наборы
символов — четыре строки "иконка-чип (`abc`/`ABC`/`123`/`#$%`) + подпись
+ `bootstyle="round-toggle"`" вместо прежних обычных `ttk.Checkbutton`
с текстом самого класса символов. Кнопки внизу — иконка-кубик
(перегенерировать, без подписи), "Копировать", "Готово" (акцент,
просто закрывает диалог) — вместо прежних "Сгенерировать"/
"Копировать"/"Закрыть".

**Сегментированная шкала надёжности — новый декоративный элемент,
дополняющий, а не заменяющий текстовое объяснение.** Пять полосок
(`tk.Frame` шириной по `fill="x", expand=True` каждая, обычные прямые
прямоугольники без скругления — для полоски толщиной 6px скругление
визуально несущественно, а её отсутствие не стоит усложнения ради
малозаметной детали, тот же компромисс, что уже принят для `Treeview`/
строки поиска в разделе 10.8) и цветной бейдж-подпись
(`"Слабая"`/`"Очень высокая"` и т.п.) вместе выражают ту же самую
`assistant.strength.estimate_entropy_bits`, что и текст под ними —
третьей, независимой шкалы стойкости в проекте НЕТ: `_STRENGTH_LEVELS`
(таблица порог-в-битах → сколько сегментов закрасить → подпись → цвет)
— чисто GUI-категоризация одного и того же числа, определена в
`gui/app.py`, а не в `assistant/strength.py` — советнику и генератору
для их собственной логики (`WEAK_ENTROPY_THRESHOLD_BITS` в advisor.py)
понятие "уровня из пяти" не нужно, только сырое число бит; заводить его
в общем модуле означало бы тянуть чисто оформительскую деталь в
крипто-логику без необходимости.

**Обновление стало "живым" сразу с трёх сторон.** У ползунка длины
(`ttk.Scale(..., command=self._on_length_change)`) и у каждого
переключателя набора символов (`ttk.Checkbutton(..., command=
self._on_generate)`) теперь есть обработчик, который сразу
перегенерирует пароль и пересчитывает шкалу/бейдж/подпись — раньше
чекбоксы влияли на результат только при следующем нажатии
"Сгенерировать" отдельной кнопкой. Тот же принцип "обратная связь сразу
по вводу", что уже появился у оценщика надёжности в `EntryDialog`
(раздел 10.13), только раньше (тот раздел был про EntryDialog,
написанный ДО этой переверстки GeneratorDialog).

**Найденный и исправленный баг: `AttributeError` при самом построении
диалога.** Первая версия объявляла `self._use_lower`/`_use_upper`/
`_use_digits`/`_use_symbols` в секции "Наборы символов" — ПОСЛЕ секции
слайдера длины по коду выше неё. Но `ttk.Scale(...).set(20)` сразу же,
синхронно, вызывает свой `command` (`_on_length_change` →
`_on_generate`), а `_on_generate()` читает все четыре `_use_*` — на
момент вызова `.set()` они ещё не существовали как атрибуты экземпляра,
что падало с `AttributeError: 'GeneratorDialog' object has no attribute
'_use_lower'` прямо при открытии диалога (пойман немедленно первым же
тестовым запуском под Xvfb — виджет ещё не был даже показан).
Исправление — все `tk.StringVar`/`tk.IntVar`/`tk.BooleanVar` состояния
диалога (`_result_var`, `_length_var`, четыре `_use_*`) вынесены в
самое начало `__init__`, ДО создания любых виджетов, а не объявляются
"по месту" рядом с виджетом, который их использует, как это раньше
делал прежний код (и как обычно делает остальной код проекта) — здесь
это не просто стиль, а необходимость из-за побочного эффекта `.set()`
на `ttk.Scale` с уже привязанным `command`.

**Что сознательно НЕ повторяет референс:** референс рисует иконку-бейдж
градиентом — Tkinter/`ImageDraw` такого не умеет без ручной генерации
градиентного растра ради одной маленькой иконки, поэтому бейдж залит
сплошным акцентным синим (`_ACCENT`), тот же цвет, что и у всех
остальных акцентных элементов приложения, — визуально почти неотличимо
на таком маленьком элементе, а лишней ML-подобной "красивости" ради
самой красивости в проекте и так стараются избегать (раздел 7).
Иконки-чипы наборов символов (`abc`/`ABC`/`123`/`#$%`) — обычные
`ttk.Label` с плоским фоном, без скругления (в отличие от истории со
скруглением кнопок/панелей, раздел 10.5/10.9, скругление ради
квадратика 22×22px с моноширинным текстом внутри не оправдывает
дополнительный код) — тот же класс компромисса, что и с сегментами
шкалы выше.

**Проверено:** полный набор 83 тестов проходит без изменений
(`test_audit_dialog_close_button_is_not_squeezed_to_zero` по-прежнему
использует `GeneratorDialog` только через публичный `_on_copy_click()`,
внутренняя перестройка виджетов его не касается); реальный запуск под
Xvfb — скриншот с настройками по умолчанию (пароль 20 символов, все
четыре класса, бейдж "Очень высокая", все 5 сегментов зелёные) и
отдельный скриншот с намеренно ослабленными настройками (8 символов,
только строчные буквы — бейдж переключился на "Ниже среднего", 2 из 5
сегментов, соответствующий текст энтропии) подтверждают, что слайдер,
переключатели и шкала обновляются согласованно и сразу, без нажатия
отдельной кнопки.

### 10.15. Найденный и исправленный баг: кнопки "Копировать" и "Готово"
в генераторе стояли вплотную без единого пикселя зазора

По запросу пользователя ("отдали друг от друга кнопки копировать и
готово") — они действительно визуально сливались в одну группу.

**Причина — не опечатка в коде, а совпадение размеров.** Кнопка
"Готово" паковалась `pack(side="right")` без собственного `padx` —
это не ошибка само по себе (`pack` с `side="right"` не обязан оставлять
отступ, он просто прижимает виджет к правому краю ОСТАВШЕЙСЯ area).
Обычно между левой и правой группой кнопок остаётся видимый зазор,
потому что после авторазмера `Toplevel` (раздел 10.9 уже объяснял, что
у `resizable=(False, False)`-диалога нет явно заданной ширины — она
вычисляется по самому широкому ряду контента) в cavity, как правило,
остаётся немного свободного места. Здесь же ряд кнопок (`dice` + отступ
8px + `"Копировать"` + `"Готово"`) ОКАЗАЛСЯ ровно такой же ширины, как
и самый широкий из остальных рядов диалога (поле пароля / шкала
надёжности) — то есть окно авторазмерилось ТОЧНО по ширине кнопок, без
единого лишнего пикселя, и левому (`dice`+"Копировать") и правому
(`"Готово"`) пакованным блокам просто нечем было раздвинуться.
Подтверждено попиксельно (`PIL.Image.getpixel` вдоль строки кнопок,
тот же метод контроля, что и в разделах 10.9/10.12): белых пикселей
фона между концом "Копировать" и началом "Готово" не нашлось вообще —
только явный 8px разрыв между `dice` и "Копировать" (там есть свой
`padx=(8, 0)`), а у "Готово" такого отступа не было.

**Исправление.** `padx=(16, 0)` на `pack()` кнопки "Готово" — отступ
задан на самой кнопке, а не как "надежда, что в cavity точно останется
воздух": теперь гарантированный зазор не зависит от того, совпадёт ли
случайно ширина ряда кнопок с шириной других рядов диалога. Проверено
той же попиксельной проверкой — 16px чистого белого фона между
кнопками на скриншоте.

**Проверено:** полный набор 83 тестов проходит без изменений (`padx`
не влияет ни на одну проверку в `test_gui.py`); реальный запуск под
Xvfb с попиксельным замером ширины зазора.

### 10.16. Найденный и исправленный баг: поле сгенерированного пароля
было двухцветным — белый прямоугольник внутри серой подложки

По запросу пользователя ("сделай поле со сгенерированным паролем
однотонным") — попиксельная проверка подтвердила, что поле
действительно было в двух цветах: `_NEUTRAL_FILL` по краям (там, где
видна подложка `_rounded_backdrop`) и чистый белый `#ffffff` ровно там,
где сам `ttk.Entry` рисует свой текст — то есть подложка была
правильного цвета, а САМО поле поверх нее — нет.

**Причина.** Поле сделано `state="readonly"` (пользователь не должен
редактировать сгенерированный пароль вручную), стилизовано как
`Flat.TEntry` — тем же стилем, что и строка поиска (раздел 10.11),
где `style.layout()` полностью убирает элемент `Entry.field` из
раскладки, оставляя только `Entry.padding`/`Entry.textarea`, а цвет
фона красится напрямую опцией `background` на самом объекте `Entry`,
в обход `style`. Этот приём работает ТОЛЬКО для обычного (редактируемого)
состояния — `search_entry` в главном экране никогда не бывает readonly,
поэтому там баг не проявлялся. Для readonly-состояния `Entry.textarea`
красит фон вообще по-другому: не по прямой Tk-опции `background`, а
полагаясь на то, что фон уже закрашен элементом `Entry.field` — а он
как раз убран из раскладки `Flat.TEntry`. Без него readonly-тексту
просто не от чего унаследовать цвет фона, и он остаётся белым — причём
ДАЖЕ если задать `fieldbackground` явно через `style.map(...)`, потому
что раз элемента, который читает `fieldbackground`, в раскладке нет, то
и красить им уже физически нечего (тот же вывод, что и раздел 10.11
сделал для НЕ-readonly случая, только там про `fieldbackground` при
уже убранном `Entry.field`, а здесь — то же самое, но теперь оказывается,
что это ломает уже не рамку, а сам фон текста).

**Как диагностировано.** Изолированным тестовым скриптом (вне всего
проекта) перебраны варианты: (1) обычный `TEntry` (без удаления
`Entry.field`) + `state="readonly"` + `style.map(fieldbackground=
[("readonly", ...)])` — красится ПРАВИЛЬНО; (2) тот же `style.map`, но
поверх раскладки с удалённым `Entry.field` (как `Flat.TEntry`) —
остаётся белым НЕЗАВИСИМО от `style.map`. Это и указало на точную
причину: дело не в состоянии readonly самом по себе, а в комбинации
"readonly + убранный `Entry.field`".

**Исправление — новый стиль `PasswordDisplay.TEntry`, отдельный от
`Flat.TEntry`.** Вместо попытки убрать рамку через `style.layout()`
(что и ломает readonly-фон), рамка сделана НЕВИДИМОЙ другим способом —
тем же приёмом, что уже применялся к "прозрачным" картинкам кнопок в
разделе 10.5 (не прозрачность, а буквально тот же цвет, что и то, на
чём элемент стоит): `bordercolor`/`lightcolor`/`darkcolor` покрашены в
`_NEUTRAL_FILL` — раскладка (и, значит, элемент `Entry.field`) остаётся
на месте, поэтому `fieldbackground` есть кому красить, а рамка не видна,
потому что нарисована тем же цветом, что и заливка вокруг неё. Плюс
`style.map(...)` для `fieldbackground`/`bordercolor`/`lightcolor`/
`darkcolor` в состояниях `readonly`/`disabled` — в теме `bootstrap-light`
они по умолчанию заданы ОТДЕЛЬНО от обычного состояния (`style.lookup(
"PasswordDisplay.TEntry", "fieldbackground", ("readonly",))` без этой
перезаписи вернул бы `#ffffff`, а не `_NEUTRAL_FILL`, даже после того,
как `style.configure(...)` для НЕ-специфичного по состоянию значения
уже задан правильно) — та же логика "у ttk своя система приоритетов по
состоянию виджета поверх base-конфигурации", что уже встречалась в
разделе 10.6 при выборе направления hover-подсветки.

**Что не изменилось.** `Flat.TEntry` (строка поиска) не тронут — там
всё было и остаётся корректным, потому что то поле никогда не readonly.
Сама раскладка `Entry.field` для `PasswordDisplay.TEntry` НЕ удаляется
(в отличие от `Flat.TEntry`) — это единственная содержательная разница
между двумя стилями, и именно она чинит баг.

**Проверено:** полный набор 83 тестов проходит без изменений (стиль не
затрагивает ни один существующий тест); реальный запуск под Xvfb с
попиксельной проверкой (`PIL.Image.getpixel` построчно внутри поля) —
белых пикселей внутри поля больше нет, вся видимая площадь (кроме самих
символов пароля) закрашена ровно `_NEUTRAL_FILL`; отдельно проверен
пароль длиной 64 символа (максимум слайдера) — поле по-прежнему
скроллится внутри фиксированной ширины, не раздувая диалог, и остаётся
однотонным на всю видимую область.

### 10.17. Тот же баг найден в строке поиска главного экрана; `Flat.
TEntry` и `PasswordDisplay.TEntry` объединены в `NeutralField.TEntry`

По запросу пользователя ("сделай строку поиска на главном экране
однотонной") — попиксельная проверка (тот же метод, что и в разделе
10.16) подтвердила: у строки поиска РОВНО ТА ЖЕ болезнь, что и у поля
пароля — белый `#ffffff` внутри самого `Entry`, `_NEUTRAL_FILL` только
по краям скруглённой подложки.

**Важное уточнение: это не новый баг, а тот же самый баг из разделов
10.10/10.11, который тогда сочли исправленным, но реально не
проверили попиксельно.** Раздел 10.11 в своё время "исправил" ту же
самую проблему через `search_entry.configure(background=_NEUTRAL_FILL)`
— прямую Tk-опцию `background`, в обход `style`, и записал в
"Проверено", что "попиксельная проверка подтверждает" правильный цвет.
На практике эта проверка, судя по всему, замеряла точки НЕ внутри
самого поля (где рисуется текст), а рядом — в отступах подложки
`_rounded_backdrop`, где заливка была верной всегда. `Entry.cget(
"background")` после той правки действительно возвращал правильное
значение (сама Tk-опция устанавливалась исправно), но `Entry.textarea`
— то немногое, что осталось от раскладки после удаления `Entry.field`
(раздел 10.10) — эту опцию для закраски СВОЕГО фона не использует
вообще, ни в одном состоянии; белый на очень светло-сером
(`#ffffff` на `#eef1f8`) достаточно похожи, чтобы разница не бросалась
в глаза на обычном скриншоте — та же ловушка "выглядит правильно, не
проверено попиксельно", что уже не раз фиксировалась в этом файле
(разделы 10.1/10.5/10.7/10.9/10.12), только в этот раз она обманула не
только беглый взгляд, но и саму формулировку "проверено" в разделе
10.11. Раздел 10.16 сначала решил, что дело именно в `state="readonly"`
(там баг тоже был, и фикс для него был необходим), но, вернувшись к
теме заново по этому запросу, стало ясно: `state="readonly"` был
ДОСТАТОЧНЫМ условием для проявления бага, но не ЕДИНСТВЕННЫМ — то же
самое отсутствие покраски `Entry.textarea` происходит и в обычном
редактируемом состоянии, просто раздел 10.11 не заметил этого вовремя.

**Исправление — не новый приём, тот же самый из раздела 10.16
(`fieldbackground`+невидимая рамка вместо удаления `Entry.field`),
только теперь применённый к ОБОИМ полям через ОДИН общий стиль.**
Поскольку `Flat.TEntry` (строка поиска) и `PasswordDisplay.TEntry`
(поле пароля) в итоге нуждались в АБСОЛЮТНО одинаковой настройке (одни
и те же цвета, одна и та же раскладка с сохранённым `Entry.field`,
одна и та же карта состояний readonly/disabled) — держать их отдельными
стилями значило бы дублировать идентичный код без причины. Оба стиля
удалены и заменены одним — `NeutralField.TEntry` — используемым и
`search_entry` на главном экране, и `result_entry` в `GeneratorDialog`.
Старая (неверная) Tk-опция `background=_NEUTRAL_FILL` на `search_entry`
убрана вместе со своим комментарием — она не делала ничего полезного,
только маскировала истинную причину непроверенного визуального
совпадения.

**Что не изменилось.** Сама скруглённая подложка (`_rounded_backdrop`)
вокруг строки поиска не тронута — она с самого начала красилась
правильно, проблема была исключительно в самом `Entry` поверх неё.

**Проверено:** полный набор 83 тестов проходит без изменений (замена
имени стиля не затрагивает ни одну проверку в `test_gui.py`); реальный
запуск под Xvfb с попиксельной проверкой ПО ВСЕЙ площади строки поиска
(построчно, не только по краям, — урок раздела 10.16 учтён) — белых
пикселей внутри поля больше нет, только `_NEUTRAL_FILL` и цвет текста/
плейсхолдера; `GeneratorDialog` перепроверен тем же скриншотом после
переименования стиля — поле пароля осталось однотонным, ничего не
сломалось от объединения стилей.

### 10.18. Защита от брутфорса, продолжение: проверка энтропии
мастер-пароля при создании хранилища, в современном диалоге

По вопросу пользователя "как защитить хранилище от брутфорса" и его
решению реализовать один из предложенных пунктов — раздел 2 уже
объясняет ГЛАВНУЮ защиту (Argon2id, дорогой по памяти перебор), но она
работает только если сам мастер-пароль не тривиален: Argon2id одинаково
дорого перебирает что "correct horse battery staple", что "12345678" —
если пароль есть в словаре первых кандидатов, атакующему не нужен
полный перебор алфавита вообще, и вся дороговизна KDF ничего не спасает
(это и есть "мусор на входе — мусор на выходе": KDF защищает от
БРУТФОРСА, но не от УГАДЫВАНИЯ). Раньше `create` (и в CLI, и в GUI)
проверял только ДЛИНУ мастер-пароля (`MIN_MASTER_PASSWORD_LENGTH = 8`)
— формальную защиту от опечаток, а не от выбора реально слабого пароля.

**Почему использована ТА ЖЕ планка, что и у советника, а не новая.**
`assistant.advisor.WEAK_ENTROPY_THRESHOLD_BITS` и
`assistant.strength.is_common_password` уже определяют, что значит
"слабый пароль", для записей хранилища (раздел 9.3). Мастер-пароль —
тоже пароль, просто более важный (защищает ВСЁ хранилище, а не одну
запись) — придумывать для него отдельный, самостоятельный порог
означало бы либо рассинхронизацию критериев ("почему тут 50 бит слабо,
а на экране создания хранилища 40 бит уже нормально?"), либо
дублирование одной и той же константы под двумя именами. Одно
определение "слабости" на всё приложение — то же архитектурное решение,
что уже применялось при объединении `Flat.TEntry`/`PasswordDisplay.
TEntry` в `NeutralField.TEntry` (раздел 10.17): раз логика одинаковая,
она должна жить в одном месте.

**Почему это ПРЕДУПРЕЖДЕНИЕ, а не жёсткая блокировка.** В отличие от
паролей отдельных записей (которые можно бесплатно перегенерировать
кнопкой "Сгенерировать", не запоминая), мастер-пароль пользователь
должен буквально помнить наизусть — иногда осознанный выбор в пользу
предсказуемой, но самостоятельно придуманной фразы (внутри допустимой
длины) может быть разумным компромиссом для конкретного человека, и
инструмент не должен принимать это решение ЗА него. Советник
(`assistant.advisor`) уже устроен так же — его отчёт информирует, а не
запрещает; `create`/`CreateVaultDialog` последовательны с этим же
принципом: показать оценку максимально наглядно и спросить явное
подтверждение, но не отказать безусловно.

**CLI (`vault/cli.py`, `cmd_create`).** После проверки длины — если
`is_common_password(master_password)` или `estimate_entropy_bits(...)
< WEAK_ENTROPY_THRESHOLD_BITS`, печатается предупреждение в stderr с
самой оценкой энтропии и порогом, затем запрашивается подтверждение
`y/N` — той же формой `input()`, что уже использует `cmd_delete` для
необратимых действий (раздел 6). Ответ, отличный от `y`/`yes`/`да`,
отменяет создание с ненулевым кодом возврата — как и остальные отказы
`create`.

**GUI: `CreateVaultDialog` вместо пары `simpledialog.askstring`.** По
прямой просьбе пользователя ("оформи её в современном интерфейсе") —
поля мастер-пароля/подтверждения, которые `App._on_create` раньше
запрашивал двумя примитивными системными окошками
(`simpledialog.askstring`), заменены полноценным диалогом в том же
визуальном языке, что и `GeneratorDialog`/`EntryDialog`: иконка-бейдж
(замок на синем фоне) + заголовок, подписанные поля, кнопка-"глаз" (тот
же приём, что на экране разблокировки, раздел 10.7), и — главное для
этого раздела — ЖИВАЯ оценка надёжности мастер-пароля: бейдж
("Слабая"/"Очень высокая"...), пятисегментная цветная шкала и текстовая
подпись, обновляющиеся на каждое нажатие клавиши через `trace_add` на
`_password_var` (тот же принцип мгновенной обратной связи, что и у
`EntryDialog`, раздел 10.13). Если пароль слабый — при нажатии
"Создать" `messagebox.askyesno` спрашивает явное подтверждение, тем же
текстом, что предупреждение в CLI.

**`App._build_strength_meter` — общий виджет, вынесенный из
`GeneratorDialog`.** До этого раздела вся разметка "подпись + бейдж +
сегменты + подпись-объяснение" была написана один раз, прямо внутри
`GeneratorDialog.__init__`/`_update_strength` (раздел 10.14). Как
только понадобилась ВТОРАЯ живая оценка надёжности для мастер-пароля —
с абсолютно той же разметкой и той же логикой (`_STRENGTH_LEVELS`,
`explain_password`) — стало ясно, что держать её в двух местах значило
бы просто скопировать один и тот же виджет под разными именами
(`self._strength_badge` в одном классе, что-то similar в другом).
Метод перенесён в `App` (методы диалогов и так уже вызывают
`parent._rounded_backdrop(...)`/`parent._icon_kwargs(...)`/`parent.
_styled(...)` — тот же установившийся паттерн) и строит те же три
виджета внутри переданного `parent`-фрейма, возвращая ОДНУ функцию
`update(password)` — единственное, что нужно вызывающему коду
(`GeneratorDialog._on_generate`/`CreateVaultDialog`'s
`_password_var.trace_add`). `GeneratorDialog` при этом ничего не
потерял — просто его прежний `_update_strength`-метод стал instance-
атрибутом, полученным из общего метода, вместо отдельно написанного.

**Найденный и исправленный баг: `wait_window` на диалоге, уничтоженном
СРАЗУ в конструкторе, падает с `TclError`, а не "возвращается
немедленно".** При обновлении `tests/test_gui.py` под новый
`CreateVaultDialog` первая версия тестового фейка
(`_FakeCreateVaultDialog`) вызывала `self.destroy()` сразу в
`__init__`, в расчёте на то, что `App._on_create`'s `self.wait_window(
dialog)`, вызванный ПОСЛЕ конструктора, на уже несуществующем окне
просто вернётся сразу (интуитивно ожидаемое поведение "ждать закрытия
уже закрытого окна"). На практике это падало с `_tkinter.TclError: bad
window path name` — к моменту вызова `wait_window` путь окна в Tcl уже
невалиден, и `tkwait window` не умеет молча проигнорировать несуществующий
путь, а бросает ошибку. Исправление — `self.after(0, self.destroy)`
вместо прямого вызова: уничтожение окна откладывается в очередь
Tcl-событий и происходит уже ПОСЛЕ того, как `wait_window` запустил свой
локальный цикл обработки событий и держит окно валидным в момент
регистрации ожидания — `tkwait window` в этом случае корректно
обрабатывает отложенное уничтожение как обычное событие и возвращается
штатно. Тот же принцип уже дважды встречался в этом файле в других
формах (`_rounded_backdrop`, раздел 10.9: важен не факт вызова, а ТОЧНЫЙ
момент в очереди событий Tcl) — здесь тот же класс ошибки, но в
контексте тестовой инфраструктуры, а не отрисовки.

**Тесты.** `tests/test_gui.py`: `_create_vault()` (общий helper,
используемый почти всеми тестами файла) теперь подменяет сам класс
`guiapp.CreateVaultDialog` на фейковый `tk.Toplevel`, а не
`simpledialog.askstring` — раз диалог, а не пара функций, стал
источником пароля; `test_create_rejects_mismatched_confirmation`/
`test_create_rejects_too_short_password` заменены на
`test_create_dialog_rejects_*`, тестирующие `CreateVaultDialog`
НАПРЯМУЮ (`dialog._on_submit()`), поскольку сама валидация переехала
внутрь диалога и её больше нечем тестировать через `App._on_create`;
добавлен `test_create_dialog_warns_about_weak_master_password`
(проверяет оба ответа `askyesno` — отказ и подтверждение) и
`CreateVaultDialog` в `test_dialog_construction_does_not_raise`.
`tests/test_cli.py`: два новых теста на предупреждение о слабом
мастер-пароле (отказ `n` не создаёт файл, подтверждение `y` создаёт) —
существующие тесты используют `MASTER = "correct horse battery
staple"` (~133 бита энтропии), поэтому предупреждение под них не
попадает и они не требуют изменений. Итого 86 тестов (было 83: −2
переименованных/переписанных + 3 новых в GUI, +2 новых в CLI), все
проходят.

**Проверено:** полный набор 86 тестов проходит; реальный запуск под
Xvfb — скриншоты `CreateVaultDialog` с сильным паролем (бейдж "Средняя"/
"Очень высокая" в зависимости от ввода, зелёные сегменты) и с намеренно
слабым ("aaaaaaaa", 8 символов только строчных — бейдж "Ниже среднего",
2 из 5 сегментов оранжевые) подтверждают, что живая оценка работает
идентично тому же виджету в `GeneratorDialog`.

### 10.19. Скругление полей МАСТЕР-ПАРОЛЬ/ПОДТВЕРЖДЕНИЕ в `CreateVaultDialog`

По запросу пользователя ("сделай нормальное скругление на поле ввода и
поле подтверждения") — оба поля `CreateVaultDialog` (раздел 10.18) на

убирающий его, как `Flat.TEntry`) единственный, что красит фон
текстовой области корректно, а не оставляет под ней белый прямоугольник.
Кнопка-"глаз" осталась внутри того же `pw_row`, что и поле пароля (тот
же паттерн, что и кнопка копирования внутри `password_box` в

кнопку вместе, а не два соседних отдельных скругления.

### 10.20. Уменьшены поля МАСТЕР-ПАРОЛЬ/ПОДТВЕРЖДЕНИЕ; кнопки "Создать"/
"Отмена" выровнены по ширине

По запросу пользователя ("уменьши длину и ширину полей для ввода
мастер пароля, а так же сделай кнопки создать и отмена одного размера")
внесены два независимых изменения `CreateVaultDialog` (раздел 10.19).

**Поля стали заметно компактнее — фиксированным размером, а не просто
меньшим padding'ом.** До этого раздела `pw_row`/`confirm_box`
паковались `fill="x"`, то есть растягивались на всю ширину карточки
диалога (~400px) независимо от значения `padding=` — уменьшение
padding само по себе НЕ уменьшило бы ширину поля, только внутренние
отступы вокруг уже растянутого на всю ширину содержимого. Вместо этого
оба контейнера теперь заведены с явным `width=_MASTER_FIELD_WIDTH`
(260px), `height=_MASTER_FIELD_HEIGHT` (38px) и `pack_propagate(False)`
— эта комбинация принудительно держит размер фрейма РОВНО тем, что
задано, вместо того чтобы (как повёл бы себя `pack` по умолчанию)
подстраивать размер под содержимое или растягиваться под `fill="x"`.
Упаковка самих контейнеров сменилась с `pack(fill="x")` на
`pack(anchor="w")` — без этого `pack_propagate(False)` не имело бы
смысла: `fill="x"` всё равно растянул бы фрейм на всю ширину
родителя, игнорируя заданный `width`.

**Почему именно фиксированный размер, а не просто "уже растянутое, но с
меньшим padding".** У поля пароля внутри есть кнопка-"глаз", а у поля
подтверждения — нет: если бы оба контейнера просто сжимались "по
содержимому" (обычный `pack` без `width=`/`pack_propagate(False)`), их
итоговая ширина отличалась бы друг от друга на ширину этой кнопки — то
есть поля выглядели бы РАЗНОГО размера, хотя визуально должны читаться
как пара одинаковых полей формы. Фиксация обоих одним и тем же
`_MASTER_FIELD_WIDTH`/`_MASTER_FIELD_HEIGHT` гарантирует одинаковый
размер контейнера независимо от того, что внутри — а `password_entry`/
`confirm_entry` внутри упакованы с `fill="both", expand=True`, поэтому
само поле ввода занимает всё оставшееся после кнопки (если она есть)
место в уже фиксированной по размеру "плитке", а не наоборот.

**Кнопки "Создать"/"Отмена" — через `grid` с `uniform=`, а не `pack`.**
У кнопки "Создать" есть иконка (`compound="left"`), у "Отмена" — нет,
поэтому при упаковке через `pack` (как было раньше) их ширина
определялась независимо каждой своим содержимым и не совпадала.
Исправление — обе кнопки помещены в `grid` с двумя колонками, у которых
`columnconfigure(..., weight=1, uniform="create_vault_footer")`: общая
`uniform`-группа заставляет `grid` выделить ОБЕИМ колонкам одинаковую
ширину (по более широкому требованию из двух), а `sticky="ew"` у самих
кнопок растягивает их на всю ширину своей колонки — в результате кнопки
одинаковой ширины независимо от разницы в содержимом. Это тот же приём
выравнивания по сетке, которым и в целом решаются подобные задачи в
`tkinter`/`ttk` (в отличие от `pack`, где нет общего понятия "растянуть
несколько виджетов до одной ширины между собой" без ручного вычисления
максимума).

**Проверено:** полный набор 86 тестов проходит без изменений (сами
`_password_var`/`_confirm_var`/`_on_submit`/кнопки не переименованы и
не потеряли команды — изменилась только их геометрия); реальный запуск
под Xvfb — свежий скриншот показывает заметно более компактные поля
и кнопки одинаковой ширины; попиксельная проверка (`PIL.Image.getpixel`
построчно внутри обоих полей) подтверждает отсутствие белых артефактов
после смены способа упаковки (`_NEUTRAL_FILL` на всей видимой площади
полей); отдельный замер горизонтальных границ кнопок на скриншоте
(поиск смены цвета вдоль строки кнопок) показал ширину ~189px у
"Создать" и ~191px у "Отмена" — расхождение в пределах сглаживания
скруглённых углов, то есть кнопки визуально и по факту одного размера.

### 10.21. Кнопка-"глаз" отделена от поля мастер-пароля; иконка-замок в
шапке заменена на иконку приложения

По запросу пользователя ("раздели кнопку показать пароль и поле ввода,
а также смени иконку с замком на иконку приложения") — два независимых
изменения `CreateVaultDialog` (разделы 10.19–10.20).

**Разделение поля и кнопки-"глаза".** До этого раздела `pw_row` был
ОДНОЙ скруглённой "плиткой" (`_rounded_backdrop`), внутри которой рядом
лежали и `password_entry`, и кнопка переключения видимости — то есть
кнопка визуально была впаяна в ту же рамку, что и само поле, хотя по
смыслу это два разных действия (ввод и вспомогательное переключение).
Исправление — поле и кнопка разнесены на два независимых соседних
виджета внутри общего `pw_container` (обычный `ttk.Frame` без своего
фона): `pw_box` — скруглённая "плитка" РОВНО того же вида, что и
`confirm_box` (та же `_rounded_backdrop`, тот же `_MASTER_FIELD_WIDTH`/
`_MASTER_FIELD_HEIGHT`), содержащая ТОЛЬКО `password_entry`; кнопка-
"глаз" — рядом, `pack(side="left", padx=(8, 0))`, ЗА пределами этой
плитки, сохранив свой собственный, отдельный `_rounded_button_style`
(его скругление не менялось — оно и раньше было самостоятельным, просто
раньше оба скруглённых элемента стояли впритык друг к другу без зазора
внутри одной, а не двух, "плиток"). Побочный положительный эффект: поле
пароля теперь занимает ВЕСЬ `_MASTER_FIELD_WIDTH` целиком (раньше делило
его с кнопкой), поэтому по размеру полностью совпадает с полем
подтверждения — раздел 10.20 фиксировал их одинаковый размер именно ради
такого совпадения, и теперь оно достигается без дополнительных ухищрений
(раньше `pw_box` вынужденно была одного размера с `confirm_box`, хотя
делила его с кнопкой — сейчас это уже не "хотя", а естественное
следствие того, что оба поля устроены идентично).

**Иконка приложения вместо схематичного замка.** До этого раздела шапка
диалога рисовала СВОЙ собственный синий скруглённый квадрат
(`parent._rounded_image(42, _ACCENT, "#ffffff")`) с наложенным поверх

же приём, что и у иконки-бейджа `GeneratorDialog` (кубик на синем фоне,

иконку приложения — ту же картинку (`gui/icon.png`, раздел 10.2), что

medium` (64px, `subsample(4, 4)` от исходных 256px), тот же вариант, что
уже показывает `_build_unlock_frame` на карточке разблокировки: одна и

"иконка приложения" крупным планом, а не набор разных бейджей под

`hasattr`-проверкой на случай отсутствия файла иконки на диске

`_build_unlock_frame`.

**Что не изменилось.** `GeneratorDialog`'а собственный синий бейдж с
кубиком не тронут — пользователь попросил заменить иконку именно в

"глаз" на экране разблокировки (раздел 10.7) тоже осталась как была —
там она никогда и не была визуально сращена с полем в одну плитку
(поле там вообще без `_rounded_backdrop`), так что раздел её не касается.

**Проверено:** полный набор 86 тестов проходит без изменений
(`_password_var`/`_password_entry`/`_on_toggle_visibility`/структура
`values` не переименованы — тесты не ссылаются на промежуточные
`pw_row`/`pw_container` по имени); реальный запуск под Xvfb — свежий

### 10.22. Кнопка-"глаз" сделана соразмерной полю ввода по высоте

По запросу пользователя ("сделай кнопку показать пароль соразмерной
полю ввода") — после разделения поля и кнопки на два независимых
элемента (раздел 10.21) стало заметно, что кнопка ощутимо НИЖЕ поля:
её высота определялась только внутренним `padding=(8, 6)` вокруг иконки
22px (см. `_rounded_button_style`, раздел 10.5), то есть примерно
22 + 2×6 = 34px, тогда как высота `pw_box` зафиксирована явно —
`_MASTER_FIELD_HEIGHT = 38px` (раздел 10.19). Разница небольшая, но
достаточная, чтобы пара "поле + кнопка" не читалась как единая по
высоте группа.

**Исправление — тот же приём фиксированного размера, что уже применён
к самим полям.** Кнопка обёрнута в `eye_button_box` —
`ttk.Frame(pw_container, width=_MASTER_FIELD_HEIGHT, height=
_MASTER_FIELD_HEIGHT)` с `pack_propagate(False)` (тот же механизм, что
у `pw_box`/`confirm_box`, раздел 10.19) — квадрат РОВНО высотой поля.
Сама кнопка внутри упакована `pack(fill="both", expand=True)`, а не
оставлена с "естественным" размером — сработало без дополнительных
правок `_rounded_button_style`, потому что его фон уже растягиваемый
(9-patch приём, `border=` в `element_create`, раздел 10.5): тот же
константный `radius`-бордюр остаётся нетронутым, а внутренняя площадь
просто растягивается под любой заданный контейнером размер, ровно как
и у полноширинных кнопок ("Разблокировать", "Создать" и т.п.).

**Почему квадрат, а не только высота.** `width=_MASTER_FIELD_HEIGHT`
даёт кнопке квадратную форму (сторона равна высоте поля) — это
осознанный выбор, а не побочный эффект: единственная иконка без текста
внутри уже подразумевала примерно квадратные пропорции и раньше
(`padding=(8, 6)` тоже давало почти квадратную кнопку), просто другого,
меньшего размера — увеличение до полного соответствия высоте поля
сохраняет ту же, уже привычную пользователю форму, просто масштабирует
её вверх.

**Проверено:** полный набор 86 тестов проходит без изменений (обёртка
кнопки в дополнительный `Frame` не меняет `command=self._on_toggle_
visibility` и не задействована ни в одном тесте по имени); реальный
запуск под Xvfb — свежий скриншот показывает кнопку и поле визуально
одной высоты; попиксельная проверка (`PIL.Image.getpixel`, поиск границ
заливки `_NEUTRAL_FILL` по вертикали отдельно в колонке поля и в
колонке кнопки) подтверждает, что обе области занимают один и тот же
диапазон строк (~132–165px), то есть кнопка и поле теперь буквально, а
не только на глаз, одной высоты.

### 10.23. Найденный и исправленный баг: иконка "глаза" смещена в
правый нижний угол своей квадратной кнопки

По запросу пользователя ("поставь на место эмодзи глаза на кнопке
показать пароль") — после увеличения кнопки-"глаза" до квадрата
`_MASTER_FIELD_HEIGHT`×`_MASTER_FIELD_HEIGHT` (раздел 10.22) сама иконка
внутри оказалась заметно смещена к правому нижнему углу кнопки, а не
по центру — видно и на обычном скриншоте, и подтверждено попиксельным
увеличенным кропом квадрата кнопки.

**Расследование — не компонент, который казался очевидным.** Первая
гипотеза — `compound="left"` (из `_icon_kwargs`, раздел 10.3),
применяемый ко ВСЕМ иконка-кнопкам приложения, включая эту, где текста
нет вообще. Изолированный тестовый скрипт (отдельно от проекта, тот же
стиль и иконка, но контейнер `pack_propagate(False)` РОВНО 38×38 —
точно как `eye_button_box`) показал: тот же сдвиг воспроизводится
что с `compound="left"`, что и БЕЗ него (`image=` без `compound`) —
значит, дело не в compound. Дальше проверен `padding` стиля кнопки
(`_rounded_button_style(..., padding=(8, 6))`, унаследованный от
`"Rounded.IconToggle"`, раздел 10.7): тот же тест с `padding=(0, 0)` —
иконка встаёт РОВНО по центру; с `padding=(8, 6)` — тот же характерный
сдвиг вниз-вправо повторяется стабильно. Вывод: конкретно при точном
совпадении итогового размера кнопки (38px) с суммой иконки и удвоенного
padding по ширине (22 + 2×8 = 38 — совпадение до пикселя без единого
"лишнего" пикселя пространства) `ttk.Button` в этой теме перестаёт
центрировать содержимое по `anchor="center"` и вместо этого прижимает
его к правому нижнему углу доступной области — не задокументированная
где-либо особенность, обнаруженная только прямым экспериментом, а не
чтением документации `ttk`.

**Почему не трогать сам `"Rounded.IconToggle".`** Этот стиль
используется кнопками-"глазами" в НЕСКОЛЬКИХ местах приложения (экран
разблокировки — раздел 10.7, эта же кнопка до раздела 10.22 при
естественном, а не квадратном размере) — везде ИМЕННО при их
естественном (не растянутом искусственно до отдельного контейнера)
размере, где сумма иконки и padding НЕ совпадает так же точно с
итоговым размером кнопки, и проблема не проявляется (там годами
работало корректно, что и подтверждают все прежние визуальные проверки
разделов 10.7 и далее). Кроме того, `_rounded_button_style` кэширует
стиль по имени (раздел 10.7) — второй вызов с тем же именем, но другим
`padding`, был бы просто молча проигнорирован, а не переопределил бы
существующий стиль, так что "поправить padding по месту" для этой
ОДНОЙ кнопки, оставив имя стиля прежним, было бы попросту невозможно.

**Исправление.** Заведён отдельный стиль `"Rounded.IconToggleSquare"` с

### 10.24. `AuditDialog` переверстан по референсу-варианту C: единый
список находок с цветными маркерами вместо `ScrolledText`

По запросу пользователя ("Пришли ещё референсы для советника" → выбран
вариант C из трёх присланных HTML-мокапов) `AuditDialog` — окно отчёта
советника (`assistant.advisor`) — переверстан вплотную к референсу:
раньше это был простой read-only `ttkbootstrap.widgets.ScrolledText` с
уже отформатированной в одну строку текстом (`assistant.advisor.
format_report`), без единого элемента визуального языка остальных
диалогов приложения (раздел 10.1: изначально это было сознательным
ограничением объёма изменений — "дотянуть до общего вида можно позже").

**Диалог теперь принимает сам `AdvisorReport`, а не готовую строку.**
`App._on_audit()` раньше вызывал `AuditDialog(self, format_report
(report))` — строка, в которой сайт/логин/причины уже необратимо
склеены в текст под конкретный формат вывода терминала. Новой вёрстке
нужны ОТДЕЛЬНЫЕ поля (цветной маркер зависит от категории, сайт
показывается жирным, логин и причина — приглушённым текстом рядом и
под ним) — то есть нужен именно объект `AdvisorReport`, а не текст.
`format_report()` никуда не делся и не изменился — он по-прежнему
единственный путь вывода отчёта в CLI (`vault audit`, раздел 9.3); GUI
и CLI теперь просто читают ОДИН И ТОТ ЖЕ `AdvisorReport` по-разному, а
не делят между собой текстовое представление, как раньше.

**Шапка** — тот же приём иконки-бейджа, что и в `GeneratorDialog`/
`CreateVaultDialog` (синий скруглённый квадрат 42×42 + `shield_white`
поверх, `parent._rounded_image`/`parent._button_icon`), с подписью
"эвристический анализ, без ИИ и без сети" — прямая отсылка к разделу 9
(советник — не LLM, ничего не отправляет в сеть), теперь видимая прямо
в интерфейсе, а не только в комментариях кода.

**Бейджи-счётчики категорий** — три `ttk.Label` с фоном
`_mix(цвет, "#ffffff", 0.85)` и текстом того же цвета, формат
`"Категория: N"` (например, `"Слабые: 2"`), а не грамматически
согласованная подпись с числительным ("1 повтор"/"2 повтора"/
"5 повторов"), как на самом референсе-мокапе — правильное русское
склонение по числу для трёх разных категорий ("повтор", "слабый",
"устаревший" склоняются по-разному) было бы самостоятельной, отдельно
тестируемой задачей ради чисто декоративной детали (раздел 7: не
усложнять сверх задачи). Бейдж с нулевым счётчиком просто не
показывается (`add_chip` рано выходит при `count == 0`).

**Цвета категорий — переиспользованы из `_STRENGTH_LEVELS`, а не новая
палитра.** `_ADVISOR_REUSED_COLOR`/`_ADVISOR_WEAK_COLOR`/
`_ADVISOR_OLD_COLOR` — это те же самые `"#d6484b"`/`"#e0724a"`/
`"#d1a625"`, что уже используются как первые три уровня шкалы
надёжности пароля (`_STRENGTH_LEVELS`, раздел 10.14): повтор пароля —
самая серьёзная находка, тот же красный, что и "Слабая" на шкале;
слабый пароль — предупреждение, тот же оранжевый, что "Ниже среднего";
устаревший — самая мягкая по срочности находка, тот же золотой, что
"Средняя". Одна и та же идея "серьёзность → цвет" на всё приложение
(тот же принцип, что и переиспользование `WEAK_ENTROPY_THRESHOLD_BITS`
между советником и проверкой мастер-пароля, раздел 10.18), а не второй
независимый источник истины для похожей по смыслу шкалы.

**Список находок — `Canvas` + внутренний `Frame` + `Scrollbar`, а не
`Treeview`/`Text`.** Раздел 10.12 уже объяснял, почему `ttk.Treeview` не
подходит для строк со смешанным форматированием (жирный сайт + два
приглушённых подтекста) без owner-drawn ячеек, которых у стандартного
`Treeview` нет; `Text`/`ScrolledText` тоже не годится — это снова была
бы одна строка текста, а не настоящие виджеты с цветным маркером.
Классический для Tkinter приём "скроллируемый Frame": `tk.Canvas`
фиксированной высоты (320px — раньше эту роль неявно играл `ScrolledText`
со своим авторазмером и прокруткой) содержит внутренний `ttk.Frame`
через `create_window(...)`, `<Configure>` на внутреннем фрейме
пересчитывает `scrollregion`, `<Configure>` на самом канвасе растягивает
внутренний фрейм на актуальную ширину — та же последовательность идей
(не полагаться на порядок готовности геометрии "на глаз", а слушать
реальные Tk-события), что уже применялась для `_rounded_backdrop`
(раздел 10.9). Прокрутка колёсиком мыши забинжена отдельно на сам
канвас (`<MouseWheel>` для Windows/macOS, `<Button-4>`/`<Button-5>` для
Linux/X11) — не глобально на диалог, чтобы не перехватывать прокрутку
где-либо ещё.

**Цветные кружки-маркеры находок — `App._advisor_marker(color)`, тот же
приём рисования, что и `_site_avatar` (раздел 10.12).** Первая версия
рисовала маркер как плоский квадратный `tk.Frame(width=8, height=8,
background=color)` — по факту работало, но визуально выглядело именно
квадратиком, а не кружком-точкой, как на референсе. Раз в приложении
уже есть готовый, проверенный способ рисовать цветной кружок (аватары
записей списка — суперсэмплинг 4x/8x + `PIL.ImageDraw.ellipse` +
уменьшение `LANCZOS`, раздел 10.12), заведён `_advisor_marker` — тот же
приём, но без буквы внутри и меньшего размера (9px), кэшируется по
цвету в `self._advisor_markers` (тот же принцип кэша на экземпляр окна,
что и `self._icons`/`self._avatar_images` — `ImageTk.PhotoImage`
привязан к конкретному Tcl-интерпретатору, раздел 10.3).

**Пустое хранилище (`report.is_clean`) — отдельное дружелюбное
сообщение, а не пустой список.** Тот же смысл, что и "Явных проблем не
найдено." в текстовом отчёте CLI (`format_report`), но оформлено как
часть карточки (жирный заголовок + приглушённая подпись), а не голая
строка текста — без бейджей-счётчиков и без пустого прокручиваемого
канваса, которые в этом случае были бы просто пустым местом на экране.

**Футер — одна нейтральная кнопка "Закрыть", без изменений по смыслу.**
У `AuditDialog` и раньше не было акцентной кнопки (раздел 10.6: советник
только информирует, ничего не подтверждает и не создаёт) — это не
изменилось, просто кнопка теперь в отдельном `footer`-`Frame` (тот же
паттерн, что у `CreateVaultDialog`/`GeneratorDialog`), а не напрямую в
`self` с `pack(pady=8)`.

**Тесты.** `tests/test_gui.py`: оба места, создававшие `AuditDialog(app,
"report text")` (произвольная строка-заглушка, что было ЕДИНСТВЕННО
возможно для старой сигнатуры), заменены на реальные `AdvisorReport` —
`test_dialog_construction_does_not_raise` теперь строит диалог ДВАЖДЫ:
с отчётом, покрывающим все три категории находок (чтобы построение
`add_reused_row`/`add_issue_row`/секций сработало хотя бы раз каждое), и
отдельно с пустым `AdvisorReport()` (ветка `is_clean`) — обе ветки
вёрстки теперь под смоук-тестом, а не только одна, как получилось бы,
проверяя один и тот же отчёт дважды. `test_audit_dialog_close_button_
is_not_squeezed_to_zero` — кнопка "Закрыть" в новой вёрстке лежит не

исправлено рекурсивным `_find_widgets_by_class()`-хелпером. Итоговое
число тестов не изменилось (86) — обе правки расширяют существующие

**Проверено:** полный набор 86 тестов проходит; реальный запуск под

### 10.25. Найденный и исправленный баг: заголовки диалогов показывали
фирменную иконку `ttkbootstrap` (перо), а не иконку приложения

Пользователь заметил в заголовке окна `GeneratorDialog` (видно в
панели задач/заголовке окна на реальном рабочем столе — этого не видно
на Xvfb-скриншотах этой сессии, они без оконного менеджера и без рамки
окна вообще) синий значок с белым пером вместо иконки приложения
(тёмно-синяя гора со скважиной, раздел 10.2). Значок-перо — это не
случайная путаница и не повреждённый файл, а **фирменная иконка самой
библиотеки `ttkbootstrap`**, зашитая в её код.

**Причина — найдена чтением исходника `ttkbootstrap/window.py`, а не
догадкой.** И `ttkbootstrap.Window` (наш `App`), и `ttkbootstrap.
Toplevel` (родитель ВСЕХ наших диалогов — `EntryDialog`,
`CreateVaultDialog`, `ViewEntryDialog`, `AuditDialog`, `GeneratorDialog`)
принимают параметр `iconphoto` со значением по умолчанию `''` (пустая
строка, НЕ `None`) и в своём `__init__` безусловно вызывают
`self._setup_icon(iconphoto, default_data=_DEFAULT_ICON_DATA)`. Раскрыв
`_setup_icon`: `iconphoto == ''` означает "нет своего пути — применить
`_apply_default_icon`", а та, в свою очередь, красит `self.iconphoto(
True, ...)` картинкой из `ttkbootstrap/assets/app_icons/ttkbootstrap.
png` (или встроенным в код base64 PNG `_DEFAULT_ICON_DATA`, если файла
нет) — то есть **логотипом самого ttkbootstrap**, а не чем-то нашим.

Наш собственный код (`App.__init__`) ПОСЛЕ вызова `super().__init__()`
дополнительно делает `self.iconphoto(True, self._icon_image)` со своей
картинкой (`gui/icon.png`) — это перекрывает иконку `ttkbootstrap` НА
ГЛАВНОМ ОКНЕ, и параметр `default=True` по документации Tk должен
делать эту иконку значением по умолчанию для ВСЕХ будущих дочерних
`Toplevel`-окон приложения — ровно так это описано и в комментарии
самого `ttkbootstrap.window._setup_icon()`: "The application root's
icon is the app-wide default, so child toplevels ... inherit it instead
of the Tk feather". Но на практике каждый НАШ диалог — тоже отдельный
`ttkbootstrap.Toplevel`, и его СОБСТВЕННЫЙ `__init__` заново вызывает
`_setup_icon('', ...)` → `_apply_default_icon(...)` УЖЕ НА СЕБЕ, то есть
явно перезаписывает ЛЮБОЙ унаследованный "дефолт" своей собственной
иконкой ttkbootstrap раньше, чем до этого дефолта вообще доходит дело
— наш `App.iconphoto(True, ...)` просто не успевает "дожить" до
дочерних окон, потому что каждое из них само сначала красится в
дефолтный логотип библиотеки.

**Исправление — `iconphoto=None` в конструкторе каждого диалога.** По
докстрингу `_setup_icon` в самом `ttkbootstrap`: `None` означает
"оставить иконку как есть, ничего не трогать" (в отличие от `''`,
которое явно применяет дефолтную иконку). Добавлен именно этот
параметр в вызов `super().__init__(..., resizable=(False, False),
iconphoto=None)` во всех пяти диалогах — теперь ни один из них САМ не
перезаписывает свою иконку, и она действительно наследуется от того,
что было установлено как "дефолт для будущих окон" на главном `App`
(наша `gui/icon.png`), как и задумано в самом `ttkbootstrap`.

**Проверено:** полный набор 86 тестов проходит без изменений (`
iconphoto=None` не влияет ни на один из проверяемых атрибутов/методов
диалогов); прямой Tcl-уровневый тест (`hasattr(dialog, "_icon")` сразу
после конструктора) подтверждает, что ДО исправления каждый диалог
(проверено на `GeneratorDialog`/`CreateVaultDialog`) сам себе заводил
атрибут `_icon` с картинкой ttkbootstrap (`_apply_default_icon`
отрабатывала), а ПОСЛЕ исправления — не заводит вообще (`_setup_icon`
рано выходит на `None`), то есть путь кода, красивший диалоги в чужой
логотип, для них больше не выполняется.

**Дополнительно — реальная визуальная проверка заголовка окна, по
просьбе пользователя.** Обычные Xvfb-скриншоты этой сессии рамки/
заголовка окна вообще не показывают (Xvfb без оконного менеджера рисует
только клиентскую область) — именно поэтому баг с чужой иконкой ни разу
не был замечен на предыдущих скриншотах. Чтобы увидеть заголовок
по-настоящему, в тестовое окружение установлен `openbox` (лёгкий
оконный менеджер), запущенный поверх отдельного Xvfb-дисплея — тогда
`xwd -root` захватывает уже полноценное окно с рамкой, кнопками
свернуть/развернуть/закрыть и иконкой заголовка, как на реальном
рабочем столе. Скриншоты экрана разблокировки, `GeneratorDialog`,
`AuditDialog` и `ViewEntryDialog` под openbox подтверждают: у всех
четырёх в заголовке окна — иконка приложения (гора со скважиной), а не
логотип-перо `ttkbootstrap`, то есть исправление работает не только на
уровне Tcl-атрибутов, но и в реально видимом пользователю заголовке
окна.

### 10.26. Найденный и исправленный баг: на Windows-ноутбуке с
масштабированием экрана иконки пропадали, а скруглённые панели теряли
и форму, и заливку

Пользователь прислал скриншоты `GeneratorDialog`/`EntryDialog`/
`ViewEntryDialog`, снятые на реальном Windows-ноутбуке (а не в этой
разработческой Linux+Xvfb-песочнице) — и там всё выглядело заметно
хуже, чем на скриншотах из раздела 10.25: иконки на кнопках (кубик,
копирование, глаз, карандаш) — пустые блёклые квадраты без единого
значка; скруглённые "плитки" полей и тёмная шапка `ViewEntryDialog` —
с острыми, а не скруглёнными углами; по краю окна кое-где проступают
кусочки обоев рабочего стола вместо сплошного фона приложения. Также
по-прежнему виден логотип-перо `ttkbootstrap` в заголовке — отдельный
открытый вопрос, см. ниже.

**Причина — масштабирование экрана Windows (HiDPI), а не испорченные
файлы.** У Windows-ноутбуков почти всегда включено системное
масштабирование интерфейса (125%/150% — обычная настройка для экранов
с высоким разрешением, Параметры → Система → Экран → Масштаб).
`ttkbootstrap.Window.__init__` по умолчанию принимает `high_dpi=True`
(прочитано прямо в исходнике `ttkbootstrap/window.py`) и, если он
истинный, сразу вызывает `utils.enable_high_dpi_awareness()`, которая
на Windows дёргает `SetProcessDpiAwareness()`/`SetProcessDPIAware()` —
помечает ВЕСЬ процесс приложения как "DPI-aware" для ОС. После этого
сам Tk (не ttkbootstrap — это встроенное поведение самого Tk на
Windows) автоматически подбирает коэффициент масштабирования (`tk
scaling`) под реальный DPI монитора и применяет его ко ВСЕМУ, что
измеряется в его логических единицах ("points") — шрифтам, отступам
(`padding=`), стандартным размерам виджетов. Но НАША СОБСТВЕННАЯ
графика (иконки 22px, скруглённые подложки, бейджи-квадраты 42px —
разделы 10.2/10.3/10.5/10.9) нарисована через `PIL` в АБСОЛЮТНЫХ
пикселях, без какого-либо понятия о "points" или коэффициенте
масштабирования Tk — при включённом DPI-aware режиме эти растровые
картинки остаются ФИЗИЧЕСКИ теми же 22/42 пикселями, в то время как
все окружающие их нативные ttk-виджеты вырастают в 1.25–1.5 раза.
Результат — ровно то, что видно на скриншотах пользователя:
- **Иконки "пропадают".** Крошечная 22px-картинка, показанная внутри
  выросшей (за счёт увеличенных шрифта/padding) кнопки, визуально
  теряется — не буквально исчезает, а становится непропорционально
  маленькой на фоне остального контента кнопки.
- **Скруглённые подложки не покрывают виджет целиком, из-под них видно
  рабочий стол.** `_rounded_backdrop` рисует картинку под РЕАЛЬНЫЙ
  измеренный размер фрейма (`winfo_width()`/`winfo_height()`), но при
  DPI-масштабировании тайминг пересчёта geometry Tk (`pack`/`update_
  idletasks()`) может отличаться от того, что уже проверено и
  откалибровано в разделах 10.9/10.19 для обычного (не-DPI) режима —
  подложка либо не успевает пересчитаться до финального (уже
  увеличенного DPI-режимом) размера виджета, либо просто не дотягивает
  до его новых физических границ, и сквозь непокрытый край становится
  виден истинный фон окна — в данном случае рабочий стол Windows,
  который просвечивает потому, что где-то в дереве виджетов остаётся
  непрокрашенный прозрачный/системный фон.

**Почему это не проявлялось раньше ни на одном скриншоте в этой
сессии.** Все предыдущие визуальные проверки (включая раздел 10.25 с
openbox) сделаны в Linux+Xvfb-окружении с фиксированным DPI 96 — на
Linux `enable_high_dpi_awareness()` пытается импортировать `ctypes.
windll` (Windows-специфичный модуль), ловит исключение и молча ничего
не делает (`except Exception: pass`) — то есть `high_dpi=True` в этом
дев-окружении был и остаётся полным no-op'ом. Баг мог проявиться
ТОЛЬКО на настоящей Windows-машине с реальным включённым масштабированием
экрана — то есть именно там, где его и обнаружил пользователь, а не в
этой песочнице, как бы тщательно здесь ни тестировали интерфейс.

**Исправление.** `App.__init__` теперь передаёт `high_dpi=False`
в `super().__init__(...)` — это ЦЕЛИКОМ отключает вызов
`enable_high_dpi_awareness()`, то есть процесс остаётся "DPI-unaware"
для Windows: сама ОС в этом случае считает, что приложение "не умеет" в
масштабирование, и вместо честного перерасчёта geometry растягивает уже
готовое отрисованное окно как ЕДИНУЮ картинку (стандартный DPI
Virtualization-режим Windows). Изображение станет слегка менее чётким
на очень высоком DPI (та же "мыльность", что видна у старых не-DPI-aware
приложений на Windows) — сознательно принятый компромисс: коэффициент
масштабирования Tk (`tk scaling`) при этом остаётся 1.0 НЕЗАВИСИМО от
реального DPI монитора, то есть наша собственная растровая графика и
нативные ttk-виджеты снова растут (точнее, НЕ растут) СИНХРОННО друг с
другом — ровно тот режим, что уже подтверждённо работает корректно на
любом экране в этой сессии (раздел 10.25 и все предыдущие визуальные
проверки), просто раньше `high_dpi=True` был безопасен только потому,
что на Linux он ничего не делал.

**Открытый вопрос — логотип-перо `ttkbootstrap` в заголовке окна,
всё ещё виден на скриншотах пользователя.** Раздел 10.25 исправил
причину появления ЭТОЙ иконки на уровне кода (`iconphoto=None` во всех
диалогах) и подтвердил фикс на Linux+openbox — но скриншоты
пользователя сделаны предположительно ДО этого исправления (или до
того, как обновлённый код был у него на машине) — нужно, чтобы
пользователь подтвердил, что запускает актуальную версию кода после
обоих исправлений, прежде чем считать иконку заголовка отдельной,
всё ещё открытой проблемой именно для Windows (`iconphoto` вообще
исторически менее надёжно поддерживается на Windows-сборках Tk, чем
`iconbitmap` с `.ico` — если проблема повторится и на актуальном коде,
потребуется отдельное исправление через `.ico`, а не PNG, специально
для Windows).

**Проверено:** полный набор 86 тестов проходит без изменений
(`high_dpi=False` не влияет ни на один существующий тест — это чистая
Windows-ветка, no-op на Linux/Xvfb, что и подтверждено повторным
скриншотом `CreateVaultDialog`, идентичным скриншоту ДО этого
изменения). Само исправление НЕ могло быть проверено попиксельно на
реальном Windows+HiDPI в этой сессии (в песочнице нет Windows-машины
и нет возможности эмулировать реальный масштаб экрана) — но
**пользователь подтвердил фикс на своём Windows-ноутбуке**: свежие
скриншоты `GeneratorDialog` и `ViewEntryDialog` после `git pull` +
`high_dpi=False` показывают все иконки на месте (кубик, копирование,
дискета, глаз, карандаш) и скруглённые панели/плитки без единого
разрыва — обои рабочего стола больше нигде не просвечивают.
**Важное уточнение первопричины первого "ничего не поменялось":** до
этого подтверждения пользователь безуспешно пытался запустить
`python -m gui.app`, находясь В ПАПКЕ `gui`, а не в корне репозитория —
`ModuleNotFoundError: No module named 'gui'`, поскольку `-m gui.app`
ищет пакет `gui` в ТЕКУЩЕЙ рабочей директории, а не внутри неё самой.
То есть предыдущие "ничего не изменилось" скриншоты были сделаны ДО
того, как исправленный код вообще успешно запустился на его машине —
сам HiDPI-фикс работал с самого начала, просто не был по-настоящему
проверен. **Урок для защиты:** отчёт "не помогло" стоит перепроверять
с той же дотошностью, что и сам баг — здесь заняло два раунда
диагностики, чтобы обнаружить, что дело было не в неверном
исправлении, а в том, что исправленный код ни разу не запускался.

### 10.27. Найденный и исправленный баг: плитки полей с кнопкой рядом
(«Логин», «Пароль» в `ViewEntryDialog`) на Windows рисовались плоскими —
подложка перерисовывалась один раз по устаревшему размеру

Пользователь спросил "почему они выглядят не так как на референсах" про
те же два Windows-скриншота, которые раздел 10.26 записал как
подтверждение HiDPI-фикса. Формулировка "скруглённые панели/плитки без
единого разрыва" в конце 10.26 оказалась неполной: верна для
`GeneratorDialog` и полей `ViewEntryDialog` БЕЗ кнопки рядом («Сайт»,
«Создан / изменён»), но не для полей С кнопкой («Логин» — одна кнопка,
«Пароль» — три): их плитка была плоским прямоугольником без углов и
без рамки.

**Первая попытка не помогла (записано честно).** Гипотеза была "одного
`update_idletasks()` перед перерисовкой мало, Windows нужен второй
проход" — вызов продублировали в трёх диалогах (коммит `1e58cff`).
Пользователь ответил "не помогло". Проверить гипотезу в песочнице было
нельзя (на Linux баг не воспроизводился), и именно поэтому она была
объявлена непроверенной — но стоило сразу искать механизм, который
можно воспроизвести, а не добавлять "ещё один проход". Двойной вызов
удалён как не имеющий эффекта.

**Настоящая причина — найдена воспроизведением, а не догадкой.**
`_rounded_backdrop(..., dynamic=False)` рисовал картинку подложки ОДИН
раз, по `frame.winfo_width()` в момент вызова `redraw()`. Плитка `box`
пакуется `expand=True` и сразу получает подложку, а кнопка допаковывается
в тот же `row` позже и "сжимает" плитку. Если к моменту `redraw()`
плитка ещё не сжата (порядок пересчёта геометрии на Windows-Tk другой),
картинка рисуется под СТАРУЮ, бОльшую ширину. `tk.Label` с `.place(
relwidth=1)` при этом меньше своей картинки и показывает её ЦЕНТР — а
центр скруглённого прямоугольника это плоская заливка без углов и
рамки. Это ровно то, что видно на скриншоте.

**Воспроизведение на Linux.** Скрипт строит `ViewEntryDialog`, затем
допаковывает широкую кнопку в строку «Логин» (имитация позднего
сжатия) и сравнивает размер Tk-картинки каждой подложки с реальным
`winfo_width/height` её фрейма. На коде до исправления:
`MISMATCH frame=133x37 image=261x37` (картинка почти вдвое шире
плитки); на исправленном — 0 расхождений из 6 подложек, до и после
сжатия.

**Исправление.** `_rounded_backdrop` теперь ВСЕГДА слушает `<Configure>`
своего фрейма (раньше — только при `dynamic=True`, у главного экрана),
`frame.bind("<Configure>", redraw, add="+")`. Первичная отложенная
перерисовка в конце `__init__` диалогов осталась, но больше не является
единственным шансом: любое последующее изменение размера плитки (в том
числе то самое позднее сжатие) вызывает перерисовку под финальный
размер. Две сопутствующие правки: `redraw` пропускает работу, если
размер не изменился (`<Configure>` приходит часто), и хранит одну
актуальную картинку на подложку (`backdrop.photo`) вместо бесконечно
растущего списка `self._rounded_images` (раньше каждая перерисовка
главного экрана при изменении размера окна оставляла картинку навсегда).

**Проверено:** 86 тестов проходят; воспроизведение выше; визуальной
проверки на самой Windows-машине по-прежнему нет — **нужно подтверждение
пользователя**: плитки «Логин» и «Пароль» должны быть скруглёнными и с
рамкой, как «Сайт». **Урок для защиты:** когда фикс по догадке не
помогает, ценность имеет только воспроизводимый механизм — здесь его
дало сравнение размера картинки с размером фрейма, а не очередной
вариант "подождать ещё один цикл событий".

### 10.28. Скругление ВСЕХ полей ввода: экран разблокировки и диалог
"Новая запись"

После раздела 10.27 пользователь написал "уже лучше, но почему все поля
без нормального скругления?". Причина оказалась не в Windows: скруглённой
подложкой (`_rounded_backdrop`) были обёрнуты только поля `ViewEntryDialog`,
`GeneratorDialog`, `CreateVaultDialog` и строка поиска. Два поля экрана
разблокировки ("Файл хранилища", "Мастер-пароль") и все три поля
`EntryDialog` ("Сайт", "Логин", "Пароль") остались обычными прямоугольными
`ttk.Entry` — с самого начала (разделы 10.7/10.19 прямо оговаривали, что
экран разблокировки "без `_rounded_backdrop`"), и в общем визуальном языке
приложения это выглядело как "поля без скругления".

**Исправление.** Новый метод `App._rounded_field(parent, variable, *, show,
width)` — фрейм с подложкой (`_NEUTRAL_FILL`, рамка `_NEUTRAL_BORDER`,
`_ROUNDED_RADIUS`) + `Entry` со стилем `NeutralField.TEntry` (раздел 10.17).
Возвращает `(box, entry)`; `box` размещает вызывающий код. Подложка создаётся
с `dynamic=True` (перерисовка по `<Configure>`, раздел 10.27) — поэтому
вызывающему коду не нужен список `pending_backdrops`. Применено в трёх
местах: поле пути и поле мастер-пароля на экране разблокировки
(`self._password_entry` и `<Return>` работают как раньше) и три поля в
`EntryDialog`. Дополнительно сглаживание подложек повышено со 2× до 4×
суперсэмплинга (`factor` в `_rounded_backdrop`) — края углов на Windows
получаются мягче.

**Проверено:** 86 тестов проходят; скриншоты экрана разблокировки и
`EntryDialog` на Linux показывают скруглённые поля с рамкой. На Windows —
нужно подтверждение пользователя.

### 10.29. Настоящая поддержка HiDPI вместо `high_dpi=False`; кириллица в
аватарах; иконки через Pillow

Пользователь прислал скриншот главного окна с Windows-ноутбука: "это
слишком режет глаза, повысь разрешение". Размытость — прямое следствие
фикса из раздела 10.26: `high_dpi=False` оставляет процесс DPI-unaware,
и Windows растягивает готовое окно как картинку (в 10.26 это было названо
"компромиссом" — на практике он оказался неприемлем). Правильное решение
— наоборот, включить DPI-режим и сделать так, чтобы НАША графика и размеры
в пикселях масштабировались вместе со шрифтами Tk.

**Что сделано.**
- `high_dpi=True` (значение по умолчанию ttkbootstrap) возвращено; сразу
  после создания окна `App._init_ui_scale()` вычисляет `_UI_SCALE =
  tk scaling / (96/72)` (1.0 при 96 DPI, 1.5 при масштабе Windows 150%;
  ограничено диапазоном 1.0–3.0) и выставляет размер/минимальный размер
  окна. Шрифты Tk (в пунктах) масштабируются сами; всё, что в пикселях,
  проходит через `_px()`.
- ~120 отступов (`padx`/`pady`/`ipady`/`padding`) обёрнуты в `_px(...)`
  автоматической заменой по токенам (`tokenize`), чтобы не задеть
  комментарии и строки; остальное правилось вручную: размеры
  скруглённых картинок кнопок и подложек, радиус скругления, толщина
  рамок, высота сегментов шкалы, бейджи 42px, холст советника, ширины
  колонок списка, высота строки списка, `wraplength`, фиксированные
  размеры полей `CreateVaultDialog`.
- Иконки кнопок, иконка окна и иконки сайдбара/карточек теперь грузятся
  через Pillow (`ImageTk.PhotoImage`) и масштабируются `LANCZOS`, а не
  через `tk.PhotoImage(file=...)` + `subsample` — единый путь для всей
  растровой графики (аватары и подложки и так шли через Pillow и на
  Windows работали). **Ограничение:** исходные иконки кнопок — PNG
  22×22, поэтому при масштабе выше 1.0 они увеличиваются из маленького
  исходника и чуть мягче текста; чётче будет, если перерисовать их
  крупнее (скрипт генерации в репозитории не сохранён).
- `MENEDGER_UI_SCALE` — отладочная переменная окружения (например `1.5`):
  принудительно задаёт масштаб, чтобы проверять HiDPI-вёрстку на Linux/
  Xvfb без HiDPI-экрана.

**Найденный баг: квадратик вместо буквы в аватаре.** На скриншоте для
записи "цук" в кружке был прямоугольник вместо "Ц": `ImageFont.
load_default()` в Pillow — шрифт без кириллицы. Воспроизведено на Linux.
Исправление — `_avatar_font()`: перебор системных шрифтов с кириллицей
(`segoeuib.ttf`, `arialbd.ttf`, `DejaVuSans-Bold.ttf`, …), встроенный —
лишь запасной вариант.

**Что НЕ подтверждено.** На том же скриншоте на кнопках главного экрана
не было иконок, и в заголовке окна оставалось перо ttkbootstrap, хотя на
Linux те же иконки рисуются. Причина не воспроизведена; переход на
загрузку через Pillow — гипотеза (все Pillow-картинки на Windows
работали, а `tk.PhotoImage(file=...)` — нет, возможно из-за кириллицы в
пути `C:\Users\Кирилл\...`). Нужна проверка на Windows.

**Проверено:** 86 тестов проходят при масштабе 1.0 и 1.5
(`MENEDGER_UI_SCALE=1.5`); скриншоты главного экрана, `ViewEntryDialog` и
`EntryDialog` при 1.5 — всё растёт согласованно, кириллица в аватаре
рисуется. На реальном HiDPI-экране Windows — не проверено.

### 10.30. Иконки на Windows: заголовок окна через `.ico`, картинки через
`tk.PhotoImage`, диагностика `MENEDGER_DEBUG`

После раздела 10.29 пользователь написал, что разрешение хорошее, а иконок
на кнопках нет — "ни на одной кнопке в приложении". Причина НЕ найдена
воспроизведением (на Linux иконки рисуются при любом масштабе), поэтому
этот раздел — исправление ОДНОЙ подтверждённой причины и две гипотезы с
инструментом для проверки.

**Подтверждено чтением исходника: перо в заголовке окна.** На Windows
`ttkbootstrap` ставит свою `.ico` через `wm_iconbitmap(default=...)`, а
наш последующий `iconphoto(True, png)` её не перекрывает. Исправление:
`App._window_icon_arg()` передаёт ttkbootstrap путь к нашему
`gui/icon.ico` (на win32), и тот применяет его сам; диалоги наследуют.
`gui/icon.ico` добавлен в `datas` PyInstaller. На других ОС — `None` и
прежний `iconphoto`.

**Гипотеза 1: `ImageTk.PhotoImage` для иконок кнопок.** Версия, где иконки
были видны (разделы 10.3–10.28), грузила их `tk.PhotoImage(file=...)`;
в 10.29 я перевёл их на `ImageTk.PhotoImage` (Pillow) — и иконки пропали
везде. Теперь `App._tk_image(pil_image)`: масштабирование через Pillow,
но в Tk картинка попадает как родной `tk.PhotoImage` из PNG-данных
(base64) — тот же тип, что работал, плюс масштаб. Аватары и подложки
остались на `ImageTk` (они на Windows работали).

**Гипотеза 2 (не проверена): причина в чём-то, что зависит от машины
пользователя.** Поэтому добавлен `MENEDGER_DEBUG=1`: при запуске и после
разблокировки в stderr печатаются версии Python/Tk, масштаб, наличие
папки иконок и для КАЖДОГО виджета с `image` — существует ли картинка в
Tk и её размер (подозрительные — отсутствует или 0–1 px). На Linux отчёт
показывает все 13 иконок существующими (23×23 при масштабе 1.04).
Попутно найдена и исправлена ошибка самой диагностики: у ttk-виджетов
`cget("image")` возвращает кортеж, и первая версия считала все картинки
несуществующими.

**Проверено:** 86 тестов при масштабе 1.0 и 1.5; скриншот главного экрана
на Linux — иконки на месте. На Windows — не проверено; если иконок всё ещё
нет, нужен вывод `MENEDGER_DEBUG=1`.

### 10.31. НАСТОЯЩАЯ причина пропавших иконок: в PyInstaller-сборке пути к
ресурсам вычислялись от `__file__` точки входа

Пользователь прислал вывод `MENEDGER_DEBUG=1` (раздел 10.30) и сообщил:
"при обычном запуске всё без изменений, а при запуске через консоль иконки
появляются". Вывод показал 19 существующих картинок, подозрительных 0 —
то есть код при запуске `python -m gui.app` исправен, а "обычный запуск"
— это собранный `.exe`.

**Воспроизведено.** Собрал сборку PyInstaller на Linux и запустил её с
`MENEDGER_DEBUG=1`: `ICONS_DIR=/tmp/_MEI.../icons exists=False files=0`,
кэш иконок пуст. Причина: `ICON_PATH`/`ICONS_DIR` вычислялись как
`Path(__file__).resolve().parent / ...`, а у точки входа
(`gui/app.py` в `Analysis`) `__file__` в сборке указывает в КОРЕНЬ
`_MEIPASS`, тогда как `packaging/menedger.spec` кладёт данные в
`_MEIPASS/gui` и `_MEIPASS/gui/icons`. Поэтому в `.exe` не находилось
НИЧЕГО: ни иконки кнопок, ни иконка бренда в сайдбаре, ни иконка окна

### 10.33. Собственная строка заголовка: свернуть / развернуть / закрыть
в стиле приложения вместо системной рамки

Пользователь прислал три скриншота с Windows-ноутбука (экран
разблокировки, главное окно, диалог записи) и попросил "органично
добавить кнопки свернуть, полноэкранный режим и закрыть, а то сейчас
это очень плохо выглядит": светло-серая системная строка заголовка
Windows жила отдельной полосой поверх тёмного/светлого интерфейса
приложения и спорила с ним по цвету.

**Решение — безрамочное окно (`overrideredirect(True)`) + собственный
виджет `TitleBar`** (`gui/app.py`). Системная рамка убирается целиком, а
строка заголовка рисуется самим приложением, в цвет того, что под ней:
- над экраном разблокировки — тёмная (`_SIDEBAR_BG`), над главным
  экраном — светлая в цвет "страницы" (`_PAGE_BG`), так что полоса не
  читается как отдельный элемент; тема переключается в `_show_main`/
  `_on_lock` через `App._set_chrome_theme`;
- слева — название приложения приглушённым цветом (без иконки: бренд с
  иконкой уже есть в сайдбаре/карточке), справа — три кнопки;
- кнопки — `tk.Label` с картинками-значками (`_chrome_glyph`: линия,
  квадрат/два квадрата, крестик со скруглёнными концами), нарисованными
  через Pillow с 4-кратным суперсэмплингом на НЕПРОЗРАЧНОМ фоне (урок
  раздела 10.5 про прозрачность); при наведении — скруглённая подсветка,
  у "закрыть" — красная с белым крестиком; действие срабатывает по
  отпусканию кнопки над ней же (как у системных);
- размеры идут через `_px()` (HiDPI, раздел 10.29), значки кэшируются
  в `App._chrome_images`.

**Поведение, которое теперь приходится делать самим** (системная рамка
всё это давала бесплатно):
- *Перетаскивание* — за строку заголовка (`<B1-Motion>` → `geometry("+x+y")`);
  двойной клик по ней — развернуть/вернуть.
- *Развернуть* (`_toggle_maximize`) — окно растягивается на рабочую
  область экрана (на Windows — без панели задач, через
  `SystemParametersInfoW(SPI_GETWORKAREA)`; на остальных ОС — весь
  экран), прежняя геометрия запоминается; значок меняется на "два
  квадрата"; при развёрнутом окне перетаскивание и "уголок" отключены.
- *Изменение размера* — маленький "уголок" справа внизу
  (`_grip_start`/`_grip_move`, с учётом минимального размера); растягивать
  за любую грань, как системное окно, нельзя — признанное упрощение.
- *Свернуть* (`_minimize`) — у окна с `overrideredirect(True)` `iconify()`
  не работает. На время сворачивания рамка возвращается
  (`overrideredirect(False)` → `withdraw()` → `iconify()`), а в
  обработчике `<Map>` (окно снова показано) — снова убирается
  (`_restore_chrome`) с восстановлением сохранённой геометрии.
  **Найденный при проверке нюанс:** без `withdraw()` перед `iconify()`
  окно под openbox осталось на экране (`state` = `normal`) — WM ещё не
  "подхватил" окно после смены override-redirect; с `withdraw()` —
  `state` = `iconic`, а после `deiconify()` рамка корректно убирается
  обратно (проверено скриптом под Xvfb+openbox).
- *Панель задач / Alt+Tab на Windows* — безрамочные окна по умолчанию
  пропадают оттуда. `_apply_taskbar_style` ставит `WS_EX_APPWINDOW` (и
  снимает `WS_EX_TOOLWINDOW`) через `ctypes` и один раз скрывает/
  показывает окно, чтобы стиль подхватился. Любая ошибка `ctypes`
  глотается — в худшем случае окно просто не будет на панели задач.
- *Положение при старте* — без WM окно некуда ставить, поэтому оно
  центрируется по рабочей области вручную (`_install_chrome`).

**Диалоги** получают ту же рамку через `App._dialog_chrome` (вызывается
сразу после `super().__init__`, чтобы строка оказалась сверху): строка
с названием и ОДНОЙ кнопкой "закрыть", 1px граница (`_CHROME_BORDER`,
иначе безрамочное окно "растворяется" на светлом фоне), закрытие по
Escape. `ViewEntryDialog` использует тёмную строку без текста: название
записи уже есть в его тёмной шапке, верхние углы которой стали
прямыми (скруглять их при безрамочном окне нечем — и незачем).

**Запасной вариант:** `MENEDGER_NATIVE_FRAME=1` оставляет системную рамку
(и `TitleBar` не создаётся) — на случай, если безрамочное окно на
какой-то системе поведёт себя плохо.

**Что проверено, а что НЕТ.** Под Xvfb+openbox (реальный WM) проверено:
вид обоих экранов и диалогов, наведение (красный "закрыть"),
перетаскивание, развернуть/вернуть геометрию, свернуть/восстановить,
HiDPI-масштаб 1.5 (`MENEDGER_UI_SCALE`); 4 новых теста
(`test_custom_titlebar_*`, `test_toggle_maximize_*`, `test_titlebar_theme_*`,
`test_dialog_gets_close_only_titlebar`), всего 92. **На реальной Windows
не проверено** (в песочнице её нет) и именно там возможны отличия:
панель задач/Alt+Tab, мигание при `withdraw`/`deiconify`, кратковременное
появление системной рамки при восстановлении после сворачивания, Aero
Snap и анимации сворачивания (у безрамочного окна их нет). Чтобы
увидеть изменение, `.exe` нужно ПЕРЕСОБРАТЬ (`packaging\build_windows.bat`).

### 10.34. Найденный и исправленный баг: окно "зависало" при растягивании,
"развернуть" и вообще на главном экране — скруглённые подложки
перерисовывались слишком дорого

Пользователь после раздела 10.33 написал: "панель с кнопками стала
нормальной, но вот главный экран полностью зависает". На Windows это не
воспроизводилось (в песочнице её нет), поэтому искал то, что МОЖНО
воспроизвести и измерить.

**Измерение (Linux, Xvfb+openbox, масштаб 1.0 и 1.5).** Скрипт открывает
главный экран, разворачивает/возвращает окно и имитирует 20 шагов
растягивания за "уголок", считая время `Image.resize` (им нагружена
перерисовка подложек):
- показ главного экрана — ~0,2–0,4 с на отрисовку;
- "развернуть" — ~0,6 с чистого времени `resize`;
- растягивание за уголок, 20 шагов — **3,2 с при масштабе 1.0 и 6,9 с при
  1.5** (общее время 4–8,5 с), то есть ~0,2–0,4 с НА КАЖДЫЙ шаг.
Событий мыши при растягивании приходит много, а каждое запускало полную
перерисовку всех панелей, поэтому очередь событий копилась и окно
переставало реагировать — на Windows при масштабе 150% и экране Full HD
это заведомо хуже, чем в песочнице. Раздел 10.33 сделал проблему
заметной: до него окно нельзя было растянуть ни за уголок, ни кнопкой
"развернуть", а при каждом таком действии `<Configure>` приходил всем
подложкам сразу.

**Причина.** `_rounded_backdrop` рисовал подложку целиком в 4-кратном
размере (на панели ~1100×900 px это картинка ~4400×3600) и уменьшал
`LANCZOS` — стоимость пропорциональна ПЛОЩАДИ окна, хотя сглаживание
нужно только в четырёх углах: всё остальное — ровные одноцветные полосы.

**Исправление (две части).**
1. `_render_rounded_rect` (модульная функция): суперсэмплингом рисуется
   только небольшая эталонная картинка `(2·ячейка+1)²`, из неё берутся
   четыре угловые ячейки и по одной центральной строке/столбцу для
   рёбер, которые растягиваются `NEAREST` под нужную длину, середина
   заливается цветом центра. Стоимость почти не зависит от размера
   окна: **1900×1000 px — 0,003 с вместо 0,443 с**. Результат проверен
   попиксельно против прежней полной отрисовки на 4 радиусах/рамках × 4
   масками углов × 4 размерах: максимальная разница по каналу — 0.
   Эталонное сравнение вошло в тесты
   (`test_fast_rounded_render_matches_full_supersampled_render`).
2. Перерисовка по `<Configure>` теперь схлопывается: обработчик только
   ставит ОДНУ задачу `after_idle`, и размер читается в момент её
   выполнения, а не в момент события. `after_idle` срабатывает, когда
   очередь событий пуста, поэтому серия событий при растягивании даёт
   не десятки перерисовок, а считанные единицы
   (`test_backdrop_redraw_is_coalesced_during_resize`).

**Результат измерения после правки:** растягивание за уголок, 20 шагов —
0,46 с (масштаб 1.0) и 0,73 с (1.5) вместо 4,1 и 8,6 с; "развернуть" и
"вернуть" — доли секунды чистого времени `resize`.

**Что НЕ подтверждено.** Это единственная ПРОВЕРЕННАЯ причина
"зависания", найденная измерением; на реальной Windows эффект не
проверен. Если после этой правки главный экран всё равно виснет БЕЗ
растягивания окна (например, сразу после разблокировки), причина другая —
тогда нужны подробности (в какой момент именно, мгновенно или через
несколько секунд, реагирует ли кнопка закрыть) и вывод запуска из
консоли с `MENEDGER_DEBUG=1`. **Урок для защиты:** функция, дешёвая при
фиксированном размере (диалоги), может стать узким местом, когда размер
начинает меняться непрерывно (безрамочное окно с растягиванием) —
стоимость нужно оценивать для самого частого события, а не для
однократного. Чтобы увидеть исправление, `.exe` нужно ПЕРЕСОБРАТЬ
(`packaging\build_windows.bat`).

### 10.36. Зависание — в безрамочном режиме: на Windows своя рамка стала

Пользователь запустил приложение с `MENEDGER_NATIVE_FRAME=1` (быстрая

`focus_force()`). Значит, виновата одна из этих деталей на Windows.

**Чего я НЕ знаю.** Какая именно: на Linux (Xvfb+openbox) ни синтетические

   <FocusOut>` поля поиска (подмена плейсхолдера + перестройка списка) в
   этот момент могут получать лавину событий фокуса;
2. `withdraw()/deiconify()` после смены стиля окна (`WS_EX_APPWINDOW`)
   оставляет окно в состоянии, где первый клик зацикливает активацию;
3. `focus_force()` (`SetForegroundWindow`) во время клика.
Гадать "ещё одним исправлением" не стал (уроки разделов 10.27 и 10.35).

**Что сделано.**
1. Политика рамки вынесена в `_use_native_frame(platform, env, argv)`:
   на Windows по умолчанию СИСТЕМНАЯ рамка (приложение работает так,
   как проверено), собственная — только по запросу: `set
   MENEDGER_CUSTOM_FRAME=1` или флаг `--custom-frame` (для ярлыка
   `.exe`). `MENEDGER_NATIVE_FRAME=1` принудительно включает системную и
   приоритетнее всего. На Linux/macOS поведение прежнее — своя рамка по
   умолчанию (там всё проверено). Это ОТКАТ видимой функции на Windows
   до выяснения причины, а не её исправление: рабочее приложение важнее
   красивой рамки.
2. Код опционального режима НЕ менялся — чтобы журнал, который
   пользователь пришлёт, описывал ровно то поведение, которое зависает.
   В журнал `MENEDGER_DEBUG=1` добавлены события `<Activate>/
   <Deactivate>` (активация окна), чтобы проверить гипотезу 1.

**Как найти и починить причину** (на Windows, в папке проекта):
`set MENEDGER_DEBUG=1` и `set MENEDGER_CUSTOM_FRAME=1` →
`python -m gui.app` → разблокировать, кликнуть до зависания → закрыть
через диспетчер задач → прислать `menedger_debug.log` (последние
события перед зависанием + стек "сторожа" покажут, что зациклилось).
Когда причина будет найдена и исправлена, политику можно вернуть на
"своя рамка по умолчанию" одним изменением `_use_native_frame`.
**Для проверки `.exe` нужно ПЕРЕСОБРАТЬ** (`packaging\build_windows.bat`);
тесты: `test_use_native_frame_policy` (6 случаев).

### 10.37. Причина "зависания" найдена по журналу: модальный диалог
оказывался ЗА главным окном (безрамочный режим, Windows)

Пользователь прислал `menedger_debug.log` (раздел 10.35) из запуска с
`MENEDGER_CUSTOM_FRAME=1` (`native_frame=False`). Журнал показал, что
**приложение НЕ зависало**: "сторож" (`faulthandler`) не записал ни одного
`Timeout`, то есть цикл событий ни разу не стоял дольше 3 с. Хронология:
- 8.6 с — нажатие "Разблокировать", главный экран показан;
- 10.05 с — клик по строке списка (`Treeview`) — обработан, фокус перешёл
  штатно (ни лавины `FocusIn/FocusOut`, ни зацикливания — гипотеза 1
  раздела 10.36 не подтвердилась);
- 10.30 с — второй клик по той же строке = двойной клик → открылся
  `ViewEntryDialog` (`FocusIn Toplevel .!viewentrydialog`, 10.35 с);
- далее 18 секунд тишины и три клика (28.0, 28.4, 28.6 с), у которых
  виджет — **сам диалог** (`Toplevel .!viewentrydialog`), а не его
  кнопки/поля.

**Вывод.** Диалог модальный (`grab_set`): пока он открыт, Tk доставляет
ЛЮБЫЙ клик по другим окнам приложения самому окну с захватом
(`event.widget` = диалог) — именно это и видно в журнале. То есть
пользователь кликал по главному окну, а оно было заблокировано открытым,
но НЕ ВИДИМЫМ диалогом: безрамочный (`overrideredirect`) диалог на
Windows оказывается под главным окном (главное окно занимает почти весь
экран, диалог по центру экрана — целиком им перекрыт). Для пользователя
это "главный экран зависает при клике куда угодно" — а с системной рамкой
оконный менеджер сам ставит диалог поверх, поэтому там всё работало
(результат бисекции из 10.36). Первопричина порядка окон — активация/
порядок наложения безрамочных окон на Windows; точный механизм я не
выяснял и не проверял — важно, что симптом объяснён и лечится независимо
от механизма.

**Исправление (`App._dialog_chrome`).**
1. Через 100 мс после создания диалог поднимается (`lift` + временный
   `-topmost` True → через 300 мс False, `_clear_topmost`): он встаёт НАД
   главным окном, но не остаётся поверх всех приложений.
2. Страховка от повторения любой причины: при клике мимо диалога
   (`<ButtonPress>` с `event.widget is dialog` — тот самый перенаправленный
   клик из журнала) диалог снова поднимается, берёт фокус и звякает
   (`bell`). Ловушка "модальный и невидимый" больше не молчит.
3. В журнале `MENEDGER_DEBUG` — строка о каждом диалоге: геометрия,
   `viewable`, состояние (через 250 мс) — чтобы проверить гипотезу
   напрямую.
Тесты: `test_click_outside_modal_dialog_raises_it`,
`test_dialog_clears_temporary_topmost` (всего 111). На Linux порядок окон
под openbox и так правильный — воспроизвести исходную ошибку здесь нельзя,
поэтому исправление подтверждено только логикой журнала, а не запуском на
Windows.

**Что НЕ изменено сознательно.** Политика рамки (раздел 10.36) осталась
прежней: на Windows по умолчанию системная, своя — по запросу
(`MENEDGER_CUSTOM_FRAME=1`). Вернуть "своя рамка по умолчанию" можно
одной правкой `_use_native_frame` — после подтверждения пользователя, что
в режиме `MENEDGER_CUSTOM_FRAME=1` диалоги теперь появляются поверх
(и в новом журнале строка `dialog ...: viewable=1`). **`.exe` для проверки
нужно ПЕРЕСОБРАТЬ** (`packaging\build_windows.bat`). **Урок для защиты:**
"зависание" оказалось не зависанием — журнал событий с именами виджетов
(а не только стек "сторожа") различил "программа встала" и "программа
ждёт закрытия невидимого модального окна", и три предыдущих гипотезы про
циклы событий были бы напрасными.

### 10.38. Собственная рамка снова по умолчанию на всех ОС (включая Windows)

ПЕРЕСОБРАТЬ** (`packaging\build_windows.bat`).

## 11. Упаковка в отдельное приложение (PyInstaller)

По решению пользователя менеджер собирается в **один отдельный
исполняемый файл**, чтобы на целевой машине не требовался ни Python,
ни `pip install` — актуально и для демонстрации на защите на чужом
компьютере, и просто для конечного пользователя.

**Инструмент — [PyInstaller](https://pyinstaller.org/).** Стандартный,
самый распространённый способ упаковки Python-приложений; не требует
переписывания кода — только конфигурацию сборки (`packaging/menedger.spec`).
Альтернативы (`cx_Freeze`, `Briefcase`/BeeWare) дают похожий результат,
но PyInstaller — самый простой в настройке для одного `.spec`-файла.

**Режим `--onefile`.** `packaging/menedger.spec` собирает всё
(интерпретатор Python, `tkinter`, `cryptography`, `argon2-cffi` и код
приложения) в один файл, а не в папку с зависимостями рядом
(`--onedir`). Компромисс: при каждом запуске файл распаковывается во
временную директорию, из-за чего старт чуть медленнее — для
демонстрации на защите это несущественно, а получить и передать один
файл вместо папки — удобнее.

**Собирается ОТДЕЛЬНО на каждой целевой ОС.** PyInstaller не
кросс-компилирует: чтобы получить `.exe` для Windows, сборку нужно
запускать на Windows; для Linux/macOS — соответственно на них. Один
и тот же `.spec`-файл используется на всех платформах, отличается
только ОС, на которой запущена команда `pyinstaller ...`.

**Почему пришлось явно прописать `collect_all()` для `cryptography`,
`argon2` и `ttkbootstrap`.** Первые две библиотеки используют
скомпилированные расширения — у `cryptography` это Rust-биндинги, у
`argon2-cffi` — cffi-биндинги; статический анализ импортов, которым
PyInstaller ищет зависимости кода, не всегда находит такие бинарные
модули сами по себе. `ttkbootstrap` (добавлен в разделе 10.1) не
бинарный, но несёт файлы данных — описания тем и изображения для части
виджетов — которые точно так же не видны статическому анализу.
`collect_all(...)` в `packaging/menedger.spec` явно забирает из каждого
из этих трёх пакетов всё (модули, бинарники, данные), не полагаясь
только на догадку по коду — иначе собранный файл мог бы запуститься, но
упасть с `ImportError` именно в момент вызова
`derive_key()`/`encrypt_vault()` или при попытке применить тему GUI, то
есть ровно там, куда сборка сама не потрудилась заглянуть. (На практике
установленный в системе `PyInstaller` версии 6.x уже содержит готовые
хуки для всех трёх — `cryptography`/`argon2` через
`pyinstaller-hooks-contrib`, `ttkbootstrap` — через собственный
`_pyinstaller`-модуль пакета; `collect_all()` в spec-файле остаётся
дополнительной подстраховкой, а не единственной защитой от этой
проблемы.)

**Найденный и исправленный баг сборки (после подключения `ttkbootstrap`,
раздел 10.1).** Первая пересборка после перехода на `ttkbootstrap`
падала прямо при создании главного окна:
`ModuleNotFoundError: No module named 'PIL._tkinter_finder'`.
Причина: `ttkbootstrap` рисует часть иконок темы (например, у
`Combobox`) через Pillow (`PIL.ImageTk`), а Pillow сама подключает свой
Tk-биндин через `PIL._tkinter_finder` — но не обычным `import`, а
отдельным динамическим механизмом поиска модуля, который статический
анализ PyInstaller не отслеживает (в отличие от самого факта
использования `PIL.ImageTk`, который он видит). Раньше эта проблема не
проявлялась, потому что до `ttkbootstrap` GUI не создавал ничего через
Pillow вообще. Исправление — один явный `hiddenimports.append(
"PIL._tkinter_finder")` в `packaging/menedger.spec`. Важный урок:
**"собирается без ошибок" на этапе `pyinstaller ...` и "реально
запускается" — РАЗНЫЕ проверки** — сама сборка PyInstaller прошла
успешно и в сломанной версии, ошибка проявлялась только при фактическом
запуске получившегося файла, поэтому раздел ниже про проверку реальным
запуском — не формальность.

**Проверено реальной сборкой и запуском** (в среде разработки — через
Python 3.12 с доступным `tkinter`, поскольку основной Python проекта
3.11 в этой конкретной песочнице собран без `tkinter`; сама сборка и
код приложения от версии Python 3.11 vs 3.12 не зависят): итоговый
файл — около 24 МБ (вырос после `ttkbootstrap`+Pillow), запускается без
единой ошибки импорта, окно корректно отрисовывается (включая
кириллицу в интерфейсе). Файл полностью самодостаточен — PyInstaller
сам упаковывает нужные библиотеки Tcl/Tk внутрь (`hook-_tkinter.py`),
устанавливать Tcl/Tk отдельно на целевой машине не нужно.

**Файлы:**
- `packaging/menedger.spec` — конфигурация сборки, входная точка —
  `gui/app.py` (GUI, а не CLI — это то, что запускает конечный
  пользователь двойным кликом).
- `requirements-build.txt` — `pyinstaller`, отдельно от
  `requirements.txt`: собирать приложение и просто пользоваться им —
  разные роли, обычному пользователю/разработчику не нужно ставить
  инструмент сборки.
- `.gitignore` дополнен записями `/build/` и `/dist/` — артефакты
  сборки не должны попадать в репозиторий, в нём хранится только сам
  `.spec`-файл.
- `packaging/build_windows.bat` — обёртка вокруг команды сборки для
  Windows: `cd` в корень репозитория (`%~dp0\..`, чтобы работать
  независимо от того, откуда запущен — из `packaging/` или из корня),
  `pip install` + `pyinstaller`, с проверкой кода возврата после
  каждого шага (`if errorlevel 1 ...`) и понятным сообщением об ошибке
  вместо мгновенно закрывшегося окна. Нужен, потому что **эта
  разработческая среда — Linux, а PyInstaller не кросс-компилирует**:
  настоящий `.exe` физически можно собрать только на самой Windows —
  скрипт сводит это к одному двойному клику вместо ввода команд в
  терминале.

**Команда сборки** (из корня репозитория):
```bash
pip install --upgrade -r requirements.txt -r requirements-build.txt
pyinstaller packaging/menedger.spec
```
Результат — `dist/menedger` (Linux/macOS) или `dist/menedger.exe`
(Windows). На Windows то же самое делает двойной клик по
`packaging\build_windows.bat`.

### 11.1. Найденный и исправленный баг: `ImportError: cannot import
name 'ScrolledText' from 'ttkbootstrap.widgets'`

При реальной сборке `.exe` на Windows-машине пользователя (не в этой
разработческой песочнице) собранный файл падал сразу при запуске:

```
ImportError: cannot import name 'ScrolledText' from 'ttkbootstrap.widgets'
```

**Причина — не баг в коде проекта, а незакреплённые версии
зависимостей.** В `requirements.txt` версии были указаны диапазоном
(`cryptography>=42.0`, `argon2-cffi>=23.1`, `ttkbootstrap>=1.10`), а не
точным значением. У `pip install -r requirements.txt` есть неочевидное
поведение: если пакет **уже установлен** в среде (например, остался от
более ранней неудачной попытки сборки, или используется в другом
проекте с тем же Python) и уже установленная версия **удовлетворяет**
указанному диапазону — pip его не трогает и не переустанавливает, даже
если вышла более новая версия. `ScrolledText` появился в
`ttkbootstrap.widgets` не с первой версии 1.x — соответственно, если на
машине пользователя уже стояла старая версия (например, 1.10.1 из
раннего эксперимента), формально удовлетворяющая `>=1.10`, `pip
install` её не обновлял, и `import ScrolledText` падал — хотя в коде
`gui/app.py` и в `packaging/menedger.spec` всё было верно, и точно та
же команда на чистой машине без предустановленного `ttkbootstrap`
работала бы правильно.

**Как проверялось.** Диапазоны `>=` в `requirements.txt` — это не
абстрактный риск, а реально воспроизводимая ошибка: собственная
тестовая среда этой сессии оказалась в похожей ситуации независимо —
там, где раньше был установлен пакет `cryptography` без версии через
`pip install --user`, отдельная команда `pip install -r
requirements.txt` тоже молча оставила старую системную `cryptography
41.0.7` вместо требуемой `>=42.0`, и это не проявлялось как ошибка,
пока явно не сравнили с версией, полученной в гарантированно чистом
окружении (`python -m venv` без единого предустановленного пакета).
Именно так и был подтверждён диагноз: свежий `pip install -r
requirements.txt` в чистом виртуальном окружении корректно ставит
`ttkbootstrap 2.2.3`, где `ScrolledText` импортируется без ошибок — то
есть баг не в коде, а именно в том, что диапазон версий позволяет
устаревшей уже стоящей копии пакета остаться незамеченной.

**Исправление — два независимых слоя защиты:**

1. **Точные версии (`==`) в `requirements.txt`,
   `requirements-build.txt` и `requirements-dev.txt`** вместо диапазонов
   (`cryptography==50.0.1`, `argon2-cffi==25.1.0`, `ttkbootstrap==2.2.3`,
   `pyinstaller==6.22.3`, `pytest==8.4.2` — версии, реально прогнанные
   через полный набор тестов и реальную сборку/запуск в этой сессии).
   Это не только
   защита от версии-которая-уже-стоит: `==` гарантирует, что через
   полгода `pip install` не подтянет случайно вышедшую новую несовместимую
   версию той же библиотеки и на "чистой" машине тоже — воспроизводимость
   сборки важна и для демонстрации на защите (у всех членов комиссии,
   если они попробуют собрать сами, должен получиться тот же результат).
2. **Флаг `--upgrade`** добавлен в `pip install` внутри
   `packaging/build_windows.bat` (и в аналогичную команду для
   Linux/macOS в README) — подстраховка сверх точных версий: если на
   машине почему-то стоит версия, НЕ совпадающая с закреплённой (не
   только старее, но и новее), `--upgrade` заставит pip привести её
   ровно к той версии, что в `requirements.txt`, а не оставить как есть
   в надежде, что она "достаточно новая".

**Урок для защиты проекта:** открытый диапазон версий (`>=`) в файле
зависимостей — это не только про "не сломается ли будущее обновление",
но и про куда менее очевидный сценарий "у пользователя уже что-то
стоит от предыдущей попытки, и pip это не заметит и не исправит".
Для приложения, критичного к конкретному API конкретного пакета (как
`ScrolledText` из `ttkbootstrap`), точная версия — не излишняя
осторожность, а единственный способ гарантировать одинаковое поведение
у всех, кто ставит проект с нуля.

### 11.2. Найденная и исправленная проблема: строгий `pytest==9.1.1`
ломал установку на более старом Python

Сразу после фикса из раздела 11.1 (переход на точные версии `==`)
установка на компьютере пользователя упала на новом месте:

```
ERROR: Ignored the following versions that require a different python
version: 9.0.0 Requires-Python >=3.10; ...
ERROR: Could not find a version that satisfies the requirement
pytest==9.1.1
```

**Причина.** `pytest` начиная с версии 9.0.0 требует Python 3.10+. У
пользователя на Windows-машине оказался более старый Python (сборка
`.exe` в остальном не зависит от конкретной версии Python на машине
разработчика — код проекта не использует специфичных для 3.10+
конструкций типа `match`, кроме заявленного в разделе 2 предпочтения
— так что для СБОРКИ это не блокер, но `pytest==9.1.1` в
`requirements.txt` физически невозможно поставить на таком Python, а
`pip install` останавливается на первой неудовлетворимой строке файла,
из-за чего не ставились и остальные, совместимые пакеты
(`cryptography`, `argon2-cffi`, `ttkbootstrap`, `pyinstaller`) —
`build_windows.bat` был не в состоянии даже начать сборку.

**Настоящая первопричина — архитектурная, а не только про версию.**
`pytest` вообще не нужен, чтобы пользоваться приложением или собрать
`.exe` — он нужен только для того, чтобы разработчик мог прогнать
`python -m pytest`. До этого момента он тем не менее жил в общем
`requirements.txt`, из-за чего `build_windows.bat` (который ставит
именно `requirements.txt`) тянул за собой инструмент тестирования,
совершенно не нужный конечному пользователю, ровно по той же логике,
по которой `requirements-build.txt` уже был отделён от
`requirements.txt` в разделе 11 ("собирать приложение и просто
пользоваться им — разные роли").

**Исправление:**
- `pytest` вынесен из `requirements.txt` в отдельный **`requirements-dev.txt`**
  — по той же логике разделения ролей, что и `requirements-build.txt`
  (раздел 11): пользоваться приложением, собирать `.exe` и запускать
  тесты разработчика — три разные роли с разным набором зависимостей.
  Теперь `build_windows.bat` (ставит только `requirements.txt` +
  `requirements-build.txt`) вообще не зависит от версии `pytest` и не
  падает из-за него.
- Версия в `requirements-dev.txt` закреплена как `pytest==8.4.2` —
  последняя версия ветки 8.x (`Requires-Python >=3.9`), а не самая
  свежая 9.x (`Requires-Python >=3.10`) — сознательный выбор в пользу
  более широкой совместимости с уже установленным у людей Python,
  а не "бери самое новое". Полный набор из 83 тестов прогнан заново
  именно с `pytest==8.4.2` (в дополнение к более ранней проверке с
  9.1.1) — поведение тестов от этой замены не зависит, различия между
  8.x и 9.x pytest не затрагивают синтаксис `assert`-тестов проекта.

**Урок для защиты проекта:** точная версия (`==`) сама по себе не
панацея — если зафиксировать версию пакета, которая жёстко требует
более новый Python, чем стоит у части пользователей, `pip install`
ломается ещё до того, как дело доходит до кода проекта. Отсюда и
второй урок: зависимость, нужная только для тестирования, не должна
жить в одном файле с зависимостями, нужными для работы или сборки
приложения — иначе проблема с тестовым инструментом блокирует установку
того, что реально нужно пользователю.

### 11.3. Тот же сценарий повторился с `ttkbootstrap` — добавлена явная
проверка версии Python

После фикса из раздела 11.2 установка на той же Windows-машине упала
ещё раз, с тем же по сути диагнозом, но на другом пакете:

```
ERROR: Ignored the following versions that require a different python
version: 1.19.0 Requires-Python >=3.10; ...
ERROR: Could not find a version that satisfies the requirement
ttkbootstrap==2.2.3
```

`ttkbootstrap`, начиная с версии 1.19, тоже требует Python 3.10+ — то
есть на машине пользователя Python старше, чем заявленный в разделе 2
минимум ("Python 3.11+"), и это уже второй пакет из `requirements.txt`
(после `pytest` в 11.2), который эту границу подтверждает. Дальше
подбирать версии пакетов "чтобы завелось на любом Python" — путь в
никуда: рано или поздно какой-то нужный API (как `ScrolledText` в
разделе 11.1) снова потребует более новую версию библиотеки, которая
снова потребует более новый Python. **Правильный фикс — не понижать
версии пакетов дальше, а обновить сам Python** до заявленного минимума,
как и было написано в README/CLAUDE.md с самого начала — просто раньше
это нигде не проверялось явно, и вместо понятного сообщения "нужен
Python 3.11+" пользователь видел непонятную многострочную ошибку
разрешения версий от `pip`.

**Исправление** — `packaging/build_windows.bat` теперь ПЕРЕД установкой
зависимостей явно проверяет версию Python:

```batch
python -c "import sys; sys.exit(0 if sys.version_info >= (3, 11) else 1)" 2>nul
if errorlevel 1 (
    rem понятное сообщение с инструкцией, что делать, вместо ошибки pip
    ...
)
```

Если версия меньше 3.11 (или `python` вообще не найден), скрипт
останавливается с понятным объяснением ("нужен Python 3.11+, скачайте
с python.org, отметьте „Add python.exe to PATH“") ещё до вызова `pip
install` — вместо того чтобы пользователь разбирался в списке из
полутора десятков "Ignored the following versions..." строк. Это тот
же принцип, что уже применён во всём остальном проекте (раздел 6: "все
внутренние исключения превращаются в понятные сообщения... наружу
traceback не протекает") — только на уровне сборочного скрипта, а не
кода приложения.

**Дополнительная деталь, учтённая в сообщении:** на машине может быть
установлено НЕСКОЛЬКО версий Python одновременно (например, старая 3.9
осталась от другой задачи, а новая 3.11 добавлена только что) — тогда
команда `python` в PATH может продолжать указывать на старую версию
даже после установки новой. Сообщение об ошибке явно предупреждает про
этот случай и просит перепроверить `python --version` после установки.

## 7. Требования к коду (для всех последующих модулей)

- Каждое крипто-решение сопровождается комментарием на русском: не
  "что делает строка", а **зачем именно так**, со ссылкой на
  соответствующий раздел этого файла, где уместно.
- Публичные функции — с type hints и docstring.
- Секреты (мастер-пароль, производный ключ, расшифрованные пароли) не
  логировать и не оставлять в исключениях/трейсбеках без необходимости.
- Любое изменение формата хранилища или крипто-параметров — сразу
  отражается в этом файле (разделы 2–5) и сопровождается ростом
  `VERSION`, если меняется бинарный layout.
